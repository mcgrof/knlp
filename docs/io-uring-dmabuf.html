One storage interface, several GPU exporters

The goal is a vendor-neutral Linux path between GPU memory and NVMe. An application shares an allocation through a DMA-BUF file descriptor and submits storage reads or writes through io_uring. The GPU driver supplies the memory; the storage driver maps it for the NVMe device.

The storage interface can be common while GPU drivers and allocation APIs differ. CUDA, ROCm or Vulkan can supply memory through a suitable exporter. A DMA-BUF descriptor alone does not prove that the payload stays in GPU memory or that NVMe can access it.

Current statusExperimental kernel support, working integrations, and qualification for specific configurations. This is an upstreaming effort, not a feature already supplied by every stock Linux kernel or GPU driver.

Who does what?

Four separate responsibilities
LayerResponsibilityExamples
ApplicationManage cached data, gather/scatter GPU bytes, and wait for completion.vLLM with LMCache; a separate vLLM/NIXL storage connector.
Allocation and exportOwn GPU memory and share it with the storage importer.CUDA DMA-BUF; ROCm DMA-BUF; the experimental Vulkan/RM provider.
Storage submissionRegister a shared buffer and submit offsets, lengths and reads/writes.LMCache Rust backend or NIXL IO_URING plugin.
Kernel and platformMap the allocation for NVMe and execute the admitted peer transactions.Experimental io_uring DMA-BUF support, block/NVMe, GPU exporter and PCIe route.

The implementations here submit io_uring directly. They do not call cuFile or hipFile. Those libraries have their own storage paths and would need an explicit backend change to adopt this interface.

What to take away

OpenRM is an open-source Linux kernel driver, but it is out of tree. NVIDIA's current cuFile P2PDMA route uses the open kernel modules and can avoid nvidia-fs and its custom NVMe hooks. AMD's hipFile/AIS route also uses P2PDMA; the inspected AIS driver integration is out of tree. Neither route is the new io_uring DMA-BUF path.

Vulkan could provide a common allocation API. The current NVIDIA vulkan_rm provider still uses an NVIDIA-specific export helper. A portable Vulkan exporter for both vendors needs separate implementation and NVMe qualification.

The evidence does not establish a universal speed advantage. There are cuFile P2PDMA comparisons, AMD AIS runtime comparisons and application correctness tests. Their scopes differ. Export-only Nouveau tests and future Nova enablement are not full storage qualification.
