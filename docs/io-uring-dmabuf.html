Platform routing, kernel admission, memory placement and application correctness each need evidence. Registration or a full-length completion is insufficient.

A common Linux storage interface

The goal is shared upstream infrastructure beneath existing userspace APIs, reducing bespoke out-of-tree storage integration. DMA-BUF is established; the new work is DMA-BUF-backed io_uring read/write support . Different GPU drivers can export allocations into the same storage interface while retaining their own export and peer-access rules. cuFile and hipFile could adopt this transport beneath existing APIs; this implementation uses io_uring directly and does not implement that library change.

NVIDIA cuFile PCI P2PDMA UVM exposes GPU BAR memory as Linux P2PDMA device pages. Supported direct-I/O/block/NVMe paths can consume them without nvidia-fs or the traditional custom NVMe hooks.

Sources: NVIDIA storage hooks , current GDS route configuration , and AMD's inspected implementation . A successful cuFile call can also use host-staged compatibility I/O.

The experimental dmabuf-size-ceiling-v7.3-rc3 kernel branch is pinned at 856b6583ab2f4581e81670845eadb69de7a68b30 . The cited upstream proposal covers NVMe block devices. This branch adds iomap, ext4 and XFS direct I/O, a separate DMA-BUF request ceiling, an optional DMA-optimal clamp lift and a 32 MiB driver cap. Ordinary I/O still traverses filesystem extent handling where applicable, the block layer and NVMe PCI driver.

Byte-verifying read/write selftests exercise larger requests. Actual command sizes remain bounded by controller Maximum Data Transfer Size (MDTS), mapping segments, queue limits and filesystem extents. Registration creates a context; first use may construct the reusable device mapping. A large io_uring operation does not guarantee one NVMe command. Initialized aligned XFS/ext4 files and raw NVMe are distinct test targets, not support for every inode, block driver or exporter.

What changes in the I/O path?

A conventional GPU offload path may copy KV into host DRAM before storage. The direct profile gathers engine KV into an exported GPU staging arena, then lets the storage driver DMA that payload. Host code still submits I/O and handles metadata; GPU gather/scatter copies remain.

The first I/O may construct the device mapping. Later requests reuse it while valid; invalidation still matters. “Map once” does not mean a mapping can never change.

The LMCache and NIXL profiles described here use ordinary fixed-buffer reads and writes. The pinned experimental kernel also enables registered DMA-BUF buffers for NVMe io_uring_cmd passthrough through its fixed-buffer import change and block-request mapping change . Host-exporter tests in an emulated NVMe guest validate that kernel path. GPU exporters and application-level passthrough still require separate qualification. A filesystem also needs a capable underlying importer; putting ext4 on a virtio disk does not supply NVMe DMA-BUF support.

A common interface still needs a working platform route

DMA-BUF/io_uring can unify the storage interface across GPU exporters. It cannot create a missing PCIe peer route. Qualification has to establish platform routing, kernel admission, memory representation and application correctness separately.

Devices below one switch

Useful endpoint control. A passing switch-local route does not qualify routing through the Root Complex.

Devices below separate Root Ports

A separate platform contract. Sharing a PCI segment does not imply a shared Root Port. Crossing sockets or segments needs its own qualification.

PCIe 4.0 §1.3.1, Root Complex describes peer routing between Root Port hierarchies as optional and implementation dependent. It remains optional in the inspected revisions through PCIe 7.0 §1.3.1 . A faster PCIe link does not supply that guarantee. A host-bridge route can forward PCIe traffic without copying payloads through host RAM.

Contract What must be established What alone is insufficient
Platform routing The exact port path supports the requested peer transactions. A PCIe generation, segment label or same-switch pass.
Kernel admission The running kernel and drivers admit and map the route under supported isolation settings. An allowlist edit or a topology prediction.
Memory representation The intended allocation exports and maps in GPU-local memory. A GPU pointer, large BAR, DMA-BUF descriptor or aggregate memory counter.
Application correctness Readiness, visibility, byte integrity and lifetime hold through checked completion and consumption. Registration success or a full-length completion.

Linux PCI P2PDMA has topology and platform admission rules. The admission history below is distinct from the hardware route itself. A rejected policy is not a completed hardware test; removing that rejection does not make a route correct. Exporters can apply different policies. AMD can clear peer eligibility and migrate a shared allocation into host GTT; waiting for migration fixes backing readiness, not GPU-direct placement.

Storage direction is not PCIe transaction direction

Application operation NVMe controller's GPU-facing transaction
Read storage into GPU memory PCIe Memory Writes into GPU memory.
Write GPU memory to storage PCIe Memory Reads from GPU memory, followed by Completions.

Recorded negative qualification: in one bounded cross-Root-Port test, an experimental admission change enabled VRAM resource mapping. The host-memory DMA-BUF control passed both ways. A guarded 4 KiB storage read into GPU memory passed, but the reverse storage write reported 4096 bytes completed while independent disk readback found all 0xff payload bytes. That pair failed qualification. The run did not isolate physical forwarding from DMA-address/IOMMU behavior, and it does not establish results for other devices or routes.

Qualify the claimed route and both directions

Use changing payloads, poisoned destinations, surrounding guards and independent readback. Compare host-memory and switch-local controls where available. Record the port path, memory placement, mapping decisions, firmware, kernel/driver versions and actual completions. Repeat buffer reuse and mapping changes before testing concurrent pairs. Preserve supported DMA isolation; blanket ACS overrides are not a substitute for platform support. Keep application I/O size, actual NVMe command size and PCIe packet size separate.

The kernel branch includes pci-peer-check.py and its usage and limits . Default mode predicts policy without storage transfers. Its source-pinned model does not automatically learn a modified kernel's admission table. The optional live-probe protocol needs a separately supplied reviewed helper. Follow with the LMCache payload and ordering tests ; a diagnostic pass is only the first gate.

Exporter enablement is separate from platform routing

The explicitly selected NVIDIA Vulkan/RM provider allocates device-local, non-host-visible memory, maps the same owned allocation into CUDA through OPAQUE_FD, and exports through the RM core DMA-BUF interface. It addresses native CUDA export refusal on the tested profile. It is version-coupled, does not convert arbitrary existing Torch allocations, and does not repair a peer route rejected by the platform or driver. See the provider design .

A template for future platform enablement

Arm SBSA 8.0 §1.2.18 and Appendix C GPU_02/RGPU_02, printed page 60 provides a useful template: within its GPU-compute scope, it requires peer reads and writes across endpoint hierarchies, including different Root Ports. This is a conditional platform requirement, not a guarantee for every Arm processor.

Future ecosystem enablement can pair a common Linux interface with explicit platform routing guarantees, documented port coverage, supported isolation and runnable integrity tests in both directions. The Arm requirement illustrates what a platform contract can add beyond the base PCIe specification. Already qualified pairs can use the interface while broader coverage grows.

From optional hardware to explicit Linux policy

Why Linux keeps a P2PDMA allowlist

PCIe 4.0 §1.3.1 already makes forwarding between Root Port hierarchies optional; that remains true through the inspected PCIe 7.0 revision. Linux therefore cannot treat a Root Complex as a switch that always forwards peer traffic. It admits well-defined switch-local routes and uses platform knowledge for routes through a host bridge. The source calls the table pci_p2pdma_whitelist ; this guide calls it the allowlist.

The commits below trace the main admission rules in the pinned kernel. Dates are commit dates. Each link opens the full change in Torvalds’ tree, including its original rationale and exact entries.

  1. 2019-05-01 0f97da831026

    Known-working Root Complexes become explicit exceptions

    Adds the first AMD host-bridge exception when no common upstream bridge exists. The rationale cites PCIe 4.0 §1.3.1: cross-Root-Port forwarding is optional. The exception admits known support instead of assuming every Root Complex routes peers.

  2. 2019-06-19 6dbbd053e6ae

    Missing IOMMU mappings temporarily block the exception

    Rejects host-bridge exceptions while an IOMMU is present because the kernel could not yet map these peer addresses correctly. Hardware routing capability alone did not make the software mapping safe.

  3. 2019-08-16 494d63b0d5d0

    Tested Intel entries gain a same-host-bridge limit

    Introduces the table structure and REQ_SAME_HOST_BRIDGE for tested Intel bridges. Its rationale identifies poor performance across distinct host bridges via the CPU interconnect. The flag compares Linux pci_host_bridge objects; it does not require the two endpoints to share one Root Port.

  4. 2019-08-16 5daf40b03924

    Correct DMA mappings remove the temporary IOMMU ban

    Removes the earlier iommu_present() restriction after the requests are mapped correctly. This is why the temporary 2019 guard is not advice to disable a current IOMMU. Supported translation and mapping still require qualification.

  5. 2019-12-10 bc123a515cb7

    Another tested Intel platform enters the table

    Adds host-bridge entries after successful peer transactions spanning host and PCI bridges with the IOMMU enabled. These entries have no same-host-bridge flag. That is an explicit policy choice for those entries, not a rule for all Intel systems.

  6. 2020-03-18 7b94b53db34f

    Additional Root Ports receive tested coverage

    Adds three remaining Intel Root Port entries for the platform covered by the preceding change, after reported P2P tests. Enabling one port identifier did not automatically identify the other ports.

  7. 2020-07-30 dea286bb71ba

    AMD admission becomes a CPU-family rule

    Replaces individual AMD bridge entries with an AMD CPU-family allowance. Linux can encode a documented family-level routing property instead of maintaining one bridge entry per product. Admission is therefore broader than an exact device-ID table on this path.

  8. 2022-02-25 feaea1fe8b36

    A newer Intel server bridge is recognized

    Adds a bridge entry for another supported Intel server generation. It extends the recognized platform set; it does not infer capability from PCIe link generation or add a generic forwarding mechanism.

  9. 2022-04-11 1af7c26c59eb

    Root Port discovery works beyond device zero

    Checks the first device on the root bus when it is either device/function zero or a PCIe Root Port. Previously, an allowed Root Port at a nonzero device/function could be missed. This repairs recognition of an existing allowance, not physical routing.

  10. 2026-04-10 1a1f96e3e2a8

    The table can express vendor-wide platform support

    Adds wildcard device matching while retaining the vendor match and same-host-bridge constraint. This permits a platform-wide contract to be represented without adding every device identifier separately.

  11. 2026-04-10 70cf146a674c

    Google SoCs use that wildcard mechanism

    Adds the vendor-wide SoC rule, with the commit stating that these SoCs support peer transactions between Root Ports. This records a vendor platform guarantee rather than making the PCIe base requirement universal.

  12. 2026-06-09 0ba76b19fd4c

    Accelerator root buses gain their own recognition

    Adds Intel crypto, data-streaming and analytics accelerator entries because such an accelerator may be the first device on its own root bus. The commit discusses future ACPI HMAT capability reporting to avoid continual table growth; it does not implement that discovery mechanism.

  13. 2026-07-22 894a78088fc3

    NVIDIA CPU platforms gain explicit entries

    Adds NVIDIA CPU-platform identifiers for supported peer transactions. These are host-platform allowances, not a blanket approval of every NVIDIA GPU, exporter or GPU/NVMe pair.

An absent entry is an unqualified route, not a completed negative hardware test. Adding an entry only changes Linux admission. It adds no forwarding hardware, fixes no exporter and proves no payload integrity. Require documented platform support and independently verified reads and writes before proposing broader enablement.

See Linux’s P2PDMA documentation for topology and lifetime rules. Table entries, CPU-family rules and exporter-specific decisions must be checked against the running kernel; a policy prediction is not a transfer result.

A transition plan for existing NIXL users

  1. Keep your current baseline. Record backend, model weights, layouts, chunk/block geometry, token IDs, chosen-token logprobs and transfer counters. Preserve the current network or GDS configuration for rollback.
  2. Qualify ordinary storage first. Use the dated plugin and matching API-v2 Python binding. The historical nixl==1.5.0 API-v1 wheel is incompatible with this pinned plugin. Begin with buffer_mode=host on a fresh, initialized scratch file. Verify independent readback before serving.
  3. Measure classic registration separately. Select buffer_mode=fixed . Keep prompts, target, lengths and concurrency unchanged. Confirm the fixed path actually ran.
  4. Introduce DMA-BUF deliberately. Boot the experimental kernel, verify exporter/importer support, then select buffer_mode=dmabuf and register an owned export using metaInfo="dmabuf:<fd>" . This mode requires every memory registration on that engine to carry a DMA-BUF. Use separate engines if ordinary host buffers are also needed.
  5. Choose the higher layer. Stay with the separate vLLM/NIXL connector for a NIXL storage experiment, or use the direct LMCache backend for LMCache cache management. This is not a switch that turns stock NixlConnector network transfers into storage P/D.
  6. Roll back without sharing formats. Restore the original connector/backend configuration. LMCache and NIXL storage metadata are not interchangeable; use isolated targets and migrate/recompute cache contents explicitly.

Corrections found during validation

Local tests found two runtime bugs. LMCache b8845f7c prevents repeated close from submitting cleanup to a stopped receiver event loop. The regression reproduces the timeout and coroutine warning on the base; all 33 asynchronous backend tests pass with the fix.

In the separate NIXL lane, vLLM 2697fd5ead registers the whole contiguous host staging arena once with CUDA. Copies crossing separately registered chunks previously failed with cudaErrorInvalidValue. Storage registrations retain their DMA-BUF boundaries. The CUDA regression, 52 adapter tests and 57 same-GPU model continuations pass; four adapter hardware gates remain explicit.

Use the follow-up branches linked below when reproducing these results. The original feature refs are unchanged. The P/D correction details distinguish regression checks from model measurements; neither fix extends the hardware qualification above.

A test ladder that avoids false positives

  1. Prove target identity, initialized extents, alignment and kernel capability. Test a harmless owned file before a dedicated block target.
  2. Write known payloads and independently read/hash them with a fresh reader. Check registration mode and actual native operation path.
  3. Test finite submission pressure, short reads, partial submissions, cancellation and shutdown. A timeout is not proof DMA stopped.
  4. Run the same no-connector model oracle and split/recompute control before comparing offload restoration. Cold L1 and payload-read counts must establish a real restore.
  5. For P/D, verify READY/claim/adopt/restore/ACK ordering, eviction protection and strict failed-load rejection. Add warm prefixes, concurrency and reader/writer failure as separate cases.
  6. Only then measure latency, throughput or host-memory savings against your existing NIXL baseline. Report device command traces separately from logical I/O counts.

A GDS-labelled arm must also establish that GPU-direct storage engaged. A cuFile POSIX compatibility fallback is a useful staged baseline, not a measurement of GPUDirect.
