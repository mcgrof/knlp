Inference systems · KV-cache offload reads

ReadPlan L2

What does a KV-cache offload read do before its bytes move?

Serving engines save the attention state of text they have already processed, and LMCache can keep that state on storage for later requests. Each read from storage first has to find the object and decide how to read it. This project asks how much that lookup work costs on network storage, and whether remembering the answer could help.

Current status  ·  Results  ·  Held descriptors for NFS users

Motivation

KV-cache offloading is usually treated as a bandwidth problem: move reusable inference state back to the engine faster than the engine can recompute it. Every offload hit also starts with a control-path question. Where is the object, which backend holds it, which byte range must be read, and is that location still valid? Depending on the backend, the answer can take a key lookup, a metadata request, a file open or a location lease before the first byte moves. We call the answer a read plan: what to read and from where, not the bytes themselves.

Sidharth Bajaj and Venkatraghavan Srinivasan describe one large-scale answer in Meta's AI storage blueprint at scale (Engineering at Meta, July 1, 2026). Meta describes separating object-location metadata from data transfer and caching read plans in its AI storage stack. That motivates a question here: could a metadata plan adapter help pNFS-backed KV-cache workflows?

Meta's article concerns its own storage system and training workloads; it does not establish a benefit for pNFS or KV-cache serving. Its metadata read-plan cache is also separate from the data cache it describes, and the article lists inference challenges as future work. Existing client caching may already remove much of the work. The task is to measure what remains, and to preserve correctness when locations change.

Current status

The read-plan cache is not needed, and one simpler change is. On local XFS, NFS loopback and NFS over a 1 Gb/s link, the per-object control work added at most 14.8% to an 8 MiB request, and LMCache's native connector already removes most of it. On pNFS the kernel client keeps file layouts across close, so the only metadata work left on a repeated read is an open and a close: four metadata-server operations per object read on the Lattice server. Keeping read descriptors open (held_fd_capacity) removes them. In our one-host pNFS lab that made one 8 MiB read 22.4% faster and let 16 clients reach 140,427 reads per second against 37,926 with open per read. The held descriptors page is written for NFS and pNFS users who want to check this on their own deployment.

Profiling the native read path then showed where a page-cache hit spends CPU: the copy itself and the read pool's thread handoff, not metadata. A new read_mode setting with three values, pool, inline and adaptive, trades that handoff against latency. Reading into GPU memory with DMA-BUF costs almost no host CPU and is bounded by the drives, and a projection onto datacenter GPUs shows that the NVMe bandwidth needed is cheap against the GPU. The results page has the measurements. A Linux NFS client change gives each open file's state its own lock, so threads opening different files under one credential, as LMCache's reader pool does, no longer share one; it raised opens per second 64% at 8 threads on a virtual machine. The NFS and pNFS page has the branches and one make target to test both changes on your own mount.

Seven defconfigs reproduce the work: the CPU-only rpl2-smoke, the mounted-filesystem baseline rpl2-mounted-fs, the three pNFS lab profiles rpl2-pnfs-lab, rpl2-pnfs-sweep and rpl2-pnfs-remote, and two that run on a filesystem you already have as an ordinary user: rpl2-closure, the read-plan closing measurement at one position, and rpl2-site, which adds the many-reader sweep and the read modes. See the reproduction page.

Terms used on these pages

Glossary
TermMeaning here
KV cacheThe key and value tensors a transformer saves for tokens it has processed, so later tokens need not recompute them.
Offload readLoading saved KV objects from a storage tier back into the serving engine. LMCache calls its storage tiers secondary or L2 storage.
Read planThe answer to "how do I read this object": which backend, path or server, byte range and validity token.
Metadata workLookups, opens, attribute checks and location requests that run before or alongside the data transfer.
pNFSParallel NFS, part of NFS version 4.1 and later. A metadata server hands the client a layout describing where file data lives, and the client then reads the data servers directly.
Page cache and O_DIRECTLinux keeps recently read file data in memory, the page cache. Opening a file with O_DIRECT asks the kernel to bypass it, where the filesystem supports that.
