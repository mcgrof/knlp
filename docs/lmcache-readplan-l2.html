LMCache ReadPlan L2

Metadata-Aware KV-Cache Offload Reads

Can a cached read plan reduce the control-path latency of a KV-cache offload hit? This is a project inception note for an optional LMCache secondary-storage adapter that caches where a KV chunk lives and how to read it, so repeated hits can amortize backend metadata resolution before bytes move. It is an unvalidated hypothesis, stated so it can be falsified.

1. Motivation 2. Hypothesis 3. Proposed shape 4. What it might improve 5. Flex Files v2 as a future use case 6. What would falsify this 7. Status and references

1. Motivation

KV-cache offloading is usually framed as a bandwidth problem: move reusable inference state from a slower or larger tier back to the serving engine faster than recomputing it. But every successful offload hit begins with a control-path question — where is the object, which backend holds it, which byte range must be read, and is that location still valid? Depending on the backend, an L2 hit can require a key-existence check, a metadata or manifest lookup, selection among adapters or locations, resolving an object name into paths, ranges, offsets or extents, opening a file or obtaining a handle, registering a transfer path, and handling leases or stale locations — all before the first KV byte is read.

For local storage this work may be negligible, and data transfer may still dominate. The point of the project is to measure whether metadata and setup are material in realistic KV-offload regimes, not to assume that they are.

2. Hypothesis

Hypothesis. An optional LMCache L2 adapter could cache a compact read plan for frequently accessed KV chunks or object ranges, allowing repeated L2 hits to bypass or amortize backend metadata resolution and begin data movement sooner.

A read plan, at brush-stroke level, records a cache key or object identity, a backend or location, a byte range, a generation or validity token, an expiry, and a transfer hint. It caches the answer to "how do I read this," not the KV bytes themselves, and it must be cheap to validate and safe to invalidate.

3. Proposed shape

The adapter sits inside LMCache's existing secondary-storage path, splitting plan resolution from byte movement:

vLLM / inference engine
         |
      LMCache
         |
   ReadPlan L2 adapter
      /          \
plan lookup     byte backend
                   |
         POSIX / GDS / NIXL / object store

It is optional and preserves ordinary LMCache behavior when disabled. The first prototype uses an ordinary storage backend — likely POSIX — and does not depend on pNFS Flex Files or any distributed metadata service. The inference engine remains unaware that a storage plan exists.

4. What it might improve

Possible benefits, none promised until measured: lower L2 lookup latency; lower warm-hit time-to-first-token; fewer repeated metadata calls and fewer sequential backend probes; a place to cache backend capabilities and transfer preparation; easier prefetching of metadata before bytes are needed; and a common home for future tier and locality policy.

The likely value grows with many small chunks, high cache reuse, multiple L2 backends, remote metadata services, network filesystems, object storage, or backends whose data placement changes independently of LMCache. It shrinks toward zero when the backend already caches all relevant metadata cheaply.

5. Flex Files v2 as a future use case

One intended future provider behind the generic ReadPlan interface is pNFS Flexible File Layout v2. Flex Files layouts can describe file ranges and data-server mirrors; the metadata server can provide a per-layout mirror-utility estimate; and the storage system retains authority over placement, replication, and tiering. A future provider might translate an inference object's latency, locality, trust, durability, or reuse requirements into storage policy and return a cached plan to LMCache, amortizing one broad object-range plan over many chunk reads.

Kept honest. Flex Files v2 does not today standardize an arbitrary inference-SLO request such as "put this KV range in the lowest-latency secure tier," and userspace LMCache cannot currently inspect or select kernel pNFS layouts directly. Flex Files is one potential provider behind a generic interface, not a mandatory dependency and not the project's reason to exist.

6. What would falsify this

  • metadata and setup are negligible next to the data path;
  • current backends already cache all relevant metadata efficiently;
  • an extra adapter adds more synchronization and queuing than it removes;
  • warm-hit time-to-first-token does not improve;
  • plan invalidation proves too expensive or unreliable;
  • or gains appear only under artificial metadata delays.

A negative result is useful: it redirects effort toward chunk layout, gather/scatter, DMA granularity, prefetching, or the storage data path, and says plainly that the control path was not where the time went.

7. Status and references

Status: project inception / unvalidated hypothesis. The first step is a backend-independent, optional LMCache secondary-storage adapter with a POSIX byte backend, instrumented to separate control-path time from data-path time before any caching is added.
