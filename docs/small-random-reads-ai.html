Research tracker

Small random reads
in AI workflows

This page tracks the leading use cases we have found for small random reads below 4096 bytes (4 KiB) in AI workflows. Recommendation embeddings, ANN retrieval and GNN feature gathering are the clearest examples so far.

We also try to identify whether each workload is known to use Direct I/O or Buffered I/O, and whether it could benefit from using buffered I/O in the future.

knlp supports early AI R&D through reproducible experiments. It is available as a kdevops plugin and also runs on an existing host. Kconfig presets and Make targets let others repeat a study, inspect the results and test changes. The reproduction section lists starting points for this work.

We use ebpf-syscall to record I/O from different AI workflows, compare application requests with device traffic, and replay the recorded storage access patterns. The aim is to make questions about read amplification, caching and data layout reproducible. This tracker is one R&D use case for those tools.

kvio provides recording and replay for KV-cache offloading workflows, including LMCache-based experiments. Here, the focus is small random reads below 4096 bytes; conventional KV-cache offload usually involves larger transfers.

Research notes

Recommendation embeddings

Supporting Massive DLRM Inference through Software Defined Memory (Audio Summary) describes small row lookups and a direct-I/O implementation with an application cache. Its measurements favored that design over mmap. A buffered-read comparison would need to account for the different cache granularity and available RAM.

The NVMe SGL bit-bucket mechanism reduces the unused data transferred to host memory. Keith Busch’s 2022 partial-sector read series proposed exposing this through direct I/O. The support was never merged upstream and remains out of tree. Ordinary buffered reads can return small records, but do not reproduce that transfer mechanism.

ANN retrieval and reranking

FusionANNS (Audio Summary) shows how placement and page reuse can reduce redundant reads of small reranking vectors. Its direct-I/O implementation and the buffered SamsungDS prototype provide different starting points for further work.

DiskANN’s Linux reader and Qdrant’s mmap storage illustrate the range of access paths already used in ANN systems. A comparison should preserve retrieval quality and include the complete record read, index overhead and reranking traffic.

GNN feature gathering

GNNs gather feature vectors for sampled neighbors before aggregation. Small, scattered feature records can cause much larger storage reads when the feature table is on SSD. The DGraphFin showcase records useful feature bytes and NVMe commands using eBPF, then replays the device access pattern without feature values.

Page-aware sampling and changing the I/O backend should be evaluated separately: the current showcase’s arms consume different useful-byte totals. For an I/O comparison, hold requested feature IDs fixed.

A buffered feature reader would let us test the same requests through the page cache. The papers below extend this work to larger GNN datasets, graph transformers and Kumo’s relational models.

Session state and agent metadata

The Storage-Next analysis (Audio Summary) includes classical key-value-store and ANN case studies. Session state and reasoning metadata appear as motivations, with no separate application trace sufficient to reproduce their storage demand.

RocksDB supplies a practical buffered-read baseline and direct-I/O options. The next step is to identify a real record format and workload. The LMCache / kvcache.io agentic-cache capacity projection can help with sizing, but does not specify individual I/O requests.

GNNs and graph transformers

The feature store and graph structure can be much larger than the model’s weights. Our DGraphFin feature table fits in RAM, so that experiment forces SSD access to study read amplification. GIDS supplies larger public examples, while KumoRFM-2 describes an SSD-backed relational graph engine. These give us several ways to study feature gathering at different scales.

Financial workloads

Nubank: Your Spending Needs Attention (Audio Summary) describes nuFormer, which learns from transaction histories and combines them with tabular features. The updated paper reports production use for credit-default prediction. Its daily batch inference is a useful case for tracing history and feature access. The audio summary covers an earlier version of the paper.

Visa Research: TransactionGPT (Audio Summary) evaluates transaction modeling and anomaly detection on billion-scale payment data. It is another concrete financial workload to investigate for feature and history access.

Both use transaction transformers. Their papers do not establish a GNN storage path, sub-4096-byte reads, or a Direct I/O / Buffered I/O choice. Those details need a workload capture before they can enter the main table as known small-read cases.

MUVERA and REFRAG

MUVERA (Audio Summary) addresses retrieval. A model such as ColBERT represents a document with many token vectors. MUVERA converts these sets into fixed-dimensional encodings (FDEs), with different constructions for queries and documents. Their dot product approximates the original multi-vector similarity, so a conventional vector index can find candidates. Reranking then uses the original token vectors. The paper’s online setup compresses a 10,240-dimensional FDE to a 1,280-byte product-quantization code; index data and reranking vectors add storage.

REFRAG (Audio Summary) addresses the context supplied to generation. An encoder compresses token chunks into embeddings, which are projected into the decoder’s input space. The generation path is trained to use these compressed representations, shortening the sequence the decoder processes. It still computes its own attention and KV state. A cached REFRAG chunk embedding is therefore different from a MUVERA retrieval encoding; an FDE is not automatically an input a language model can understand.

Our MUVERA visualization and experiment tracker studies the storage question behind both approaches: how small can a useful representation be? It separates the REFRAG-inspired memory and transfer study, the local ColBERT-based retrieval approximation, and the new target using Google’s FDE construction. Google-backed quality results remain pending. The recorded memory measurements do not establish cold-NVMe performance or REFRAG answer quality.

Run make defconfig-google-muvera-small && make to extend the study. The next step is to qualify retrieval quality against serialized size, then measure full-record reads, page reuse and amplification. The legacy optional NVMe reader needs complete-record handling above 4 KiB before those tests.

Engram: host DRAM today, possible NVMe tiering at larger table sizes

DeepSeek’s Engram paper (Audio Summary) separates lookup-table capacity from GPU computation. Lookup addresses depend on the input tokens, allowing host-memory fetches to overlap earlier layers. Its separate systems experiment puts a 100B-parameter table entirely in host DRAM and reports at most a 2.8% throughput penalty. That experiment demonstrates DRAM offload over PCIe; it does not test NVMe.

The trained Engram-27B and Engram-40B variants contain 5.7B and 18.5B lookup-table parameters. At two bytes per parameter, their table payloads are about 11.4 GB and 37 GB; the separate 100B table would be 200 GB. These are BF16/FP16 capacity calculations, not measured DRAM footprints. All three fit the 256 GiB available-DRAM budget used by default in the LMCache / kvcache.io Engram I/O projection.

Using that calculator’s two-byte storage assumption and no additional unique HBM capacity, table payload exceeds memory above these thresholds:

These multipliers apply to Engram tables, not the whole model. “Available DRAM” is what remains after other uses and overhead. With 1 TiB reserved, the 40B variant’s table would need to grow roughly 30-fold before its payload alone exceeded memory. Less DRAM or several models sharing a host could justify NVMe earlier. Crossing the threshold creates a capacity case for tiering; the actual small-read demand depends on which rows miss the cache and whether prefetch completes in time. Longer contexts and larger batches increase lookups, not this static table’s size.

Model weights and HBF

LLM in a flash demonstrates selective weight loading with reuse and contiguous bundling. A small row can be part of a larger required bundle, and dense layers still consume substantial aggregate bandwidth.

Future work could test where selective random reads from SSD are viable relative to approaches such as High Bandwidth Flash (HBF). Useful comparisons need active bytes per token, miss rate, latency deadlines, CPU and transfer costs, and achieved inference throughput. No equivalence is assumed.

Conventional attention-KV offload is outside the leading sub-4-KiB cases here. The LMCache / kvcache.io KV-cache I/O projection covers the larger tensor and token-block transfers common in those paths. Fine-grained variants would need their own measured request distributions.

Buffered I/O improvements to evaluate

Ongoing Linux kernel work aims to improve the scalability of small buffered reads through the page cache. Some workflows above could benefit where many CPU threads read shared cached data. The benefit will depend on their access pattern and how much work already completes in an application cache.

One current example is Linus Torvalds’s page-reference scalability series. It reduces reference-count contention during eligible cached reads. It is a possible optimization for buffered-read implementations; it does not reduce the storage transfer size on a cache miss, and mmap uses a different access path.

To investigate a small-read workload, keep the requested records and quality target fixed, change one layout or I/O choice, and record both logical requests and device traffic. A saved access trace lets others repeat the storage comparison without the original feature values. A full application reproduction also needs the model, data preparation and workload configuration.

Measurements to keep with each result

Record useful bytes, actual syscall sizes, cache hits, completed device bytes, queue depth, CPU cost and application latency. A small logical record may cause a 4 KiB or larger storage read; a page-cache hit may cause none. Keep NVMe logical block size and the drive’s internal granularity separate.

Use resident, mixed and cold working sets. Hold useful work and quality fixed when comparing I/O paths, and record source revisions, hardware, memory budgets and variation across repeated runs. A file on the target filesystem is sufficient for buffered testing; raw NVMe access is not required.

Device traces support storage replay. Page-cache evaluation also needs logical requests, sharing and concurrency, including reads that never reached the device. Traces can omit feature values while retaining the access structure needed for a meaningful comparison.
