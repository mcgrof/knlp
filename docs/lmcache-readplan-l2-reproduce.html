ReadPlan L2 / Reproduce

Reproduction

Run the read-path profiles

Seven defconfigs reproduce this work. The smoke profile tests the tools on any Linux machine, and the mounted profile times whole-object reads on a filesystem you supply. The closure and site profiles run LMCache's native connector on a filesystem you already have, as an ordinary user: per-object NFS RPCs, open per read against held descriptors, many readers and the three read modes. The three pNFS lab profiles build a complete pNFS system on one host. Only the lab needs root, and none of them changes your system's settings.

1. Prerequisites

You need Linux, GNU make, Python 3.10 or newer and a checkout of knlp. The tools use only the Python standard library. The defconfig step uses the kconfiglib package when it is installed; without it the defconfig is copied as it is, which is enough for these profiles. Git is optional: when present, each record names the source commit.

The mounted profile also needs two directories that you create, both outside the source tree. The target directory holds the test objects; the output directory receives the records. The default object set is sixteen 8 MiB objects, 128 MiB in all.

The site, closure and pNFS profiles also build LMCache's CPU extensions, which needs git, a C++ compiler and a Python with torch. Give that Python in CONFIG_KNLP_RPL2_PNFS_PYTHON, or leave it empty and have uv create one with CPU torch. Only the pNFS lab profiles need root and the Lattice build dependencies listed in their section.

2. Run the CPU-only smoke tests

make defconfig-rpl2-smoke
make

Plain make runs rpl2-doctor, which checks the Python version, then rpl2-smoke, which runs the unit tests in tools/reproduce/rpl2/tests. They exercise the record schema, the immutable object set, corrupt and truncated objects, and the skip that replaces a direct-I/O run when the filesystem refuses O_DIRECT. They write only to temporary local directories and finish in well under a second. A passing run ends with OK; the direct-I/O test reports itself as skipped on a temporary filesystem without O_DIRECT.

3. Measure reads on a mounted filesystem

make defconfig-rpl2-mounted-fs
make RPL2_TARGET=/mnt/share/rpl2 RPL2_OUTPUT=$HOME/rpl2-records

The two variables name the target and output directories. You can also store them in the configuration with make menuconfig, where the same menu chooses the I/O mode, object size, object count, request count and seed. Plain make runs three steps, which you can also run one at a time:

make rpl2-doctor RPL2_TARGET=/mnt/share/rpl2 RPL2_OUTPUT=$HOME/rpl2-records
make rpl2-run    RPL2_TARGET=/mnt/share/rpl2 RPL2_OUTPUT=$HOME/rpl2-records
make rpl2-report RPL2_OUTPUT=$HOME/rpl2-records

rpl2-doctor prints one line per check: the filesystem type, whether the target is writable, whether it has room for the objects plus 10%, whether the object size suits the chosen I/O mode, and whether an aligned O_DIRECT read works there. It stops with an error when a required check fails.

rpl2-run writes the objects once from the seed, syncs them, makes them read-only and lists their SHA-256 digests in a manifest. A later run with the same seed, size and count reuses them; a mismatched or unrecognized directory is refused, never overwritten. Each request then opens one object, reads all of it and closes it. Requests visit the objects in order and wrap around, and every request is recorded, including the first read of each object. The digest check runs after the timed region. rpl2-report validates the newest records and writes a summary; RPL2_RECORDS=/path/records.jsonl selects an older run.

The default I/O mode is O_DIRECT into a page-aligned buffer, which bypasses the client page cache where the filesystem honors it. The buffered mode is useful as a contrast, but its reads may come from memory, particularly right after the objects are written. The tools never drop caches, so the records describe cache state as uncontrolled.

4. Use an NFS or pNFS mount

The tools do not mount anything. Mount the export yourself, following the nfs(5) manual page and your server's documentation, then point RPL2_TARGET at a directory you own on that mount. The doctor reports the filesystem type and the NFS protocol version; it deliberately omits the server name and address.

A Linux client uses pNFS only with NFS version 4.1 or later and only when the server offers layouts for the file. The basic tools do not check whether a read used a layout or which server returned the bytes. Treat a result as an NFS result unless you have separate evidence of the path; the pNFS lab below collects that evidence. Large differences between reruns usually mean the client, server or network is also doing other work, so note what else was running.

5. Build a pNFS lab and compare held descriptors

Three further profiles build a complete pNFS system and use it to compare stock LMCache with one change: LMCache's native file connector can keep read-only file descriptors open across loads (held_fd_capacity). A repeated read through a held descriptor needs no open or close, and the existence check needs no attribute lookup. On pNFS those are calls to the metadata server. The kernel already keeps a file's layout across close, so they are the metadata work that remains on a repeated read.

The lab runs on one Linux host. It consists of the Lattice pNFS metadata server with its RonDB catalogue, one or more NFSv3 kernel data servers and a kernel NFSv4.2 client, each in its own network namespace on a private subnet. Setup fetches and builds Lattice, RonDB, ntirpc and LMCache at checked pins into a directory you name, without root and without system packages. The other steps need sudo, because they create namespaces, start a per-namespace NFS server, mount and trace. They do not touch the host's own NFS server, exports or rpcbind, and teardown compares those with the state recorded before the lab came up.

make defconfig-rpl2-pnfs-lab
make RPL2P_ROOT=/disk/rpl2p RPL2_OUTPUT=$HOME/rpl2-pnfs-records

Plain make runs the following steps in order:

  1. Setup.
  2. A one-minute smoke test, whose receipt must say PASS.
  3. Lab bring-up with sealed, seeded test objects.
  4. An RPC fingerprint.
  5. A paired screen.
  6. Teardown.

The fingerprint traces, from a fresh mount, which calls each arm sends to which server, for the first touch of each object and for 100 repeated requests. The screen alternates stock and held-descriptor runs in three blocks of 200 requests each. It uses one 8 MiB object per request and sixteen distinct 8 MiB objects per request, and verifies a digest on every 8th request. Its summary gives the mean of the paired block-median differences with a block-bootstrap interval.

pNFS lab profiles
DefconfigWhat it runs
rpl2-pnfs-labOne host: smoke test, RPC fingerprint and paired screen.
rpl2-pnfs-sweepOne host with up to 16 extra clients, each its own NFS client identity. All of them read the same 16 objects at once, with and without held descriptors. Each cell records metadata-server operations and CPU per object read, aggregate throughput and latency.
rpl2-pnfs-remoteThis host as the client of a lab on another host. On the lab host, list this host in CONFIG_KNLP_RPL2_PNFS_REMOTE_CLIENTS and run make rpl2-pnfs-setup rpl2-pnfs-up. Then set CONFIG_KNLP_RPL2_PNFS_LAB_HOST here and run make.

A lab is named by a prefix (default rpl2p) and a private /24 subnet (default 10.247.0). Its namespaces, units and interfaces carry the prefix, and bring-up refuses to start when a lab with that prefix exists or the subnet is already routed. Remote clients reach the lab through a host route. Because Docker sets the forwarding policy to drop, bring-up adds two accept rules for the lab subnet to the DOCKER-USER chain, and teardown removes them. Single targets such as make rpl2-pnfs-up, rpl2-pnfs-screen and rpl2-pnfs-down are listed by make rpl2-help.

A one-host lab shares CPU, memory bandwidth and the page cache among the metadata server, the data servers and every client, and its links are virtual. It shows which operations each arm sends and what they cost this host. It does not predict throughput on a real fabric, where payload time and the metadata server's own hardware set the balance. For larger systems you can run more data servers (CONFIG_KNLP_RPL2_PNFS_DATA_SERVERS), clients on other hosts over the real network, or the same readers against your own pNFS deployment with the site profile. native_reader.py in tools/reproduce/rpl2/pnfs takes a mount path and an LMCache tree, and does not depend on the lab.

6. Measure your own filesystem: the site and closure profiles

Two defconfigs run the lab's readers against a directory you already have, for example on an NFS server or on a pNFS deployment with many data servers and NVMe drives. They run as an ordinary user and build only LMCache's CPU extensions into RPL2P_ROOT. They mount, export and reconfigure nothing, drop no cache, and write only into one subdirectory, rpl2-site, of the directory you give; delete it to undo a run. About 1.1 GiB must be free there.

make defconfig-rpl2-site
make RPL2P_ROOT=/disk/rpl2 RPL2_OUTPUT=$HOME/rpl2-records \
     RPL2_SITE=/mnt/pnfs/scratch

Plain make builds LMCache and then runs these steps into one run directory, site-<UTC time> under the output directory:

Site profile steps
StepWhat it does
doctorRecords the filesystem type, the NFS mount options and pNFS layout driver from /proc/self/mountstats, free space, and whether an O_DIRECT read and a buffered RWF_NOWAIT read work there.
fixtureSeals 64 objects of 8 MiB and 64 of 256 KiB, written once with digests. A later run reuses them.
fingerprintReads 8 hot objects once and then 100 times, open per read and held, and records the NFS RPCs each phase sent per object from the client's per-mount counters. No trace or root is needed.
screenThree alternating blocks of 200 requests, open per read against held, with 1 and with 16 objects of 8 MiB per request; the summary is the paired block-median difference with a bootstrap interval.
sweep1, 2, 4, 8 and 16 reader processes on this host, 16 objects of 256 KiB per request for 20 s, open per read and held, with throughput, latency, client CPU and RPCs per read. With a Lattice metrics URL it also counts server operations per read.
readmodesread_mode pool, inline and adaptive at 1, 4 and 16 requests in flight from one connector, over 16 cached objects of 256 KiB. Bytes are verified after each timed window.
kernelRuns the kernel selftest nfs_open_scale on the directory with one shared credential, for an A/B of client kernels; skipped unless CONFIG_KNLP_RPL2_SITE_KERNEL_SELFTEST names the binary. The procedure is on the held descriptors page.

The run ends with site-summary.md and site-summary.json, which put your figures beside ours, each with the scope it was measured in. Single steps run with make rpl2-site-<step> RPL2_SITE_RUN=<run dir>, and make rpl2-site-report RPL2_SITE_RUN=<run dir> rewrites the summary. Settings such as the label, the number of data servers and drives (recorded only), the metrics URL, the client counts and the read-mode depths are in make menuconfig under the site profile. The client's RPC counters are per mount, so run on a mount the run has to itself. The sweep's processes share this host's NFS client identity; to load the server from many identities, run the profile on several client hosts at once.

The rpl2-closure defconfig runs only the doctor, fixture, fingerprint and screen steps, with the published held-descriptor build of LMCache. It reproduces the measurement that closed the read-plan question: how much of an 8 MiB object read is per-object control work, and whether holding the descriptor removes it. Run it at each position you care about, changing CONFIG_KNLP_RPL2_SITE_LABEL: a local directory, an NFS export of the same host mounted over loopback, and an NFS export over the network. The original closing screen compared LMCache's Python file adapter with a raw-block image; this profile compares open per read with held descriptors in today's native connector, which is the remedy the screen pointed to. Its numbers are therefore comparable in mechanism, not identical in arms.

The site profile builds LMCache from the branch 2026-10-31-proto-fs-native-inline-reads, which has both held descriptors and read_mode. With an LMCache build that has no read_mode, turn the readmodes step off.

7. Read the records and summary

Each run creates rpl2-<UTC time>/records.jsonl under the output directory. The first line is a header; each further line is one request. The example below is synthetic and shortened, not a measurement.

{"type": "header", "status": "ok", "schema": "knlp.rpl2.mounted-fs.v1",
 "source": {"repository": "knlp", "commit": "<sha>", "modified": false},
 "filesystem": {"type": "nfs4", "nfs_version": "4.2"},
 "io_mode_requested": "direct", "io_mode_actual": "direct",
 "object_bytes": 8388608, "objects": 16, "requests": 64, "seed": 1,
 "cache_state": "uncontrolled", ...}
{"type": "request", "request": 0, "key": "obj-000000", "generation": 1,
 "bytes_read": 8388608, "io_mode": "direct", "start_ns": 1000,
 "end_ns": 2001000, "latency_ns": 2000000, "validation": "match", ...}
Record fields
FieldMeaning
statusok, or skipped with a reason when direct I/O was requested but refused. A skipped run has no request records.
io_mode_actualThe mode the reads used. A direct request never falls back to buffered reads silently.
latency_nsMonotonic time from just before the open to just after the close: one whole request.
validationmatch when all bytes equal the manifest digest; mismatch, short_read or error otherwise.
generationThe object's version in the manifest. Objects are written once, so it is always 1.

The report writes summary.json next to the records. It counts each validation outcome and gives the median, 90th and 99th percentile and maximum latency of verified requests, plus the median request rate in MiB/s. Percentiles use the nearest-rank method on complete requests. A failed request is never counted as a fast one, and the report exits with an error when any request failed. With 64 requests the 99th percentile is close to the maximum, so raise the request count before reading much into it.

8. Troubleshooting

Common messages
MessageCause and fix
no target directory givenPass RPL2_TARGET=/path and RPL2_OUTPUT=/path, or set them with make menuconfig.
is inside the source treeResults and objects stay out of the repository. Choose directories elsewhere.
FAIL free spaceThe target needs the object bytes plus 10%. Reduce the size or count, or choose another directory.
SKIP direct I/OThe filesystem refused an aligned O_DIRECT read. Some FUSE filesystems do this. Choose the buffered mode in make menuconfig if a buffered measurement is what you want.
refusing to reuse or overwrite itAn object directory exists with a different seed, size or count, or without a manifest. Remove it yourself, or change the seed.
missing or wrong sizeAn object file was removed or truncated after it was written. Remove the object directory and run again.
did not return the expected bytesAt least one request read a mismatched or short object. Look at its record, then check the storage before trusting any timing.
Conflicting rpl2 workloadsThe configuration also enables another reproduction. Load the rpl2 defconfig again.

Very low buffered latencies usually mean the page cache served the reads. Very high first requests usually reflect the first open or read of each object. Both are kept in the records rather than filtered out.
