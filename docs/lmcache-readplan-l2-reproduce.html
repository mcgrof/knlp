ReadPlan L2 / Reproduce

Basic reproduction

Run the basic read baseline

Two defconfigs give a starting point that anyone can run. The smoke profile tests the tools on any Linux machine. The mounted profile times whole-object reads on a filesystem you supply and checks every byte. Neither one needs root, and neither changes your system.

1. Prerequisites

You need Linux, GNU make, Python 3.10 or newer and a checkout of knlp. The tools use only the Python standard library. The defconfig step uses the kconfiglib package when it is installed; without it the defconfig is copied as it is, which is enough for these profiles. Git is optional: when present, each record names the source commit.

The mounted profile also needs two directories that you create, both outside the source tree. The target directory holds the test objects; the output directory receives the records. The default object set is sixteen 8 MiB objects, 128 MiB in all.

2. Run the CPU-only smoke tests

make defconfig-rpl2-smoke
make

Plain make runs rpl2-doctor, which checks the Python version, then rpl2-smoke, which runs the unit tests in tools/reproduce/rpl2/tests. They exercise the record schema, the immutable object set, corrupt and truncated objects, and the skip that replaces a direct-I/O run when the filesystem refuses O_DIRECT. They write only to temporary local directories and finish in well under a second. A passing run ends with OK; the direct-I/O test reports itself as skipped on a temporary filesystem without O_DIRECT.

3. Measure reads on a mounted filesystem

make defconfig-rpl2-mounted-fs
make RPL2_TARGET=/mnt/share/rpl2 RPL2_OUTPUT=$HOME/rpl2-records

The two variables name the target and output directories. You can also store them in the configuration with make menuconfig, where the same menu chooses the I/O mode, object size, object count, request count and seed. Plain make runs three steps, which you can also run one at a time:

make rpl2-doctor RPL2_TARGET=/mnt/share/rpl2 RPL2_OUTPUT=$HOME/rpl2-records
make rpl2-run    RPL2_TARGET=/mnt/share/rpl2 RPL2_OUTPUT=$HOME/rpl2-records
make rpl2-report RPL2_OUTPUT=$HOME/rpl2-records

rpl2-doctor prints one line per check: the filesystem type, whether the target is writable, whether it has room for the objects plus 10%, whether the object size suits the chosen I/O mode, and whether an aligned O_DIRECT read works there. It stops with an error when a required check fails.

rpl2-run writes the objects once from the seed, syncs them, makes them read-only and lists their SHA-256 digests in a manifest. A later run with the same seed, size and count reuses them; a mismatched or unrecognized directory is refused, never overwritten. Each request then opens one object, reads all of it and closes it. Requests visit the objects in order and wrap around, and every request is recorded, including the first read of each object. The digest check runs after the timed region. rpl2-report validates the newest records and writes a summary; RPL2_RECORDS=/path/records.jsonl selects an older run.

The default I/O mode is O_DIRECT into a page-aligned buffer, which bypasses the client page cache where the filesystem honors it. The buffered mode is useful as a contrast, but its reads may come from memory, particularly right after the objects are written. The tools never drop caches, so the records describe cache state as uncontrolled.

4. Use an NFS or pNFS mount

The tools do not mount anything. Mount the export yourself, following the nfs(5) manual page and your server's documentation, then point RPL2_TARGET at a directory you own on that mount. The doctor reports the filesystem type and the NFS protocol version; it deliberately omits the server name and address.

A Linux client uses pNFS only with NFS version 4.1 or later and only when the server offers layouts for the file. The basic tools do not check whether a read used a layout or which server returned the bytes. Treat a result as an NFS result unless you have separate evidence of the path. Large differences between reruns usually mean the client, server or network is also doing other work, so note what else was running.

5. Read the records and summary

Each run creates rpl2-<UTC time>/records.jsonl under the output directory. The first line is a header; each further line is one request. The example below is synthetic and shortened, not a measurement.

{"type": "header", "status": "ok", "schema": "knlp.rpl2.mounted-fs.v1",
 "source": {"repository": "knlp", "commit": "<sha>", "modified": false},
 "filesystem": {"type": "nfs4", "nfs_version": "4.2"},
 "io_mode_requested": "direct", "io_mode_actual": "direct",
 "object_bytes": 8388608, "objects": 16, "requests": 64, "seed": 1,
 "cache_state": "uncontrolled", ...}
{"type": "request", "request": 0, "key": "obj-000000", "generation": 1,
 "bytes_read": 8388608, "io_mode": "direct", "start_ns": 1000,
 "end_ns": 2001000, "latency_ns": 2000000, "validation": "match", ...}
Record fields
FieldMeaning
statusok, or skipped with a reason when direct I/O was requested but refused. A skipped run has no request records.
io_mode_actualThe mode the reads used. A direct request never falls back to buffered reads silently.
latency_nsMonotonic time from just before the open to just after the close: one whole request.
validationmatch when all bytes equal the manifest digest; mismatch, short_read or error otherwise.
generationThe object's version in the manifest. Objects are written once, so it is always 1.

The report writes summary.json next to the records. It counts each validation outcome and gives the median, 90th and 99th percentile and maximum latency of verified requests, plus the median request rate in MiB/s. Percentiles use the nearest-rank method on complete requests. A failed request is never counted as a fast one, and the report exits with an error when any request failed. With 64 requests the 99th percentile is close to the maximum, so raise the request count before reading much into it.

6. Troubleshooting

Common messages
MessageCause and fix
no target directory givenPass RPL2_TARGET=/path and RPL2_OUTPUT=/path, or set them with make menuconfig.
is inside the source treeResults and objects stay out of the repository. Choose directories elsewhere.
FAIL free spaceThe target needs the object bytes plus 10%. Reduce the size or count, or choose another directory.
SKIP direct I/OThe filesystem refused an aligned O_DIRECT read. Some FUSE filesystems do this. Choose the buffered mode in make menuconfig if a buffered measurement is what you want.
refusing to reuse or overwrite itAn object directory exists with a different seed, size or count, or without a manifest. Remove it yourself, or change the seed.
missing or wrong sizeAn object file was removed or truncated after it was written. Remove the object directory and run again.
did not return the expected bytesAt least one request read a mismatched or short object. Look at its record, then check the storage before trusting any timing.
Conflicting rpl2 workloadsThe configuration also enables another reproduction. Load the rpl2 defconfig again.

Very low buffered latencies usually mean the page cache served the reads. Very high first requests usually reflect the first open or read of each object. Both are kept in the records rather than filtered out.
