Context reuse · checkpoint inference · October 2026

Reusable context,
typed by its consumer.

A learned key/value prefix, a document-vector collection, and a query’s soft memory tokens can share a storage contract. Each still needs its own model interface and cache identity.

This work extends the Learned Prefix Cache (LPC) architecture toward Memorilla’s latent memory. The shared catalog and LMCache host-artifact adapter now restore document collections for released Memorilla inference. Controlled replay separates storage correctness from numerical batch sensitivity. LPC keeps its own model attachment path.

Two suites in the mapped comparison516,096 exact input rowsNo training required

October 28 result: mapped embedding reuse raises CPU input-preparation throughput by 11.7–15.1% on PubMedQA and 2.10–2.28× on NarrativeQA versus the previous arena adapter. It also beats the unchanged author control in both suites. NarrativeQA remains 4–8% below the optimized native control. These are preparation gains, not measured decoder speedups. 01 / The shared contract

Separate storage from model execution.

A context artifact is a versioned tensor payload plus the information needed to use it correctly. Its immutable ID binds the payload digest, representation, producer, and compatible consumers. File location and working-copy residency can change while that semantic identity stays fixed.

Learned prefix

prefix_kv

Per-layer key and value tensors for a particular model. Preserve exact logical positions, layer/head geometry, rotary-position settings, dtype, layout, and padding.

Document collection

document_embeddings

Vectors produced by a pinned encoder and preprocessing pipeline. One collection contains a vector for each assigned text entry; different questions can reuse it. A compatible memory reader consumes these vectors. They do not enter the decoder’s key/value cache directly.

Soft memory tokens

input_embeddings

Vectors in the decoder’s input space. Bind their reader, collection, question, prompt placement, and positions. Prefill must still turn the assembled input into layer-specific key/value state.

The file registry implements import, resolve, load, working-copy eviction, and restore. It validates safetensors before synchronizing payload files and directories, then publishes metadata in a synchronous SQLite transaction. Missing, corrupt, or incompatible required artifacts fail explicitly. Existing cartridge connector APIs remain unchanged.

02 / Sharing prospects

Reuse the stable representation.

The useful sharing boundary depends on what produced the bytes. The following are architectural prospects; CPU file reuse does not establish physical GPU aliasing or an engine cache hit.

ArtifactPotential reuseIdentity that must stay bound
LPC key/value prefixMany requests to the same compatible decoder can attach one trained artifact. Avoid training or reconstructing it on a cache miss.Checkpoint bytes, model weights, positions, geometry, layout, and ordered composition with the request.
Memorilla document collectionDifferent questions can reuse the same query-independent collection. New or changed source material needs a new version.Source content, encoder revision, preprocessing, namespace, and compatible reader.
Memorilla readoutAn identical readout can be restored when its complete dependencies match. A shared collection alone is insufficient.Actual soft-token bytes, question/readout dependencies, reader checkpoint, decoder, template, and placement.
Derived decoder key/value statePotential reuse after exact prompt-embedding prefill. This bridge is not implemented here.All preceding inputs, their order, model identity, positions, and the derived payload.

An ID gives consumers a common object to resolve. It does not make vectors interchangeable across models, enforce access control, or make independently trained prefixes composable. Namespace is part of identity; an actual service still needs authorization. Multiple runtime users, resident-memory deduplication, and cache-key propagation require separate engine tests.

05 / Papers and interfaces

Memorilla and REFRAG shorten context differently.

Memorilla reads a query-independent document-vector collection with a learned, query-conditioned module. Its released Qwen configuration emits 16 input-space memory tokens for a frozen decoder. Reading the whole selected collection is part of that method; replacing it with top-k retrieval would change the algorithm.

REFRAG, from Meta and academic collaborators, encodes fixed token chunks, projects their vectors into decoder input space, and can expand selected chunks back to text. Its reconstruction stage freezes the decoder; later continual pretraining unfreezes it. Its mixed-input path therefore needs the corresponding trained decoder, encoder, projection, and policy.

QuestionMemorillaREFRAG
Reusable unitDocument embeddingsEncoded chunks
Query-time contextFixed-size learned memory readoutOrdered mixture of compressed chunks and expanded text
Decoder dependencyFrozen decoder paired with the trained readerDecoder aligned through the paper’s training recipe
Context budgetFixed memory-token countDepends on chunk count, compression, and expansion decisions

These are method differences, not a matched accuracy or speed comparison. The papers use different models, tasks, training, and controls. Neither paper’s headline performance is a measured result of this implementation.

06 / Engineering target

Make context durable, compatible, and reusable.

Our target is a common lifecycle for context representations: publish verified bytes, resolve an immutable handle, load the representation its consumer expects, and recover it after eviction or restart. Training remains a producer’s separate responsibility. A missing LPC must not launch training, and storage must not disguise document vectors as layer KV.

Preserve each control.

Establish the real LPC engine/checkpoint baseline and the unmodified Memorilla decoder path. Keep engine-version changes separate from artifact/storage changes.

Attach context through the right interface.

Use the existing LPC attachment for KV and exact template-aware input embeddings for Memorilla. Retain engine ownership of allocations and scheduling.

Qualify sharing and restore.

Test equal-length different payloads, different questions over one collection, native and external cache keys, and actual inference after GPU eviction and process restart. File parity is the prerequisite already explored.

Measure the complete cost.

Separate encoding, readout, serialization, storage completion, transfer, prefill, and decode. Compare matched tensors and cache states before making a storage or end-to-end speed claim.

A possible REFRAG adapter belongs at the chunk-collection and mixed-input boundaries, with its own typed metadata. Whether that adapter is worthwhile needs a separate compatibility and quality evaluation. It is not part of the CPU pass reported here.

09 / Reproducible comparisons

Control when requests enter the engine.

A V1 engine process can execute a request while its caller is still submitting the rest of the batch. That timing can change numerical execution batches and native prefix reuse, even when every prompt embedding is identical. Diagnosis verified 4,096 unchanged prompt deliveries. Complete-batch admission restored parity while retaining multiprocessing, weights and cache residency.

Port and LMCache controls now default to KNLP_MEM_SCHEDULING="inprocess", following vLLM’s offline guidance. The original-author profile preserves upstream runtime behavior. The memorilla-port-batch-replay and memorilla-lmcache-batch-replay presets instead retain multiprocessing: pause scheduling at level zero, enqueue the complete call, resume scheduling, then wait for completion. They require the corresponding public APIs and an idle, exclusive offline engine.

The recorded port uses Torch 2.9.1 with ROCm 6.4, Transformers 4.57.6 and a locally patched V1 engine derived from vLLM 0.18.1rc1. Catalog modules have their own source pin; their tests do not certify a complete fork-engine build.

Eight fresh 1,024-request runs qualify the repaired source without diagnostic admission hooks. The default-runtime native/adapter control has 51 string differences. All six repaired runs agree exactly in all 15 pairwise comparisons, including native versus adapter, repeat runs and in-process versus multiprocessing admission. Decoder prefix caching, asynchronous scheduling and chunked prefill remain enabled. This qualifies the recorded port runtime; it does not certify a stock engine build or every hardware/backend combination.

Different neighboring questions and document-collection padding can still change the reader or decoder’s floating-point results. The memorilla-port-reference and memorilla-lmcache-reference presets isolate one request at a time and disable decoder prefix caching. Document-collection residency and the real restore path remain active. These are numerical reference controls; their scores need not equal a batch-32 run.

Both single-request runs complete the same 384-request trace. Native and adapter predictions and all collated-input, reader-output and decoder-prompt tensor hashes match at every position. Repeated inputs have no tensor or string variants in either run. The adapter performs 384 collection loads with eviction after every request and no resident hits. These results qualify the reference on the recorded port runtime; they do not make batch-32 or cross-backend outputs equivalent.

11 / Prepared reads

Reuse validated metadata on repeated reads.

This section describes the October 26 arena implementation. The mapped follow-up also reuses tensor references; it does not rebuild a view and take a lease for every small collection.

The host adapter caches immutable file read plans, typed manifests and validated tensor layouts. Resident reads check the consumer and stored header, then create fresh views of the actual allocation. Each payload reload still compares the current catalog and hashes every loaded byte. The collator still receives its own tensor copy. The original mmap baseline and full-collection reader remain available.

Metadata caches default to 1,024 entries, separately from the payload arena. Entry budgets do not bound caller-held plans, active references, cloned tensors or the Linux page cache. A bounded capacity wait reuses the admitted plan while another lease releases memory; it does not repeat metadata parsing on every retry. Its deadline does not interrupt file operations already running. Catalog transactions close their SQLite connections after each operation.

12 / Mapped embedding reuse · October 28, 2026

Reuse the existing pages and tensor pointers.

The current path keeps document embeddings in file-backed mappings managed by the LMCache artifact SDK. A prepared reader binds the collection to its compatible consumer and retains a tensor view. Repeated uses return the same pointer. Python tensor and buffer references keep the mapping alive, so eviction can drop cache lookup ownership without invalidating a tensor already handed to the collator.

Mapped read
File-backed FP16 pagesLinux page cache supplies the selected collection
→
Reusable tensor referenceNo extra payload arena or per-use lease
→
Final BF16 reader batchCopy and cast valid rows; initialize padding

The author maps shard files and slices the selected collection, rather than reading the whole corpus for each question. The previous adapter added a buffered file-to-arena copy and a full checksum on each reload. Both corpora fit in the page cache during the new comparison, but NarrativeQA’s roughly 2.41 GiB of vectors do not fit in that adapter’s 64 MiB arena. Mapped reuse removes this duplicate payload buffer. It still supplies every vector in the selected collection to the unchanged reader.

PubMedQA needs a different fix. Its collections already stay resident in the arena; repeated payload hashing was negligible there. Binding identity and layout once, then reusing the existing tensor reference, reduces the fixed management and view-construction cost. The mapped path avoids explicit per-copy leases; allocator-owned buffers continue to require them because an allocator can recycle their addresses.

Verification and memory limits

Publication always checks the full payload before registering it. Normal serving explicitly selects published verification: trust those verified bytes and avoid another scan on each read. The inspected author loader does not perform our equivalent per-reload artifact checksum either. Strict on-map verification remains available and hashes each newly created mapping. Reusing an existing mapped view is not a new mapping. Identity, consumer compatibility, file extent and typed layout are still admitted before use.

Backing files and borrowed tensor values must stay unchanged. Published mode does not detect later payload corruption. The mapping uses private copy-on-write storage so tensor libraries can expose its buffer; consumers must not modify it. It reads existing file-backed pages without allocating another complete payload buffer. The final BF16 batch and bounded conversion scratch remain separate allocations.

The default 512 mapping entries bound cache lookup ownership. Prepared readers can retain up to 1,024 collection references outside that budget, and callers can retain their own tensors. Linux controls physical page residency. The old 64 MiB arena setting therefore does not bound this path’s total RAM. Process RSS includes the native oracle and different mappings; no total-host-memory win is certified.
