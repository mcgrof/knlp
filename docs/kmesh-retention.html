KMesh / Retention and early loading

Questions 16–20

What does retaining shared context buy?

Singleflight already coordinates one engine restoration. External retention supplies the missing read-once behavior. These five questions measure that gain, the cost of holding state, and the additional value of preparing it before arrival.

16. Does keeping data in LMCache stop repeat SSD reads?

Yes. We removed the repeated SSD reads and measured latency again. Section 15 prepares shared context in vLLM, but follow-up lookups can still reread that context from the SSD. Here we also keep a copy in LMCache, so those lookups find it in memory. Every measured group with retention reads the 48 MiB shared state from SSD exactly once, including preparation.

It is a follow-up test of the fix, but it asks a narrower question. Both sides here prepare early, with a 250 ms head start. Both must finish warming before the follow-ups arrive. We compare keeping LMCache's copy against discarding that copy after loading vLLM.

Host DRAM and DMA-BUF are different cache arrangements

External L1 means LMCache's in-memory cache outside vLLM. It is not the CPU's hardware L1 cache. Its memory can be host DRAM or a GPU buffer. The table tests retention off and on within each of these two paths:

PathWithout retentionWith retention
Host DRAMSSD data passes through temporary host-RAM buffers before loading vLLM's GPU cache.Keep the 48 MiB copy in host RAM. Later LMCache lookups hit DRAM.
GPU DMA-BUFSSD data enters a registered GPU buffer before copying into vLLM's GPU cache.Keep the 48 MiB copy in that GPU arena. Later LMCache lookups hit this separate GPU copy.

The retained host arm is NVMe-backed host-DRAM caching; DRAM is a useful retention tier, not just a transfer buffer. Both arms start with empty resident caches and fetch from NVMe during preparation. A separate DRAM-only offload baseline would start with the state already in host RAM. This is therefore not a pure DMA-BUF on/off comparison with identical memory placement. Keeping both paths in one table makes their different resource costs and results visible.

Two stopwatches: A's first token, and everyone's eighth token

For a four-request test, we submit A, B, C and D together. Each uses the shared context and generates its own eight-token output. For an eight-request test, there are requests A through H. The two timing columns answer different questions:

  1. How long does A wait for its first token? Start when A is submitted. Stop at A's first output token. This follows A, the first request submitted, even if B produces a token sooner.
  2. How long until every request has generated 8 tokens? Start when we begin submitting the group. Stop when the last request finishes its eighth token. If D finishes last, the timer waits for D. It does not add the four requests' individual times.

For four follow-ups, the unretained path reads 240 MiB: 48 MiB for the warm request plus 48 MiB for each follow-up. Retention cuts this to one 48 MiB read for the entire group. Every follow-up reuses the already-loaded vLLM state; none needs another external load into vLLM.

The saving costs 48 MiB of additional occupied LMCache memory: host RAM in the staged path, GPU memory in the DMA-BUF path. The direct path therefore retains a second copy outside the one shared inside vLLM. Both controls configure a 512 MiB external arena and a 512 MiB engine KV pool; used external-cache bytes increase from zero to 48 MiB. This test applies no competing memory pressure.

Section 20 answers the next question. Once both approaches read the context only once, does loading early still help? Yes, in the controlled 100 ms head-start test: A's first-token wait and the time until every request has eight tokens both fall. The test verifies equal SSD bytes instead of assuming a cache setting prevents duplicate reads.

Where would RAID flash fit?

A striped SSD array is a future backing-store test. It could prepare a large context sooner or serve more cold groups at once. In this retained 250 ms control, the context is already ready and the follow-ups trigger no SSD reads. Faster flash therefore cannot remove a remaining SSD wait from their measured interval; it would need a shorter head-start or cold-demand experiment to show that benefit.

Keep three experimental choices separate: where data starts (resident DRAM, one NVMe device or striped NVMe devices), how it reaches the engine (host staging or a qualified GPU DMA-BUF path), and when preparation starts (on demand or early). A DRAM-resident baseline remains valuable alongside the flash paths.

A software RAID test does not need a hardware RAID card or HBA. Linux can stripe reads across two NVMe devices in software. Ordinary reads into host RAM do not require GPU DMA-BUF support. Sending those reads directly into a GPU buffer is the separate question: the selected RAID stack, each drive's mapping and the PCIe route must support this experimental path. A working single-drive DMA-BUF test does not prove that RAID works too.

Two-drive RAID 0 is a useful optional test of read parallelism for reconstructible cache data; it provides no drive-failure redundancy. First check the topology and existing support. If qualifying the direct path needs new RAID or driver code, defer that work to a suitably equipped storage lab. The single-drive prefetch comparison in section 20 already demonstrates a benefit without RAID.

How to project RAID's useful head start before testing it

An initial model is preparation time ≈ fixed work + bytes / effective bandwidth. The preparation wait remaining at arrival is approximately max(0, preparation time − available head start). This is a projection, not a measured request-latency model.

GB/s is decimal; MiB is binary. These illustrative rates are not RAID measurements or promises for a particular drive count. Measure aggregate delivery on the actual route, including PCIe limits, concurrency, chunk distribution and destination bandwidth. Fixed coordination, copying and warm-request model work still have to be paid. If fixed work exceeds the available head start, adding SSDs cannot make preparation finish in time.

Linux's striped-target documentation describes parallel use of multiple devices. The experimental DMA-BUF route also needs qualification through the selected RAID stack and each member's device mapping; single-device success does not establish that combination. See the kernel's P2PDMA topology and DMA-BUF mapping requirements.

17. Can the traces qualify family retention?

A family lease would protect vLLM's existing shared ancestor blocks between related requests. It would consume cache capacity that could serve other requests. The comparison must therefore count saved restoration or recomputation against displaced useful hits and unused holds. The external-L1 result above does not answer that engine-memory question.

The October 18 CPU audit of the public LMCache agent-trace corpus at its pinned revision finds 78 JSONL files, 1,915 unique parseable records, two exact duplicate records and 20 malformed nonempty lines. The malformed lines are in the MemGPT file. The Claude Code directory has capture tooling but no captured JSONL records. The source README labels PyCodeAGI as a synthetic pipeline.

None of the valid records supplies explicit parent links, invocation start and completion times, engine identity or physical cache events. There are zero observed invocation-lineage edges. Text-prefix overlap and spacing between record timestamps cannot establish fork gaps, simultaneous inference or eviction pressure. This audit therefore requires invocation capture before a trace-backed pressure comparison; it predicts no latency gain. The complete derived audit contains field coverage, counts and input hashes, without prompts or answers.

18. Does holding the ancestor pay under pressure?

The hold works, but it reduces total cached-token reuse in this controlled stress case. A bounded controller adds family references to vLLM's existing full ancestor blocks after the parent completes and before its request references are freed. It creates no second ancestor. The child later aliases those same physical blocks. Keeping them out of the eviction queue leaves less capacity for unrelated requests.

Measured on October 18, 2026, with Qwen2.5-0.5B-Instruct on a CUDA GPU, the experiment uses one synchronous eager engine, batch-invariant arithmetic, 16-token blocks and eight greedy output tokens per request. The pool has 129 physical blocks including one reserved null block. A 512-token ancestor occupies 32 blocks, or 25% of usable capacity. After the parent, the engine serves two passes over four unrelated 497-token prompts, then a child extending the parent's exact input and generated output with a 64-token tail. Each competing request needs 32 blocks with its continuation, so their working set fills the stock pool. This request order deliberately exposes capacity competition; it is not reconstructed from the public corpus.

19. Does model-driven branching leave room for better retention?

Stock vLLM reaches the ideal exact-prefix cache ceiling in this unsuccessful local-model search. This capture lets a model generate arithmetic proposals, score candidate states and choose which states to extend. Later requests follow those choices. It answers whether stock prefix caching leaves exact-prefix reuse available to an ideal retention policy in this observed search, at the same physical cache capacity.

The workload uses the official Tree of Thoughts Game of 24 search at revision 8050e67d0e3a, with its original prompts, value memoization and dataset. We replace its model provider with Qwen2.5-7B-Instruct and take puzzles 0, 1 and 2 in file order. This bounded adaptation keeps two states, evaluates each once and allows 192 output tokens per call. It uses one synchronous eager vLLM engine, BF16, a 2,048-token context, 16-token cache blocks, temperature 0.7 and seed 123 plus the call index. All task outcomes count; this is not the paper's model or accuracy setup.

Search quality fails in this profile: zero of three puzzles produce a valid selected solution. Fifteen of the eighteen selections after the first step extend an earlier state only with whitespace. The upstream parser treats proposal lines, including blanks, as candidates; cached value scores can preserve these unchanged states. All 21 proposal replies and 81 of 152 value replies terminate at the 192-token cap. The verbose output, format mismatch and truncation are not separated by this run. It validates capture and cache accounting on those calls, but does not qualify a successful reasoning baseline or measure the model's general puzzle-solving ability. A separately declared profile that follows the search protocol is needed before drawing conclusions about useful reasoning workloads.

20. Does loading shared context early actually help?

Why does this build on the earlier singleflight tests?

Singleflight was already enabled. External retention was the missing piece in the storage path. Singleflight lets related requests share one restored ancestor inside vLLM. In the earlier preloading tests, LMCache could still read that ancestor from SSD again when later lookups arrived. Keeping its external copy turns those lookups into memory hits.

This extends cascade's shared-prefix principle through offloading: the shared ancestor and private branches also guide restoration, external residency and advance preparation. The connection to cascade explains how these layers fit together. The combined performance benefit of cascade attention and these storage controls remains unmeasured.

Yes. This is a clear benefit for early loading in the tested workload. Given 100 ms of advance notice, the first submitted request waits about half as long for its first output token. The whole group finishes its short, eight-token outputs about 9–13% sooner after arrival. Both host staging and DMA-BUF benefit. This comparison does not establish that DMA-BUF is faster than host staging.

What are we comparing?

Imagine four requests, A, B, C and D, that all need the same saved context. The context is 48 MiB of cached model state on an SSD. Each request adds its own input and asks the model to generate eight output tokens. A token is a piece of text, sometimes part of a word; eight tokens need not form a complete answer. We also test groups of eight requests.

  • Load on arrival: wait for the requests, then load their shared context once and let them reuse it.
  • Load early: begin preparing that same context 100 ms before the requests are due. Load it into vLLM and run a small, one-token warm-up request, so the follow-ups arrive with their shared state ready.

Both approaches already read the SSD data only once. The benefit comes from doing preparation before the requests arrive. It is not a saving from eliminating extra SSD reads in only one side of the comparison. This is the comparison that sections 15 and 16 left open.

The 100 ms is advance notice, not free work

The test tells the system when the requests will arrive. It starts early preparation 100 ms before that time. It does not postpone the requests until preparation finishes: any delay in submitting them still counts against the measured wait. The preparation includes loading, copying into vLLM and one real warm-up token. This measures the complete preparation method, not just SSD transfer speed.

An application needs an opportunity to do that work early. For example, it might know which context a follow-up will need while waiting for a tool. This benchmark supplies that knowledge; it does not demonstrate an application predicting it. Delaying useful requests to create a 100 ms gap would have to count as extra waiting.

The pilot tried 0, 25, 100 and 250 ms of notice. At 25 ms, preparation was not ready in any of its ten groups on either path. At 100 ms it was ready in all ten, so 100 ms was selected for the larger test. This is the shortest successful tested lead, not a measured minimum or the SSD's loading time. All 800 measured early-loading groups in the larger test were ready by arrival.

The tables count waiting after the scheduled arrival. The benchmark also records an earlier, fixed 250 ms interval before arrival. For the four-request DMA-BUF example, counting from that earlier start gives 367.89 ms versus 354.06 ms: the same roughly 13.84 ms saved, but about 3.8% of the longer interval. Neither percentage is a prediction for an entire real application workflow.

Why can early SSD loading look faster than data already in DRAM?

“Already in DRAM” means the saved state is in LMCache's CPU memory. It still has to be restored into vLLM's GPU cache after the requests arrive. Early loading from SSD has already done that restoration and the warm-up before arrival. These controls differ in how much work remains; they do not show that SSD is faster than RAM.

The “engine already resident” control starts with the state in vLLM's cache. It is the closer comparison for a fully prepared request. In the small four-request pilot, early loading and that control give similar first-token waits. The placement table below keeps the actual DRAM and GPU memory controls visible.

What this result establishes

KMesh can use advance notice to reduce waiting even after duplicate reads have been removed. The next question is how often a real application can supply useful notice, and whether the benefit survives competition for storage and GPU memory. A wrong hint still spends I/O, memory and model work without helping a follow-up.

The evidence here covers one small model, a 48 MiB shared context, four or eight requests, and eight-token outputs, with no competing families or memory pressure. It supports early preparation in that setting. It does not establish a production prediction policy, a general DMA-BUF latency advantage, or a combined speedup with Cascade attention.

Pilot results: choosing the head start and comparing memory locations

Why the lead is 100 ms

The preceding pilot uses two fresh engine blocks per path, three warmups and five measured groups per control/block. Exact setup, correctness checks and reproduction commands

The October 21, 2026 experiment uses one RTX 4090, Qwen2.5-0.5B-Instruct at revision 7ae557604adf67be50417f59c2c2f167def9a775, BF16, batch-invariant synchronous eager serving with two OpenMP/MKL threads. Each request shares the same 4,096 input tokens, adds 512 input tokens of its own and generates eight output tokens with greedy decoding. vLLM prefix caching supplies physical sharing. The KMesh connector coordinates one restoration; cascade attention remains a separate optimization.

Both arms retain the external copy and join overlapping fills. Demand starts at arrival and issues no extra warm request. Early loading starts 100 ms before arrival and uses a one-token engine warm request. That preparation token is charged separately. This tests the whole preparation path, including that warm request, rather than isolating raw DMA-BUF transfer time. Arrival is fixed 250 ms after the trace origin; slow preparation cannot move it. Every actual submission delay remains in the headline waits. An accepted warm request drains normally. If completion is observed after children are due, an unsubmitted warm is skipped.

Correctness and scope

Across qualification, pilot and confirmation, 12,320 child continuations and 1,080 warm continuations pass exact-token checks, with zero delta in 99,640 chosen-logprob comparisons. All 12,320 children first expose exactly one token before their eighth-token observation. Diagnostic warmups verify restored model-KV digests and one ready, physically shared 256-block ancestor. Both paths reject deliberate corruption. Resident references show zero trial storage reads, and every cold control shows the same 48 MiB payload work. An unused hint still pays for sixteen reads, retained occupancy and one warm token without serving a child. Ownership drains before objects are cleared. Backend payload operations are not physical NVMe command traces. Direct I/O bypasses the OS page cache; it does not prove cold flash or an empty SSD cache.

The DMA-BUF route transfers NVMe bytes into an external GPU arena, then copies/scatters them into vLLM. The host path uses registered host staging. This is an exact-prefix test without memory pressure, competing families or application-quality evaluation. It assumes advance knowledge of arrival. It does not qualify a forecasting policy, a general memory manager or a combined cascade/DMA-BUF speedup. The earlier unsuccessful reasoning capture and the historical multiprocess/shifted-restore work remain separate.
