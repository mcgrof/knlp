Asymmetric KV: methods and results

The supported result is an 8K/batch-32 Qwen3-8B in-process throughput improvement with FP16 keys and FP8 values. It holds for the two tested weight formats under their matched controls. A separate dense 1K/batch-32 in-process test does not meet the confirmed gain criteria. Actual AWQ HTTP quality fails its preservation gate. This page preserves these outcomes and the conditions behind quality, memory and throughput claims.

The separate dense 1K and 8K HTTP studies report client-visible latency, throughput, failures and model qualification.

Precision/scaling reference

The completed two-model reference compares native K16/V16 with K16/V8 (A), K8/V16 (R) and K8/V8 (S), each with fixed (F) and token/head (D) scales. Complete results and aggregate data separate reference quality, physical backing and actual-worker support.

Qwen/Qwen3-8B revision b968826d9c46dd6066d109eabc6255188de91218 uses FP16 weights and compute. Qwen/Qwen2.5-7B-Instruct revision a09a35458c702b33eeacc393d103063234e8bc28 uses BF16. Queries remain native in every arm. Compressed components persist as E4M3FN codes and FP32 scales; each layer temporarily reconstructs native attention operands. No stored codes are requantized. Fixed scales use native cache-write operands after normalization/RoPE, over 32 independent documents at 1K and 8K, including 128 decode steps. Scale construction clamps the FP32 absolute maximum at 1e-12, multiplies by the rounded FP32 reciprocal of 448, divides operands in FP32, clips to ±448 and rounds E4M3FN to nearest/even. Dynamic scaling applies this rule per fresh token/head vector.

Calibration, development and confirmation documents are disjoint. Confirmation uses 64 paired documents at each context with 128 scored targets each, 200 retrieval instances per context and all 1,319 GSM8K test items. GSM8K is an exposed standard benchmark. The original last-numeric-answer-label parser, 2,048-token cap and truncation semantics are retained. Correct labeled answers at the cap count; errors, missing parses and truncations remain in the records.

Two certificate families each allocate alpha .025 across all 12 model/recipe combinations (.025/12 per certificate). Every certificate requires native math accuracy at least 50%, retrieval gross-loss upper bounds ≤5% at both lengths and relative mean NLL upper bounds ≤1% at both lengths. Preservation adds a math gross-loss upper bound ≤2%. Aggregate math instead requires the paired net accuracy lower bound ≥−1 percentage point. Gross bounds are exact binomial; net bounds invert Tango's matched-pair score with approximate coverage. For binary endpoints, gross loss is the number of native-correct to candidate-wrong transitions divided by all paired questions. Net change uses gains minus losses over that same denominator. NLL uses 100,000 paired document-bootstrap draws, seed 20261020, linear quantiles. No certificate slot was removed or margin changed after results.

Direct A−R and A−S comparisons use eight contrasts across models and scale policies within each of five endpoint families. Exact McNemar tests cover binary endpoints; centered paired bootstrap tests cover document NLL. Holm adjustment is per named endpoint. Descriptive paired 95% intervals differ from certificate bounds. A nonsignificant difference does not establish equivalence, and failure to certify does not automatically prove degradation.

The measured reference source is 782a4c5cd69b575b4736c14285477e306e176421. One redundant row-integrity comparison between a saved GPU FP32 mean and a CPU FP64 reduction exceeded an absolute 1e-6 check by 5.47e-8. The documented reader correction uses the FP32 summation rounding bound gamma_n = n·u/(1−n·u), n=128 and u=2^-24, while requiring finite nonnegative exact-FP32 losses and mean. All 1,792 NLL rows pass. Saved means, samples, statistical calculations, seeds and gates are unchanged; no GPU sample was rerun.

Physical backing includes FP32 scales and unique shared storage once. A/R backing and allocation-size multisets match within each policy. CUDA allocation rounding, temporary layer reconstruction and process peaks remain separate. Reference execution time cannot rank fused serving kernels.

AWQ HTTP quality

The actual AWQ HTTP worker does not establish quality preservation. It scored 1,195/1,319 strict GSM8K answers correct, versus 1,198 for native FlashInfer and 1,202 for native FA3. The candidate lost 20 and gained 17 answers against FlashInfer, and lost 22 and gained 15 against FA3. One-sided exact 95% loss-probability upper bounds are 2.196% and 2.373%, above the frozen 2% limit. The denominator is all 1,319 paired questions; this is not a bound on net accuracy change. Both paired net-change confidence intervals include zero.

This separate test uses the same Qwen3-8B AWQ revision, packed INT4 weights, FP16 compute, original calibrated scales and a 48 GiB KV pool on H100 80 GB. HTTP quality concurrency is 32, which is not a fixed GPU batch size. NLL and retrieval preservation pass at 8K context, and all three arms match serial in-process outputs for 32 prompts in both reference orders. Full GSM8K uses natural question lengths and natural completion. Earlier batched quality was not substituted for actual HTTP quality.

What “quality passes” means

Negative log likelihood (NLL) measures prediction loss. Each study uses 32 independent document windows and 128 scored cached-decode targets per window. The one-sided 95% upper bound on candidate-minus-control NLL must not exceed ln(1.01) = 0.009950330853168092. The document is the resampling unit. Retrieval uses 100 frozen cases and requires at least 80% native accuracy. GSM8K uses all 1,319 test questions and requires at least 50% native accuracy.

A gross loss is a case the control answers correctly and the candidate answers incorrectly. One-sided exact 95% gross-loss upper bounds must be at most 5% for retrieval and 2% for GSM8K. Gains on other questions do not cancel losses. Errors, truncations and strict parser failures stay in the denominator. The fixed chat adaptation disables thinking and uses the retained answer parser; these are not unmodified leaderboard scores.

Memory and compatibility

FP16 K plus FP16 V requires four bytes per key/value element pair. FP16 K plus E4M3 FP8 V requires three: 25% less persistent payload at equal token slots. With the same byte pool, that is one third more slots. Dense 40 GiB pool measurements have 291,264 native and 388,352 asymmetric token slots per layer, with 42,948,624,384 actual backing bytes in each arm after page rounding. Backing allocations are deduplicated by device and storage pointer.

The serving workspace includes 256 MiB of K/V staging, 32 MiB of direct float scratch and 16 KiB of indices. FlashInfer wrapper buffers add further storage: the retained workspace inventory totals 296.140625 MiB of unique constant GPU storage and 8 MiB of pinned host memory. Per-plan metadata, allocator overhead, graph pools, weights and other runtime allocations are additional. The dense clean observation records 69,533,171,712 bytes of peak reserved Torch memory and 70,341,623,808 bytes of sampled driver usage. Instrumentation's temporary oracle workspace is excluded from that window. See the downloadable dense data for per-allocation receipts.

This is not a 25% total-HBM saving. No new maximum resident batch, capacity sweep or service-latency endpoint was measured. Historical 44/58/59 batch endpoints belong to their original implementations.

The supported geometry is Q32/KV8/D128, NHD layout, page16, FP16 compute, SM90 and one worker/stream. Automatic prefix caching, chunked prefill, sliding windows, attention sinks and soft caps are disabled. Each compact prefill prompt must be whole and fresh, at most 8,192 tokens, with at most 4,096 gathered page occurrences across the eligible suffix. Unsupported calls retain serving fallback; the installation qualification fails if its eligible mixed prompts fall back. The wrapper rejects recipe drift before loading a model. It does not claim that the underlying serving fork rejects every possible unsupported configuration.
