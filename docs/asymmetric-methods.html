Asymmetric KV: methods and results

The supported result is an 8K/batch-32 Qwen3-8B serving improvement with FP16 keys and FP8 values. It holds for the two tested weight formats under their matched controls. A separate dense 1K test does not meet the confirmed gain criteria. This page preserves both outcomes and the conditions behind quality, memory and throughput claims.

What “quality passes” means

Negative log likelihood (NLL) measures prediction loss. Each study uses 32 independent document windows and 128 scored cached-decode targets per window. The one-sided 95% upper bound on candidate-minus-control NLL must not exceed ln(1.01) = 0.009950330853168092. The document is the resampling unit. Retrieval uses 100 frozen cases and requires at least 80% native accuracy. GSM8K uses all 1,319 test questions and requires at least 50% native accuracy.

A gross loss is a case the control answers correctly and the candidate answers incorrectly. One-sided exact 95% gross-loss upper bounds must be at most 5% for retrieval and 2% for GSM8K. Gains on other questions do not cancel losses. Errors, truncations and strict parser failures stay in the denominator. The fixed chat adaptation disables thinking and uses the retained answer parser; these are not unmodified leaderboard scores.

Memory and compatibility

FP16 K plus FP16 V requires four bytes per key/value element pair. FP16 K plus E4M3 FP8 V requires three: 25% less persistent payload at equal token slots. With the same byte pool, that is one third more slots. Dense 40 GiB pool measurements have 291,264 native and 388,352 asymmetric token slots per layer, with 42,948,624,384 actual backing bytes in each arm after page rounding. Backing allocations are deduplicated by device and storage pointer.

The serving workspace includes 256 MiB of K/V staging, 32 MiB of direct float scratch and 16 KiB of indices. FlashInfer wrapper buffers add further storage: the retained workspace inventory totals 296.140625 MiB of unique constant GPU storage and 8 MiB of pinned host memory. Per-plan metadata, allocator overhead, graph pools, weights and other runtime allocations are additional. The dense clean observation records 69,533,171,712 bytes of peak reserved Torch memory and 70,341,623,808 bytes of sampled driver usage. Instrumentation's temporary oracle workspace is excluded from that window. See the downloadable dense data for per-allocation receipts.

This is not a 25% total-HBM saving. No new maximum resident batch, capacity sweep or service-latency endpoint was measured. Historical 44/58/59 batch endpoints belong to their original implementations.

The supported geometry is Q32/KV8/D128, NHD layout, page16, FP16 compute, SM90 and one worker/stream. Automatic prefix caching, chunked prefill, sliding windows, attention sinks and soft caps are disabled. Each compact prefill prompt must be whole and fresh, at most 8,192 tokens, with at most 4,096 gathered page occurrences across the eligible suffix. Unsupported calls retain serving fallback; the installation qualification fails if its eligible mixed prompts fall back. The wrapper rejects recipe drift before loading a model. It does not claim that the underlying serving fork rejects every possible unsupported configuration.

Timing-audit limit: the original strict reader fails. The frozen runner turns off device observations while retaining host completion observations; per-step worker CUDA events are empty. Original and restored reports match. The separately serialized start/end boundary timestamps were not saved. This supports the scoped host-endpoint analysis above, not a full original-protocol pass or per-step CUDA-duration claim. All failures remain in the retained record.

To run the full original workloads, use the named harness checkout, the native/compact/current source selection and the stage commands, with batch 32, length 8192 and the 48/40 GiB pools above. Freeze the adapted protocol and task hashes before quality scoring. Use the published ten-block arm orders from each data file for the 8K confirmation; do not use the older seven-block batch 8 recipe. Derive timing qualification from the actual complete production, NLL, retrieval and full GSM8K evidence, never from a fabricated success file.

A fresh execution is a replication: timing need not match the old values. Generating new prompts, new scales, changing compute/backend/capture policy, or combining an unqualified source pair requires the affected quality gates again. Installation checks alone cannot qualify such a change.
