What actually moves the loss
on a 35M-parameter decoder

The Stanford CS312 "Deep Learning Alchemy" assignments run as a reproducible knlp lane on the course decoder. This page reports what the sweeps found, in four parts: which hyperparameters matter alone, which ones must be tuned together, how the learning-rate schedule changes the answer, and how far the KV cache can be quantized before training notices.

Three headline results: the learning rate dominates every single-axis sweep and the default is already near its optimum; learning rate and warmup co-vary so strongly that raising both beats the default recipe; and query-key normalization is the single strongest defense against KV-cache quantization. The lane's design and reproduction steps are in the CS312 tutorial document.

The setup

The course decoder, d8, is a small Llama-style model: 8 blocks, hidden size 512, 8 heads of dimension 64, rotary positions, RMSNorm, query-key normalization and a SwiGLU MLP, about 35M parameters. The course recipe trains it on 600,000 sequences of 1,024 tokens with AdamW, peak learning rate 0.003, 1% linear warmup, batch size 64, weight decay 0.1 and gradient clipping at 1.0. One run takes roughly ten to fifteen minutes on one H100.

Its baseline validation loss is 2.9258 on 1,000 held-out sequences, against the course handout's quoted 2.926. Repeating that exact recipe at three paired model and data seeds gives 2.9258, 2.9284 and 2.9338: mean 2.9293 and a sample standard deviation of 0.0040. Two sigma is 0.008, so any difference below that is not distinguishable from seed noise. Every claim on this page is read against that floor.

Part 2: which knobs must move together

A single-axis sweep cannot say whether two knobs compensate for each other. This part fills the 2×2 corners around the baseline for every pair. A pair is called co-varying when moving both knobs recovers most of what moving one alone cost, by more than the 0.008 floor.

The geometry: two slices through one surface

Each single-axis sweep is a straight cut through one loss surface over (log learning rate, log batch size). The left panel above is a cut at batch 64; the right panel is a cut at learning rate 0.003; they cross at the baseline. Near its optimum a smooth loss surface is an elliptical bowl, and asking whether two knobs co-vary is asking whether those ellipses are tilted relative to the axes — whether the mixed curvature is non-zero. If the ellipses are axis-aligned, the best learning rate is the same at every batch size and tuning one knob at a time finds the true optimum. If they are tilted, the floor of the valley runs diagonally, the best learning rate moves as the batch moves, and a one-at-a-time sweep stops short.

So the test is: follow the bottom of the bowl across batch sizes and see whether it moves. On log-log axes the slope of that valley floor is the scaling exponent p in lrbest ∝ batchp. The linear scaling rule is p = 1, the square-root rule is p = 0.5, and perfectly separable knobs give p = 0.

The measured valley is flat. Across batch 32, 64 and 128 — a fourfold change — the best learning rate stays at 0.003. Over that range the two knobs are close to separable at this token budget, which is the same conclusion the pair table reached from the corners alone: a larger learning rate does not rescue a larger batch.

This does not overturn the scaling rule in its own setting, because this sweep is compute matched. The usual linear and square-root results hold the step count fixed and grow the batch, so a larger batch buys more tokens and can afford a larger step. Here the token budget is fixed, so a larger batch buys nothing and only removes optimizer steps: batch 256 takes 2,344 steps where batch 64 takes 9,375. The batch axis is therefore confounded with step count, and the dominant cost of a large batch is the steps it gives up, which no learning rate can buy back.

Do we have enough data? For the shape, yes. For a number, no. The three bracketed minima are enough to say the valley does not climb the way a linear rule predicts: at batch 128 a linear rule would have put the optimum nearer 0.009, and 0.003 beats 0.009 there by 0.035, far above the floor. But the learning-rate grid steps by 3×, so each optimum is located only to within a factor of three. A square-root rule over batch 32 to 128 predicts a 2× shift, which is less than one grid step — this grid cannot see it. So the honest reading is p = 1 is disfavoured, while p = 0.5 and p = 0 cannot be told apart.

Three gaps would close it, for about eight runs and roughly 1.5 H100-hours: bracket batch 256 by running learning rates 0.001 and 0.00033 there; give batch 16 more than its single point by running 0.001 and 0.009; and refine the grid to √3 steps (0.0017 and 0.0052) at batch 32 and 128, which is the resolution needed to separate a square-root rule from a flat valley. A second seed at each minimum would also turn the depth of these bowls from one draw into an interval.

The practical list that falls out: retune warmup whenever the peak learning rate or the batch size moves; retune weight decay with batch size and partly with learning rate; warmup and weight decay can be tuned independently of each other.

One seed per pair cell. The floor comes from the three baseline seeds only, so cell-to-cell differences under 0.008 are not read as real.

Part 3: the learning-rate schedule

The third part of the assignment asks how the other knobs interact with the learning-rate scheduler. Start from the standard recipe, set the weight decay to 1.0 — ten times the default — then change only the schedule and its warmup and rank three cells. Then run that whole ranking again at three peak learning rates, 0.009, 0.003 and 0.001, to find out whether the ranking is a property of the schedule or of the rate it is driven at. Nine runs, all compute matched at the standard 600,000-sequence budget.

It did not: C won at every rate. But the test never actually happened. Loss is still falling at peak 0.001 for all three cells, so the best peak rate at this weight decay is somewhere below 0.001 and every rate tested is still on the high side of it. Settling it needs peaks of 0.0003 and below, which is three more runs per rate.

Follow-up: was it the schedule, or the weight decay?

Everything above runs at weight decay 1.0, ten times the standard recipe's 0.1. That is a confound. In AdamW the decay is decoupled, so each step shrinks the weights by lrt · wd: the product is the control, not either knob alone. Because the schedule fixes the mean learning rate — A averages 0.900 of its peak, B 0.800, C 0.500 — holding the peak is also what accumulates the most decay. Across these three cells "holds the peak longer" and "integrates more weight decay" are perfectly correlated, at 1.80×, 1.60× and 1.00× of linear's. Both explanations predict the same result everywhere, so the earlier runs could not separate them.

The separating test keeps the shapes identical and drops the weight decay to the default 0.1, which cuts the integrated decay tenfold while leaving every ratio untouched. Nine more runs.

Warmup-stable-decay was not losing on its shape; it was being charged for holding the peak under ten times the standard weight decay, which is precisely the regime its plateau is worst suited to.

This also repairs the explanation offered earlier on this page. The mean learning rate is not a separate mechanism from the weight decay — it is one half of the product that sets how far the weights actually move. Reading the two sweeps together, the optimal product is around mean lr × wd = 0.00015, which is what the standard recipe sits at. Every cell at weight decay 1.0 is 3× to 54× above it, so there the ranking simply tracks whichever cell carries the smallest product, and linear always does. At weight decay 0.1 the cells straddle that optimum instead, so the ranking turns over: linear is closest at the two higher peaks, and at peak 0.001 it has undershot while the plateau cells have not.

Why no schedule with a plateau wins at this batch size: the gradient noise scale

Both follow-ups leave one question open. Warmup-stable-decay holds the peak rate for most of the run and anneals at the end; linear decays throughout. Linear won every comparison. Is that a fact about this model, or about the setting it was run in?

There is a standard answer, and it is measurable. Write the expected change in loss from one step with learning rate e and batch B on a locally quadratic loss, with gradient G, Hessian H and per-example gradient covariance S:

dL  ~  - e |G|^2  +  (e^2 / 2) ( G' H G  +  tr(H S) / B )

The first penalty is curvature: step too far and you climb the valley wall, which limits you early while the gradient is large. The second is gradient noise, which controls you late, once the gradient has shrunk but the per-example variance has not. They are equal at the noise scale, B_noise = tr(S) / |G|^2 — the batch size at which the two barriers cost the same. Below it a run is noise limited; above it, curvature limited. Because the loss falls faster than the variance does, B_noise rises through training.

That gives schedules a crisp rule. The excess loss from noise goes as e/B, so holding a high rate is cheap exactly while the run is curvature limited and expensive once it is not. Call t* the step where B_noise passes the training batch size. A plateau is right up to t* and wrong after it, so the decay fraction a run actually wants is about 1 - t*/T.

At batch 64 the run is noise limited almost immediately. B_noise passes 64 by step 9, about 0.1% of training, so there is essentially no curvature-limited phase for a plateau to exploit. The rule then predicts an optimal decay fraction of 1.00: decay throughout, which is linear.

That prediction is testable, because the decay fraction is the one knob that defines the family and we had never swept it. It is also the knob that makes the two schedules one family: at fraction 1.0 the stable phase vanishes and wsd becomes linear, so "does WSD beat linear" is really "is the best decay fraction below 1.0?"

Closing it: the two checks

The map above has two soft spots. It was measured along a run trained with the linear schedule, which is circular if holding the peak changes the gradient statistics. And its central claim — that a plateau starts to pay somewhere above batch 384 — was an extrapolation, never run. Both are cheap to test.

Check 1: the map does not depend on the trajectory it was measured along. A second checkpointed run, identical except lr_schedule=wsd0.2, gives a noise scale that passes batch 64 just as immediately — 65.2 sequences by step 10 against the linear run's 65.7 — so the implied decay fraction is 1.00 on both. The differences that do appear run the right way and at the right time: through the plateau the warmup-stable-decay curve sits 1.2 to 1.6 times higher, because holding the peak keeps the model bouncing and tr(S) large, and then at steps 5,200 and 7,200 it falls to 0.54 times the linear curve, because by then linear has been annealing while the plateau has not. Holding the peak does raise the noise scale; it does not raise it anywhere near the factor of nine that would be needed to give a plateau a job at batch 64.

What stands and what does not. The regime claim is now tested at both ends: noise-limited at batch 64 where decaying throughout wins, curvature-limited enough at batch 512 for a plateau to win, with the crossover where the measurement put it. The precise threshold is not pinned — batch 384 and 256 were never run, so "somewhere between 256 and 512" is as sharp as this says — and every cell is one seed. All of it is at this model, this horizon and a 1,024-token context; the noise scale is a property of the loss surface being trained, so the numbers transfer no further than that.

Part 4: how far the KV cache can be quantized

The third exercise is precision. The attention keys and values that fill the KV cache are stored in low precision, and we measure how much validation loss rises. The lane sweeps three independent axes:

  • Bit width and format. 8-bit uses fp8 (e4m3). Four bits and below use a symmetric integer grid: int4 (15 levels), int3 (7 levels) and int2 (a ternary grid). Keys and values can be set independently, so an asymmetric split such as 16-bit keys with 4-bit values, or the reverse, is one setting.
  • Granularity. This determines which values share a quantization scale. per-token gives each token’s vector within each head its own scale. per-tensor shares one scale across the entire K tensor, and a separate scale across the entire V tensor, at an attention call. See the worked example below.
  • Query-key normalization. On or off. It normalizes the query and key vectors before their dot product.

Per-token versus per-tensor: which values share a scale?

A token has a key vector and a value vector for each attention head. Here, per-token means one scale per token, per head, separately for K and V; all components in that vector share it. Per-tensor means one scale for the whole K input to an attention call, and another for V, spanning the batch, heads, token positions and vector components. It does not mean one scale shared by every layer of the model.

Consider two key vectors in one head, shortened to three components for this example: token A = [0.12, 0.24, 0.70] and token B = [1.00, 2.00, 7.00]. These are illustrative values, not measured model outputs. Use this study’s symmetric 4-bit integer grid, with codes from −7 to +7 (15 levels).

The scale is the spacing between representable values: scale = max(abs(values sharing the scale)) / 7. Divide each value by the scale and round to get its integer code; multiply that code by the same scale to reconstruct the value used in attention.

Same 4-bit codes, different scale sharing. Reconstructed values include the rounding error.

For token A, per-token scaling uses its own maximum, 0.70, so the spacing is 0.10. With per-tensor scaling, token B’s 7.00 sets the spacing to 1.00 for both tokens: A’s 0.12 and 0.24 round to zero, and 0.70 rounds to 1.00. The largest absolute reconstruction error in A rises from 0.04 to 0.30 (Δ +0.26). This is error in the vector components, not validation loss.

The tradeoff: per-token scaling prevents a large value in another token or head from setting this vector’s precision, but a large component within the same vector can still dominate its scale. It also requires more scales to compute and, in a stored quantized cache, retain. Per-tensor scaling needs fewer scales but lets a large value affect a much larger group. Both modes use the same number of bits for each quantized component; their scale metadata differs. Actual serving systems may also use per-head, per-channel or block scales.

These definitions follow the lane’s fake-quantization implementation: per-token takes the absolute maximum over the last (head-dimension) axis; per-tensor takes it over all axes. The example uses the integer branch; FP8 has a different numerical grid.

Two methods are compared. Post-hoc quantization takes a finished baseline checkpoint and quantizes its cache only at evaluation; it trains nothing and is the curve to beat. Quantization-aware training (QAT) trains the model from scratch with the cache fake-quantized at every step through a straight-through estimator, so the optimizer learns to tolerate the coarse cache.

Reading the deltas. Loss differences are in nats, not percentages, and are calculated from the four-decimal losses shown. “Δ vs baseline” means loss minus 2.9258: positive is worse, negative is better. “Loss recovered” means post-hoc minus QAT: positive is better. Each other comparison names its reference.

Three findings read straight off the curve:

  • 8-bit fp8 is nearly free at both granularities, under +0.001. fp8 is not where the interesting question lives.
  • Keys are more fragile than values. At 4-bit per-token, quantizing the keys costs +0.0083 (K4 V16) while quantizing the values costs +0.0032 (K16 V4). The cache tolerates coarse values far better than coarse keys.

Stress sweep: which hyperparameters help at the hardest cell

The hardest cell that still trains to a finite, better-than-random loss is K2 V2, per-tensor, query-key normalization off (5.5000). To ask whether the optimizer alone can rescue it, each training hyperparameter is moved one at a time around the baseline (learning rate 0.003, warmup 1%, weight decay 0.1), with two extra seeds to measure the noise.

This cell is seed-unstable, so its noise floor is not 0.008. Three baseline-setting runs at different seeds give 5.50, 5.59 and 6.05: a standard deviation of 0.30, so two sigma is 0.60 nats, about seventy-five times the clean floor. At 2-bit per-tensor with query-key normalization off, the seed alone moves the loss by half a nat. Read every row below against this 0.60 band.

The findings:

  • A lower learning rate is the one optimizer knob that helps. Learning rate is monotonic: 0.001 gives 5.09, 0.003 gives 5.50, 0.009 gives 5.90. The span across the three points is 0.81 nats, larger than the 0.60 seed band, so the trend is real. A higher learning rate makes the hardest cell worse.
  • Longer warmup hurts sharply. Both longer warmups are far worse, +0.90 and +0.97, well beyond the seed band. The short default warmup is best here.
  • More weight decay does not help. Weight decay is monotonic the wrong way (5.50, 5.63, 5.80). The effect is inside the seed band, so it is weak, but there is no sign of rescue.

Put together with the frontier, the ranking at the highest KV quantization is clear: query-key normalization first, by a wide margin, then a gentler learning rate for a modest further gain. The stress cell's seed instability swamps the small optimizer effects, so no optimizer setting makes 2-bit per-tensor reliable on this model without query-key normalization.

Reproduce

Each part of this page is one defconfig in knlp:

make defconfig-cs312-problem-1      # part 1: one knob at a time (17 runs)
make defconfig-cs312-problem-1b     # part 2: pairs that co-vary
make defconfig-cs312-problem-1c     # part 3: the learning-rate schedule
CS312_P1C_CELLS=wsd0.1:0.1,wsd0.2:0.1,wsd0.5:0.1,wsd0.8:0.1 \
  make defconfig-cs312-problem-1c   # part 3: the decay-fraction sweep
make defconfig-cs312-kv-quant       # part 4: post-hoc curve + trained frontier
make defconfig-cs312-kv-quant-sweep # part 4: stress-cell sweep
make

The gradient noise scale is measured separately by tools/reproduce/cs312/cs312_noise_scale.py, which trains nothing: it loads the model at each kept checkpoint of a run and estimates the two gradient terms from independent batches. Keep checkpoints with keep_checkpoint_steps on the run you want to measure.

The fake-quant hook quantizes keys and values at the attention input with a straight-through estimator, so the same code path serves both post-hoc evaluation and quantization-aware training. The post-hoc curve runs as an evaluation-only pass over a trained checkpoint; the frontier and the sweep train each cell from scratch. All runs evaluate on the same 1,000 validation sequences, and each training cell takes roughly ten to fifteen minutes on one H100.

All numbers here are for the d8 course model at the course training horizon, on the course validation set, with one seed per cell outside the three baseline repeats. They are a clean study on one small decoder, not a claim about every model scale or every serving stack. The hyperparameter conclusions are tied to this fixed token budget in particular: the batch-size penalty is a step-count penalty, and it would read differently at a fixed step count. The KV-quantization results (keys more fragile than values, the granularity gap, and the value of query-key normalization) agree with the larger-model work elsewhere on this site, but each remains model-specific until measured again.
