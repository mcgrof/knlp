The filesystem
is not the tax.

Moving a KV cache between GPUs through NVMe does not require giving up a filesystem. On the same drive, with the payload in GPU memory and reaching the device as a registered dma-buf, writing to a file on XFS or ext4 lands within a few percent of writing to the raw namespace — and it holds for both implementations independently. The cost that does show up is elsewhere.

The comparison covers two implementations that both reach storage — the vLLM storage handoff connector over NIXL, and LMCache raw_block driving the device itself — against three targets each, with NIXL GDS as the baseline.

The GDS column is cuFile POSIX, not GPUDirect. With cuFile logging on, every transfer in this sweep recorded NVMe Driver not registered with nvidia-fs!!! followed by using cuFile posix read/write with compat mode enabled. /proc/driver/nvidia-fs/modules lists only wekafsio: no block driver ever registered, and an upstream nvme has no nvidia-fs hooks to register with. So this column is ordinary POSIX read/write with a host bounce — not peer-to-peer, not dma-buf, not nvidia_peermem. It is a useful floor for "what you get if GDS does not engage", and it is not a measurement of GDS.
cuFile and dma-buf are not alternatives for local NVMe. cuFile does carry dma-buf support — CUFILE_DMABUF_ENABLE, rdma_buffer_dmabuf_reg — but those paths are for its RDMA transport. For a local NVMe device its GPU-direct route is nvidia-fs. The io_uring column reaches the same drive through the in-tree nvme-pci driver with a dma-buf attached to it, which is a different mechanism rather than a faster setting of the same one.
One trap for anyone reproducing this. cuFile must initialise before torch establishes a CUDA context. Import torch first and registration still succeeds while every transfer then fails with internal error (err=5030), which reads like a device problem and is not one. Create the NIXL agent and its GDS backend before importing torch. Separately, cuFileBatchIOSubmit refuses more than one descriptor here, so the GDS column runs at a queue depth of one.

What this does and does not establish

ESTABLISHED

A file on XFS or ext4 carries the KV cache at essentially the raw-device rate on this drive, through the same io_uring path, with a GPU dma-buf as the payload. Both implementations show it independently, which is what makes it a property of the path rather than of one codebase. Keeping a filesystem is not what costs throughput.

NOT ESTABLISHED

Nothing here says what GDS would do on a host booted for it, where cuFileBatchIOSubmit works and the arm could queue like the others. Until that runs, the GDS column measures a path operating under a constraint the others do not have, and the gap should not be read as a verdict on GDS itself.
