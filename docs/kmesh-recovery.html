KMesh / Recovery across processes

Questions 21–25

Can shared state survive a separate cache process?

The retention experiments restore an exact prefix through the existing serving path. The next historical phase moves beyond that baseline: recover state at different positions through a separate cache server, then coordinate recovery across consumers. The controls below qualify its foundations.

21. Do the native layouts and rotations preserve the data?

All 32 required synthetic CUDA cases passed on October 23, 2026. The executor accepts several paged key/value layouts, so a positional recovery test must check each layout's addressing as well as its mathematics. The controls cover head-major and token-major storage, separate key/value planes and fused content-width formats, multiple object groups, partial tails and repeated reuse of destination slots.

Values and unchanged-position keys preserve their raw BF16 words, including negative zero. Shifted keys match an independent CPU rotation with absolute tolerance 0.03125 and zero relative tolerance. Poisoned destinations expose unintended writes. These are small synthetic tensors: four layers per group, two heads, head width 16, eight-token chunks and four-token blocks. They do not establish model-output quality or serving latency.

The test host has an RTX 4090. The prepared runtime uses Python 3.13.15, PyTorch 2.13.0+cu130, CUDA runtime 13.0 and pytest 9.1.1, with two OpenMP/MKL threads. The source and reference native binaries are pinned in the native qualification instructions. Some handler tests use storage and event-transport stand-ins; their planner, tensor geometry and CUDA kernels are real.

22. Who owns a registration and its unfinished work?

The receiving client's actual transport identity owns the registered state. An instance number alone cannot authorize its replacement client to use an old registration. A server boot, storage generation, semantic domain, worker registration and accepted operation each have an explicit identity. Retiring a registration first closes admission and revokes its users; its tensors remain held until accepted work physically finishes.

Ending a request, losing a heartbeat or cancelling a client does not prove that GPU work stopped. Uncertain completion therefore retains the exact paged and rotary generations. Store clearing and shutdown refuse outstanding physical debt. These controls are separate from the normal request heartbeat.

23. Do CUDA copies retain memory until they finish?

Yes, in the six tested download/upload cases. A separate exporter and test-server process exchange real CUDA interprocess communication handles. Downloads must encounter a producer still pending on a non-default stream, wait for its event, copy the rotary tables and compare exact host bytes. Uploads begin from completed private host snapshots, allocate private device targets and compare their bytes after the actual copy stream drains.

Each direction has success, drained-error and undrained-error cases. Error injection occurs after a real copy submission. A failed drain must preserve both registration holds and all source/destination memory until a later physical drain succeeds. The six-case transfer profile supplies the logical receiving identity explicitly. The later registration and service gates below exercise actual public RPCs.

The BF16 paged allocation has shape [2, 16, 4, 2, 8]; the FP32 rotary table is [64, 8], or 2,048 bytes. A synthetic sequence of 512 matrix multiplications on FP32 [2048, 2048] inputs keeps the download producer pending. This challenges event ordering; it is not a model or latency workload. The exporter remains alive through child cleanup. Actual device faults and exporter death are unqualified.

These copies use ordinary CUDA IPC and host/device transfers. They perform no DMA-BUF storage I/O. The successful copy gate does not imply that an imported mapping has closed: exporter teardown needs a separate exact-generation, server-owned acknowledgement.

24. What remains before one real shifted restore?

The managed raw control service now proves release; multiprocess model recovery remains disabled. Its pinned qualification passes 331 CPU cases and ten separate-process CUDA cases on the RTX 4090 runtime above. Both ZeroMQ and gRPC exercise actual receiving-client ownership, registration, ordered rotary preparation and checked retirement. Twenty-five existing CUDA controls also pass against the implementation before the stronger release run.

The server records its boot identity, the receiving client, a registration nonce, exact tensor views and a context generation before import. Retrying identical registration returns saved facts without opening another mapping; changed views, foreign clients and stale generations refuse. Ordered rotary preparation waits for a genuinely pending producer, copies completed host snapshots and publishes private uploaded tables. Exact byte checks pass, and later worker writes leave the private tables unchanged.

A release receipt follows physical completion and checked mapping retirement. Retirement closes admission, revokes holds and refuses unfinished copy debt. It removes the exact rotary generation, closes imported raw references, retires temporary inputs against new imports and detaches the exact context entry before caching its receipt. Successful workers then drop the exported tensors, empty the allocator cache and allocate replacements while the importing service remains alive. Independent private-table readback and repeated retirement still pass, with no additional native close call.

A refusal known to precede native effects can be retried after cleanup. An ambiguous native import or close remains quarantined until the importing process ends; its old pointer must not be submitted again because the address could have been reused. Partial construction also requires importer exit. The tests inject native errors before driver effects and exercise repeated requests/status lookup without dropping network packets. Actual device-fault recovery and network-loss timing remain unqualified.

The service admits one context and one rotary preparation per process, world size one, contiguous BF16 full attention, CPU DRAM L1 and same-host CUDA events. Its assembled interface exposes KMesh controls without generic transfer, lookup, peer, HTTP or automatic reaping handlers. Active GDS is refused because its staging deregistration currently logs backend errors and cannot prove checked release. These are registration and lifetime results; they measure no storage I/O, model throughput or DMA-BUF latency.

Next comes fenced storage execution and the actual model consumer. Publication and retrieval must use the accepted namespace and exact borrowed resources through physical completion. The worker must preserve destination block ownership until restoration finishes. A real shifted restore must then compare model outputs and repair deeper-layer state that depends on its original preceding context. Rotating key positions alone does not remove that dependence. Numerical checks, corruption rejection, fallback and physical drain precede the staged versus DMA-BUF serving comparison. The earlier exact-prefix retention result answers a separate, already measured question.

Reproduce the completed control-service gate

Use the prepared environment described in the CPU ownership instructions and CUDA instructions. Pin LMCache d3a4b9a6dd2a8edb649d24d48cb6e6b46b10bd9e and the paired vLLM source 9df1493cae0b98380a3c3ecb9b2d41776a6d8735, then regenerate the selected LMCache source's gRPC bindings as documented. Both public component branches are named 2026-10-23-feature-kmesh-mp-recovery: LMCache and vLLM. Select each exact source pin rather than the moving branch tip.

make defconfig-kmesh-managed-raw-service-cpu
make kmesh-contracts-plan
KMESH_CONTRACTS_SOURCE=/path/to/pinned/LMCache \
  KMESH_CONTRACTS_VLLM_SOURCE=/path/to/pinned/vllm \
  KMESH_CONTRACTS_OUTPUT=/path/outside/checkouts/cpu-capture \
  KMESH_CONTRACTS_PY=/path/to/prepared/python make kmesh-contracts

# Real raw service registration and release: ten required CUDA cases
make defconfig-kmesh-managed-raw-service-cuda
make kmesh-native-plan
KMESH_NATIVE_SOURCE=/path/to/pinned/LMCache \
  KMESH_NATIVE_OUTPUT=/path/outside/checkouts/cuda-capture \
  KMESH_NATIVE_PY=/path/to/prepared/python make kmesh-native

Every execution uses a fresh capture directory outside the checkouts and requires every selected setup, body and teardown to pass. The helpers verify source, loaded wire schemas, runtime and native identities; the CUDA gate also checks the complete process-exit log for outstanding exporter-reference warnings. Saved-capture verification needs the producing helper revision. Captured receipts, logs and tensors stay outside public Git. Receipt consistency does not independently authenticate hardware execution.

The linked instructions preserve the exact source pins and defconfigs for the earlier native-layout, context ownership, ordered-registration, raw-copy and checked-context gates. They remain separate captures with their original scope.

25. When can collective recovery be evaluated?

After one serial restore has passed the ownership and model gates. Collective recovery means several consumers coordinate reuse of compatible state, potentially across worker instances. It must retain each consumer's generation, destination and unfinished work, rather than treating a shared logical request as one physical completion.

First qualify the bounded single-worker path. Then extend its real storage, rotation and model-repair consumer to multiple instances and compare against independent serial restores. Rank barriers in the CPU registry do not establish GPU shard compatibility, collective execution or a throughput gain.
