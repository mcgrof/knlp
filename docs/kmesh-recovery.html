KMesh / Recovery across processes

Questions 21–25

Can shared state survive a separate cache process?

The retention experiments restore an exact prefix through the existing serving path. The next historical phase moves beyond that baseline: recover state at different positions through a separate cache server, then coordinate recovery across consumers. The controls below qualify its foundations.

21. Do the native layouts and rotations preserve the data?

All 32 required synthetic CUDA cases passed on October 23, 2026. The executor accepts several paged key/value layouts, so a positional recovery test must check each layout's addressing as well as its mathematics. The controls cover head-major and token-major storage, separate key/value planes and fused content-width formats, multiple object groups, partial tails and repeated reuse of destination slots.

Values and unchanged-position keys preserve their raw BF16 words, including negative zero. Shifted keys match an independent CPU rotation with absolute tolerance 0.03125 and zero relative tolerance. Poisoned destinations expose unintended writes. These are small synthetic tensors: four layers per group, two heads, head width 16, eight-token chunks and four-token blocks. They do not establish model-output quality or serving latency.

The test host has an RTX 4090. The prepared runtime uses Python 3.13.15, PyTorch 2.13.0+cu130, CUDA runtime 13.0 and pytest 9.1.1, with two OpenMP/MKL threads. The source and reference native binaries are pinned in the native qualification instructions. Some handler tests use storage and event-transport stand-ins; their planner, tensor geometry and CUDA kernels are real.

22. Who owns a registration and its unfinished work?

The receiving client's actual transport identity owns the registered state. An instance number alone cannot authorize its replacement client to use an old registration. A server boot, storage generation, semantic domain, worker registration and accepted operation each have an explicit identity. Retiring a registration first closes admission and revokes its users; its tensors remain held until accepted work physically finishes.

Ending a request, losing a heartbeat or cancelling a client does not prove that GPU work stopped. Uncertain completion therefore retains the exact paged and rotary generations. Store clearing and shutdown refuse outstanding physical debt. These controls are separate from the normal request heartbeat.

23. Do CUDA copies retain memory until they finish?

Yes, in the six tested download/upload cases. A separate exporter and test-server process exchange real CUDA interprocess communication handles. Downloads must encounter a producer still pending on a non-default stream, wait for its event, copy the rotary tables and compare exact host bytes. Uploads begin from completed private host snapshots, allocate private device targets and compare their bytes after the actual copy stream drains.

Each direction has success, drained-error and undrained-error cases. Error injection occurs after a real copy submission. A failed drain must preserve both registration holds and all source/destination memory until a later physical drain succeeds. The tests supply the logical receiving identity explicitly; they do not yet exercise an ordered registration RPC through the public server.

The BF16 paged allocation has shape [2, 16, 4, 2, 8]; the FP32 rotary table is [64, 8], or 2,048 bytes. A synthetic sequence of 512 matrix multiplications on FP32 [2048, 2048] inputs keeps the download producer pending. This challenges event ordering; it is not a model or latency workload. The exporter remains alive through child cleanup. Actual device faults and exporter death are unqualified.

These copies use ordinary CUDA IPC and host/device transfers. They perform no DMA-BUF storage I/O. The successful copy gate does not imply that an imported mapping has closed: exporter teardown needs a separate exact-generation, server-owned acknowledgement.

24. What remains before one real shifted restore?

Multiprocess KMesh engine admission remains closed. An explicitly requested KMesh recovery profile must refuse an unsupported multiprocess connector before creating the engine. Ordinary multiprocess use without that profile is a separate path.

The next gate orders the very first rotary-table read against its producer, normalizes a completed private snapshot, uploads it, and publishes only the completed generation. Legacy registration with already-drained inputs does not prove this sequence. The server also needs truthful imported-mapping teardown, fenced storage publication and retrieval, and a worker consumer that preserves destination block ownership through completion.

A real shifted restore must then compare model outputs and repair the state whose deeper-layer contents depend on its original preceding context. Rotating key positions alone does not make that contextual dependence disappear. Numerical checks, deliberate-corruption rejection, fallback and physical drain must pass before a staged versus DMA-BUF serving comparison can qualify. The earlier exact-prefix retention result answers a different, already measured question.

Reproduce the completed prerequisite gates

Use the prepared environments and exact source pins described in the CPU ownership instructions and CUDA instructions. The public component branches are LMCache and vLLM. Select the profile's exact commit rather than a moving branch tip.

# CPU ownership and transfer controls: 292 required cases
make defconfig-kmesh-rotary-transfers-cpu
make kmesh-contracts-plan
KMESH_CONTRACTS_SOURCE=/path/to/pinned/LMCache \
  KMESH_CONTRACTS_VLLM_SOURCE=/path/to/pinned/vllm \
  KMESH_CONTRACTS_OUTPUT=/path/outside/checkouts/cpu-capture \
  KMESH_CONTRACTS_PY=/path/to/prepared/python make kmesh-contracts

# Native layouts: 32 required CUDA cases
make defconfig-kmesh-native-cuda
KMESH_NATIVE_SOURCE=/path/to/native-profile/LMCache \
  KMESH_NATIVE_OUTPUT=/path/outside/checkouts/native-capture \
  KMESH_NATIVE_PY=/path/to/prepared/python make kmesh-native

# Retained downloads and uploads: six required CUDA cases
make defconfig-kmesh-rotary-transfers-cuda
KMESH_NATIVE_SOURCE=/path/to/transfer-profile/LMCache \
  KMESH_NATIVE_OUTPUT=/path/outside/checkouts/transfer-capture \
  KMESH_NATIVE_PY=/path/to/prepared/python make kmesh-native

Every execution uses a fresh capture directory outside the checkouts. Saved-capture verification runs on CPU with the producing helper revision. Captured logs, raw receipts and tensors remain outside the public source tree. Receipt consistency does not independently authenticate hardware execution.

25. When can collective recovery be evaluated?

After one serial restore has passed the ownership and model gates. Collective recovery means several consumers coordinate reuse of compatible state, potentially across worker instances. It must retain each consumer's generation, destination and unfinished work, rather than treating a shared logical request as one physical completion.

First qualify the bounded single-worker path. Then extend its real storage, rotation and model-repair consumer to multiple instances and compare against independent serial restores. Rank barriers in the CPU registry do not establish GPU shard compatibility, collective execution or a throughput gain.
