KMesh / Reusing saved state

Questions 21–25

Can requests reuse saved state when shared text moves?

Four follow-up requests need the same text, but place it at different positions among their own instructions. We test whether they can reuse the model's saved work through a separate cache process, and whether reading that work directly from SSD into GPU memory helps.

Start with the problem

When a language model reads a prompt, it builds a key/value (KV) cache: saved attention state that lets it use earlier tokens without recalculating all their work. vLLM runs the model; LMCache stores that state outside the engine, in host RAM or on storage. A token is a small piece of text.

The earlier retention experiment reused the same beginning of a prompt. This experiment asks a harder question. Suppose one agent has already read a report. Another agent puts new instructions before that report:

Same report, different preceding text
RequestIllustrative prompt order
First requestShared report → question A
Follow-upNew instructions → shared report → question B

The words of the report are unchanged, but their positions and preceding context have changed. Simply copying their saved state is insufficient. Restoration means loading that state into the follow-up's GPU memory. Repair means recalculating selected model work so the moved state can be used. Our TokenDance-style reproduction uses LMCache's CacheBlend implementation for that selective recalculation. Our extensions identify the shared text segments, adjust their saved positions and require recalculation wherever saved state is missing. The comparisons below all include these extensions.

CacheBlend already handles reuse beyond an identical prompt beginning. The TokenDance-style case gives KMesh a group of related requests and an explicit description of the text they share. The experiment checks how to coordinate that reuse across processes and storage.

Which sections test the implementation, and which run the model?

Questions 21–23 are implementation checks. vLLM already organizes its saved attention state into memory blocks, and LMCache already supports a separate cache process. Those existing capabilities are the starting point. The checks test the recovery code we add around them:

  • Question 21: Can our restore code write into vLLM's existing memory layouts and adjust the saved keys when text moves?
  • Question 22: Do our shared-segment ownership rules keep memory safe across LMCache's existing process boundary? The suite also checks existing transport behavior.
  • Question 23: Does our code wait for unfinished GPU copies before releasing or reusing their memory?

Passing these checks establishes that the tested implementation handles those operations correctly. It does not demonstrate a speed or capacity benefit for KMesh. Questions 24 and 25 run the actual model. Question 24 compares model outputs and measures SSD loading time. Question 25 checks whether changing the execution order of four requests changes their outputs or prevents safe recovery when one fails.

What we found

For each of the four requests, its generated tokens were identical across these three runs:

  1. Existing TokenDance-style method: Run our extended LMCache CacheBlend code inside the model process, finishing one request before starting the next.
  2. Move loading to another process: Obtain saved state from the separate cache process, then run the same CacheBlend method, still finishing one request at a time.
  3. Also change the execution order: Use the separate cache process, but run model layer 1 for all four requests, then layer 2 for all four, and continue through the model.

For each request, we also compared the saved attention data and the scores used to choose the next token. They matched bit for bit across all three runs. In this test, moving the data through another process and changing the execution order did not change what our TokenDance-style serial implementation computed.

CacheBlend itself reuses some saved work and recalculates selected parts. We have not shown here that this approximate method gives the same result as recalculating the entire prompt. The comparison above checks whether our engineering changes alter the existing method's output.

A separate SSD test finds that reading directly into GPU memory reduces storage-read time by 3.7%, but the complete loading process is sometimes faster and sometimes slower. That test runs one request at a time with singleflight off. It uses the fixed retention code, then deliberately evicts retained data before every child to force fresh SSD reads. The four-request group uses saved state in host RAM; combining it with SSD loading remains untested.

These tests ran on one RTX 4090 on October 23–24, 2026. For the model and SSD comparisons, jump to question 24; for the four-request execution order and failure test, jump to question 25.

21. Can we move saved state into the right GPU locations?

Implementation check: This tests our recovery code against vLLM's existing memory layouts; it does not introduce vLLM's block management. The small GPU tests pass.

vLLM divides its saved attention state into memory blocks. Those blocks can store tokens, attention heads and key/value data in different orders. An attention head is one of the model's parallel attention calculations. The restore code must find the right addresses for each supported arrangement.

Position matters too. The model encodes a token's position by rotating its key vectors, a method called rotary position embedding (RoPE). When shared text moves, the restore code adjusts that rotation. This adjustment handles position; it does not by itself fix the effect of different preceding text. That is why the real-model repair test in question 24 is necessary.

All 32 required synthetic GPU cases passed on October 23. They check that values stay unchanged, moved keys receive the expected positional adjustment, and memory outside the requested destination stays untouched. These use small, constructed arrays rather than a language model, so they establish correct copying and addressing, rather than answer quality or speed.

Array layouts, numerical checks and test runtime

The controls cover head-major and token-major storage (whether heads or tokens are grouped first in memory), separate key/value planes and formats that pack keys and values together. They include multiple saved-object groups, partly filled final blocks and repeated reuse of destination slots. These storage orders are different from the model execution order in question 25.

Values and keys that stay at the same position preserve their raw BF16 bits, including negative zero. BF16 is the two-byte floating-point format used for the saved state. Moved keys match an independent CPU rotation with absolute tolerance 0.03125 and zero relative tolerance. Destinations start with invalid data so unintended writes are visible. Each synthetic group has four layers, two heads, head width 16, eight-token chunks and four-token blocks.

The RTX 4090 runtime uses Python 3.13.15, PyTorch 2.13.0+cu130, CUDA runtime 13.0 and pytest 9.1.1, with two OpenMP/MKL CPU threads. The source and native binaries are pinned in the GPU qualification instructions. Some handler tests use stand-ins for storage and event transport; the array addressing and GPU operations are real.

22. How does a separate cache process use memory safely?

Implementation check: LMCache already supports a separate cache process. We test the ownership and memory-lifetime rules added for our shared-segment recovery, along with existing transport checks.

The model worker and cache service run as separate processes on the same machine. The cache service holds the shared originals while individual requests come and go. Before it accesses GPU memory, the worker registers it: it supplies the memory handles, describes their layout and establishes which client owns them. The service must distinguish that exact allocation from a later allocation at the same address.

The tested service keeps ownership tied to the actual client and allocation. A replacement client cannot reuse an old registration merely by claiming the same instance number. Closing a registration stops new work, but its buffers remain reserved until already accepted copies and GPU operations finish.

Consider a cancelled request whose copy is still running. If its destination were immediately handed to another request, the old copy could overwrite the new request's state. The service therefore waits for physical completion before releasing memory. Losing a heartbeat or cancelling a request is insufficient proof that the GPU has stopped.

23. What happens if a copy fails while the GPU is still working?

Implementation check: This checks our copy ordering and cleanup. It does not measure a model-output or performance improvement.

The memory stays reserved until pending work has actually finished. GPU copies can run asynchronously: the call that submits a copy may return before the copy completes. The service must also wait for the model's earlier writes before reading their results.

Six tests exercise real copies between GPU memory and host RAM with separate processes. Each direction has a successful case, an error whose pending work can be completed, and an error where the first attempt to wait is refused. In that last case, the source and destination remain held until a later wait succeeds. All six passed.

The implementation calls this wait a drain. Draining finishes already submitted work; it does not mean submitting the failed operation again. This is what makes it safe to release buffers or recalculate a failed request into them.

How the copy-ordering tests work

An exporter process shares real CUDA interprocess communication (IPC) handles with the test service. A download waits for an intentionally delayed producer on a separate GPU stream, then copies the position-rotation tables and compares exact host bytes. An upload starts from a completed private host snapshot, copies into a private GPU allocation and compares bytes after the copy stream finishes. Errors are injected after actual copy submission.

The BF16 paged allocation has shape [2, 16, 4, 2, 8]; the FP32 rotation table is [64, 8], or 2,048 bytes. A sequence of 512 matrix multiplications on FP32 [2048, 2048] inputs keeps the producer busy. This deliberately tests ordering, rather than modelling serving latency.

The six-case transfer profile supplies the receiving identity explicitly; later registration and service tests exercise actual transport requests. The exporter stays alive through cleanup. Device faults and exporter death are untested. These are ordinary CUDA IPC and host/device copies, with no DMA-BUF storage I/O. Finishing a copy and closing an imported memory mapping are separate checks; exporter teardown also needs the service's release acknowledgement.

24. Does loading saved state through another process change the model's output?

For each request, the generated tokens match when loading inside the model process and when loading through the separate cache process. Their saved attention data and next-token scores also match exactly. DMA-BUF gives a small, consistent reduction in read-call time, but no consistent reduction in complete restoration time. These are separate comparisons.

What actually ran?

The model is Qwen2.5-0.5B-Instruct, a small model with 24 layers. A layer is one stage of the model's computation; each request passes through all 24. One leader request supplies saved attention state for four shared text segments, totalling 416 tokens. Four follow-up requests, called children, each have a 512-token prompt and place those segments at different positions. This is the measured workload behind the report illustration above.

Why use this case instead of a stock CacheBlend example?

The TokenDance-style case supplies the multi-request workload and sharing information; CacheBlend supplies the selective recalculation. Original CacheBlend already addresses combining cached text chunks with different preceding context. Here the application knows which four children will reuse which segments. Our integration carries those exact segment identities and positions into each request and can coordinate the children as a group.

This lets us test the KMesh questions: can a separate cache process hold one unchanged source, can each child restore it into its own model state, and can the children advance together without interfering with one another? Keeping the same prompts, shared segments and repair settings lets us compare changes in loading and execution order against the established serial run.

A stock CacheBlend workload would also be a valid way to study DMA-BUF loading. This experiment measures our existing multi-request integration. It establishes no advantage of our additions over stock CacheBlend. A direct comparison would need a separate stock CacheBlend control with clearly defined segment inputs and recomputation settings, alongside full-prompt recalculation.

Which repair implementation does this use?

It uses our TokenDance-style recovery code built on LMCache's CacheBlend implementation. LMCache calls the feature CacheBlend, or cache blending. It implements the selective recalculation approach from the CacheBlend paper: reuse saved attention state and recalculate selected tokens to account for their changed preceding context.

In our fork, the one-request entry point is LMCBlender.blend(). Our TokenDance-style additions supply explicit shared text segments and their positions, give each request its own execution state, and force recalculation of every position without restored data. The four-request version uses our LMCBlender.blend_group() extension. This is our reproduction built with LMCache, rather than the TokenDance authors' implementation. The first comparison already includes our additions; it is not an unmodified upstream CacheBlend run.

First we run that extended serial implementation with loading inside the model process. Then we load the same saved segments through the separate cache process, place them in each child's private GPU memory, and run the same repair algorithm. Here serial means finishing one child before moving to the next. The shared source data stays unchanged; each child has its own working copy because repair changes model state.

Repair is needed because a token's saved state depends on the text before it, as well as its position. Adjusting key rotation fixes the position component. CacheBlend's selection determines which restored positions receive additional work, and our extension adds every position missing restored state. This is approximate reuse of earlier computation; the comparison is against the same method running serially, rather than recalculating the entire prompt.

Did moving the data through another process change the result?

No differences were observed against that reference in this test. All four children have bit-for-bit identical saved keys and values and logits, the scores used to choose the next token. Their generated tokens and choices of which positions to recalculate also match. We check those choices at every layer: four children × 24 layers gives 96 comparisons.

Seven failure controls also pass, including missing or corrupt saved data and failure after GPU work has been submitted. Recalculation is allowed only after pending work finishes and releases the destination memory. If cleanup cannot complete, the request must wait or fail safely.

What was compared Both runs use CacheBlend to reuse saved state and recalculate selected work. Moving loading to a separate process gives the same generated tokens, saved attention data and next-token scores for these four requests. This does not show that CacheBlend matches recalculating the whole prompt, saves total memory or improves serving speed. The ordinary multiprocess serving connector still refuses this recovery mode; the dedicated reproducer is the tested path.

Does reading directly into GPU memory make this faster?

We compare two ways of loading the saved segments from an NVMe SSD, a fast PCIe-connected solid-state drive. The model, data and repair algorithm stay the same. Children still run one at a time.

  1. Host staging: SSD → locked host RAM → GPU memory. The RAM buffer is pinned so the device can access it throughout the transfer.
  2. DMA-BUF: SSD → GPU memory through a registered buffer shared with the kernel. DMA-BUF is Linux's buffer-sharing interface; this route avoids the host staging step for the storage read.

This is a forced-read storage comparison. Singleflight is off; the retention fix is present and enabled in both routes. We run seven matched pairs, alternating which route goes first. Each pair runs all four children through each route, one child at a time.

Why was singleflight off?

The earlier engine singleflight mechanism joins requests with an identical prefix, so they can adopt one restored prefix inside vLLM. This workload puts shared text at different positions after different input. Each child therefore keeps its own position-adjusted and repaired model state. That exact-prefix mechanism is not the mechanism for sharing these interior segments. Prefix caching is disabled in this fixture so recovery is attributed to the explicitly named segments.

Sharing one stored source is still useful. Several children can use the same unchanged saved bytes while keeping their repaired GPU copies private. Retaining that source across children, and joining simultaneous loads of it, are the relevant storage optimizations. This particular transfer test runs children serially and forces a fresh load for every child, so it can time the SSD routes. The combined shifted-segment read-once serving test remains to be evaluated.

The test explicitly removes the four retained objects from LMCache's memory tier before every child. Each child therefore reads the same saved objects from SSD again: 12 MiB per child, 48 MiB across four children. This eviction makes every child exercise the selected SSD route instead of timing a hit in the memory cache. The repeated reads are deliberately requested by the benchmark, rather than caused by losing the retained copy unexpectedly.

The earlier read-once experiment had a different setup: singleflight was on, and the fixed retention kept one 48 MiB ancestor available across the children. It read that ancestor from SSD once. Here, forced eviction takes away that cross-child reuse to compare the two storage routes.

Should we compute the checksum on the GPU?

Yes: GPU-side SHA-256 is a concrete candidate to evaluate. The current restore code copies each of four padded 3 MiB source objects to the CPU and hashes it there. Hashing those bytes where they already reside on the GPU could replace the 12 MiB return transfer with four 32-byte digests: 128 bytes per child, or a small pass/fail result if comparison also runs on the GPU. The hash must cover the same original bytes, including padding, before any position adjustment.

The measured integrity stage is 0.722 ms slower on the GPU route than on the staged route, while read calls are 0.152 ms faster. This makes the integrity path worth isolating. It does not tell us how fast GPU hashing will be or predict the complete-restore gain. Moving the checksum changes the integrity implementation; the CacheBlend recalculation method can stay fixed.

There is an implementation to investigate: NVIDIA's cuPQC-Hash provides device-side SHA-256, and its requirements list the RTX 4090's GPU architecture. This is a candidate, not a qualified dependency or a measured result for this workload.

CUDA streams also let independent work overlap. A useful target is to read the next object while hashing a completed object, then restore verified data into the child's private model buffers. The current code waits for loading, checks the checksum, then restores and waits for GPU completion. Implementing overlap requires changing that sequence.

Proposed checksum and overlap evaluation — no results yet

First compare the GPU checksum against the current CPU SHA-256 for the exact same bytes and object boundaries. Then compare complete restoration with CPU hashing versus GPU hashing while keeping operation order unchanged. Finally add overlap between independent object reads and checks. Keep the model, storage route, read sizes, retention and forced-eviction settings fixed so each comparison answers one question.

Our storage route uses io_uring. It is not automatically ordered in a CUDA stream. The implementation must establish I/O completion and GPU visibility before launching a dependent hash kernel, then use CUDA events to order consumers after successful checking. NVIDIA documents the ordering requirements for peer writes. CUDA streams provide the computation schedule; the storage-to-CUDA handoff still needs explicit qualification.

The current checksum is one ordinary SHA-256 per complete 3 MiB object. Hashing smaller pieces independently and combining their digests would change that result. Earlier model-layer consumption would also need a clear integrity rule for each part; the current whole-object check completes before use. Start with identical digests and pipeline independent objects.

Check corruption rejection, padding coverage, missing data and cancellation while work is pending. Keep buffers reserved until I/O and hash kernels finish. Model outputs must still match the serial comparison. Keep independent CPU hashes and full tensor captures in separate qualification runs so they do not reintroduce the full return transfer into the optimized timing.

Measure storage calls, checking, complete restoration and model readiness, plus host transfer bytes and GPU work. Keep GPU hashing only if correctness and cleanup pass and repeated complete-restore measurements improve. GPU launch cost, contention with model computation and the limited number of independent objects can offset the saved copy. No speedup has been measured yet.

This test is separate from the earlier read-once retention result. Here, forcing a fresh read for every child causes 48 MiB of reads across four children. In the earlier test, retention kept one 48 MiB ancestor available and removed repeat reads. The equal 48 MiB totals describe different workloads.

Storage workload, hardware and correctness checks

The RTX 4090 system has a Ryzen 9 9950X3D and Samsung 990 PRO 4 TB SSD. The backing storage uses XFS regular files on the patched DMA-BUF-capable Linux 7.3-rc3 kernel. The Python/PyTorch/CUDA runtime is listed in question 21; OpenMP/MKL use two CPU threads. Both routes use a 64 MiB source memory pool, a 1 MiB metadata area, queue depth 32, maximum transfer size 128 KiB and the same 1 GiB locked-memory allowance. Fresh files are fully initialized and synced before use. Hardware caches can remain warm.

The 416 valid tokens use 4.875 MiB of state. The storage format pads each of the four segments to a 256-token object, giving 12 MiB read per child. Each object is 3 MiB: 256 tokens × 24 layers × 2 key/value planes × 2 heads × 64 elements × 2 BF16 bytes. A child issues 96 native payload-read operations, or 384 across four children. These are software read operations, not traced physical NVMe commands.

Before admitting timings, each route passes a separate model test in which the freed 64 MiB source pool is filled with invalid numbers. A successful load must therefore bring real data from storage; leftover GPU bytes cannot fake it. The two qualification runs and fourteen timed runs all match the reference's raw keys, values, next-token scores, generated tokens and recalculation choices. Maximum absolute key/value and score differences are 0.0.

The reproducer retains duplicate reference storage and numerical instrumentation. These checks make this a controlled transfer-path comparison, rather than a production memory-footprint or serving-performance result.

The frozen model configuration uses LMCacheConnectorV1 with our KMesh extension and enable_prefix_caching=false. It does not activate the earlier LMCacheMPConnector exact-prefix singleflight gate. The storage manager uses prefetch_policy=retain and prefetch_join_overlaps=false, so its optional joining of simultaneous loads is also off. The measured LMCache source includes the earlier retention fix. The runner's StorageObserver.cold() explicitly evicts the source set before each child.

Earlier storage-only qualifications

These earlier tests check moving saved segments without running model repair. The initial profile passes 341 CPU cases and 24 CUDA cases on the RTX 4090 runtime above. The CUDA set contains ten raw service lifetime controls and fourteen native span cases, covering both ZeroMQ and gRPC. These counts overlap the earlier profiles.

The interior-source extension also passes: 341 CPU cases and 36 CUDA cases at LMCache e23d4acd29420a0258a9666b98d9a10fdec12b53. It saves a segment beginning at source token five in 24 synthetic layers, using both token-major (NHD) and head-major (HND) layouts, and restores it at positions three and nine. Values remain bitwise exact; independent key rotation and untouched destination slots pass. If gathering the source fails, buffers remain reserved until pending work finishes. An incomplete source is never made available for reuse. Each layer view keeps its exporting allocation alive. This profile uses complete storage chunks.

The worker registers its BF16 attention buffer and private position tables. To save a segment, the service holds the exact allocations, waits for source writes, copies keys and values into locked host RAM and confirms that every chunk was accepted before making the source available. Unique keys distinguish allocations. Buffers used by unfinished I/O stay reserved even if a software lock expires.

The test recycles the original GPU slots before restoration. It stores sixteen synthetic tokens as two eight-token chunks, then poisons the source GPU cache with invalid data. Restoration places them at token position three in GPU blocks deliberately arranged out of order. Values match raw BF16 bits; keys match an independent CPU RoPE calculation with rtol=0.012 and atol=0.025. Untouched prefix and tail slots remain poisoned. A second restore at the unchanged position passes from the same saved source, whose checksums still match. Position adjustment uses a private GPU working copy, preserving the shared stored bytes.

The paged view is [2, 16, 4, 2, 16]; the FP32 rotary table is [64, 16]. The exporter allocation and host-RAM cache are each 64 MiB; the host allocation matches its allocator's registration unit. Source writes are submitted behind 512 FP32 matrix multiplications on [2048, 2048] inputs to challenge producer ordering. This synthetic fixture measures correctness, not serving latency.

Repeating the same request returns its saved status without launching the GPU operation again. Wrong clients, changed handles and missing or corrupt sources fail before destination writes. Failed or outdated stores cannot become reusable sources. An injected error after GPU submission, combined with a refused completion wait, keeps the source and destination reserved until a later wait succeeds. Cleanup does not resubmit the operation. Device faults and packet loss are not injected by this profile.

25. Can all four requests advance through the model one layer at a time?

Yes: all four requests generate the same tokens whether we finish one request at a time or run one model layer across the group at a time. Their saved attention data and next-token scores also match exactly. The purpose is to let related requests use the same unchanged saved segments while each maintains its own repair state. This experiment checks that the grouping works correctly; it does not establish a speed or memory-capacity benefit.

The motivation for grouping is to bring the requests to the same model stage together, so later work can investigate doing their shared work together at that stage. Here we first check that changing the execution order leaves the model's outputs unchanged and that a failed child can retry safely.

What does “layer-major” mean?

Label the four children A, B, C and D. Each must pass through the model's 24 layers. There are two execution orders:

Same children and model, different execution order
OrderWhat happens
One child at a time (serial)Run A through layers 1–24, then B through layers 1–24, then C, then D.
One layer across the group (“layer-major”)Run layer 1 for A, B, C and D. Then run layer 2 for A, B, C and D. Continue through layer 24.

“Layer-major” describes that loop order. It does not describe how data is arranged in memory, and it does not mean combining the four children's math into one batched calculation. This implementation still runs each child's tensor operations separately on one GPU worker.

What is shared, and what stays private?

The group first loads all four segments for all four children: sixteen placements in total. The original saved segments are shared and remain unchanged. Each child keeps its own GPU destination blocks and working buffers, because its surrounding text and repair calculations can differ. The service checks every member before making the group's restored inputs available to the model.

The saved sources in this group test live in LMCache's host-RAM cache tier. Some implementation files call it “CPU-L1”; that name means a software cache in ordinary system RAM, not the processor's tiny hardware L1 cache. A separate cache process supplies the data to one model worker. The NVMe/DMA-BUF comparison in question 24 ran children serially; it was not this group test.

What did the comparison show?

On October 24, the in-process serial reference, the serial path using the separate cache process and this group path all produced bit-for-bit identical keys, values and next-token scores. All four children's generated tokens and all 96 per-layer recalculation choices also match. Each child restores the same 416 shared tokens within a 512-token prompt.

What if one child fails?

We deliberately fail child B after it finishes its first actual model layer. A, C and D finish with the serial reference's generated tokens and recalculation choices. B waits for its pending work to finish, discards all restored state for its prompt, and retries by recalculating the whole prompt without reuse. Its generated tokens match the ordinary recalculation reference. All shared source handles close with no pending work.

This failure test checks safe fallback and sibling isolation. The mixed repaired/recalculated run checks generated tokens and cleanup; the successful group run is the one with the complete raw-state and next-token-score comparison.

What remains to be demonstrated Combining this group with NVMe/DMA-BUF loading needs its own integration and tests. Batched model operations, sharing across multiple GPU workers, production serving speed and total memory savings are also unmeasured. The ordinary multiprocess serving connector remains disabled for this mode. All compared successful runs use the same approximate CacheBlend method; they produce exactly the same generated tokens, saved attention data and next-token scores in this workload.
Group source and supporting safety tests

The group pins LMCache b9b5687b and vLLM 9df1493cae0b98380a3c3ecb9b2d41776a6d8735, with the runtime listed in question 21. Its supporting profiles pass 694 CPU and 208 CUDA cases, overlapping earlier profiles. They test simultaneous inputs, private writeback, early close and refusal to release memory while work remains pending, across both memory-layout families and both request transports.

Group admission binds the exact ordered requests, resource versions, tokens and declared segments. Already adjusted keys cannot receive the position rotation twice. CPU coordination alone does not establish compatibility of state split across multiple GPUs.
