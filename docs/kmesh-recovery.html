KMesh / Recovery across processes

Questions 21–25

Can shared state survive a separate cache process?

The retention experiments restore an exact prefix through the existing serving path. The next historical phase moves beyond that baseline: recover state at different positions through a separate cache server, then coordinate recovery across consumers. The controls below qualify its foundations.

21. Do the native layouts and rotations preserve the data?

All 32 required synthetic CUDA cases passed on October 23, 2026. The executor accepts several paged key/value layouts, so a positional recovery test must check each layout's addressing as well as its mathematics. The controls cover head-major and token-major storage, separate key/value planes and fused content-width formats, multiple object groups, partial tails and repeated reuse of destination slots.

Values and unchanged-position keys preserve their raw BF16 words, including negative zero. Shifted keys match an independent CPU rotation with absolute tolerance 0.03125 and zero relative tolerance. Poisoned destinations expose unintended writes. These are small synthetic tensors: four layers per group, two heads, head width 16, eight-token chunks and four-token blocks. They do not establish model-output quality or serving latency.

The test host has an RTX 4090. The prepared runtime uses Python 3.13.15, PyTorch 2.13.0+cu130, CUDA runtime 13.0 and pytest 9.1.1, with two OpenMP/MKL threads. The source and reference native binaries are pinned in the native qualification instructions. Some handler tests use storage and event-transport stand-ins; their planner, tensor geometry and CUDA kernels are real.

22. Who owns a registration and its unfinished work?

The receiving client's actual transport identity owns the registered state. An instance number alone cannot authorize its replacement client to use an old registration. A server boot, storage generation, semantic domain, worker registration and accepted operation each have an explicit identity. Retiring a registration first closes admission and revokes its users; its tensors remain held until accepted work physically finishes.

Ending a request, losing a heartbeat or cancelling a client does not prove that GPU work stopped. Uncertain completion therefore retains the exact paged and rotary generations. Store clearing and shutdown refuse outstanding physical debt. These controls are separate from the normal request heartbeat.

23. Do CUDA copies retain memory until they finish?

Yes, in the six tested download/upload cases. A separate exporter and test-server process exchange real CUDA interprocess communication handles. Downloads must encounter a producer still pending on a non-default stream, wait for its event, copy the rotary tables and compare exact host bytes. Uploads begin from completed private host snapshots, allocate private device targets and compare their bytes after the actual copy stream drains.

Each direction has success, drained-error and undrained-error cases. Error injection occurs after a real copy submission. A failed drain must preserve both registration holds and all source/destination memory until a later physical drain succeeds. The tests supply the logical receiving identity explicitly; they do not yet exercise an ordered registration RPC through the public server.

The BF16 paged allocation has shape [2, 16, 4, 2, 8]; the FP32 rotary table is [64, 8], or 2,048 bytes. A synthetic sequence of 512 matrix multiplications on FP32 [2048, 2048] inputs keeps the download producer pending. This challenges event ordering; it is not a model or latency workload. The exporter remains alive through child cleanup. Actual device faults and exporter death are unqualified.

These copies use ordinary CUDA IPC and host/device transfers. They perform no DMA-BUF storage I/O. The successful copy gate does not imply that an imported mapping has closed: exporter teardown needs a separate exact-generation, server-owned acknowledgement.

24. What remains before one real shifted restore?

Multiprocess KMesh engine admission remains closed. An explicitly requested KMesh recovery profile must refuse an unsupported multiprocess connector before creating the engine. Ordinary multiprocess use without that profile is a separate path.

Ordered registration now passes its separate prerequisite gate: 316 CPU cases and six public-server CUDA cases on the same RTX 4090 runtime. The rotary table starts with invalid values. Its producer writes a scaled valid table on a non-default stream; the server receives the event while production is still pending, snapshots before normalization, uploads private normalized tables and publishes their completed generation. Independent byte readback passes, and later exporter writes do not change the private state. Both ZeroMQ and gRPC also pass disabled-admission and failed-copy/drain/retry controls.

The tests must create a fresh PyTorch export for each attempted import. Initial refusal/retry fixtures left outstanding IPC reference warnings despite passing test bodies; isolated controls identified unused and reused exports. The corrected six-case rerun passes, and the strict reproducer rejects that warning in the complete process-exit log. This fixes those fixtures; a general worker-side export cancellation or release acknowledgement is still unimplemented.

The server still needs truthful imported-mapping teardown, fenced storage publication and retrieval, and a worker consumer that preserves destination block ownership through completion.

The lower-level raw mapping primitive now passes three scoped CUDA cases. A failed native close preserves its mapping record and final reference, and new raw imports stay blocked while cleanup is uncertain. After an injected refusal before the driver call, later actual checked close succeeds. Retirement blocks new raw aliases while an existing alias remains readable until its own release. Each test uses a 64 MiB FP32 allocation with two interior views; exporters remain alive until their importing processes exit.

This inspection counts raw-wrapper imports. PyTorch storage, virtual-memory and external driver imports require their own lifetime guarantees. The checked primitive still needs integration with raw snapshot preparation and an exact server-generation release receipt. Retired handles remain recorded for the process lifetime. The three-case runner checks its full exit log and records CUDA Python bindings 13.4.4 and CuPy 14.2.0 in the measured environment.

The subsequent six-case native-outcome gate makes retry precise. A failure known to precede native close can be retried. If the driver call may have taken effect, its old pointer must not be submitted again: the address could have been reused. Unknown import, close or interrupted bookkeeping therefore stays quarantined until the importing process ends. Even an absent completed mapping record cannot establish that import never occurred. The tests verify that an ambiguous outcome causes no second native call.

Forwarded wrapper metadata also resets the receiving copy's local reference count. Closing that copy must preserve the sender's still-active alias. All six scoped cases pass with complete source and exit-log verification. Native errors are controlled injections before driver effects; these results qualify the conservative refusal policy, rather than actual device-fault recovery. The broader IPC regression suite separately passes seventeen cases. Service-level release receipts and the model/storage comparison remain subsequent gates.

Raw imports are now owned before their first mapping attempt. The later four-case CUDA gate passes exact downloaded bytes after a pending producer, refusal before checked cleanup, a submitted copy whose stream drain fails, and a partial second import combined with refused cleanup. Every incoming wrapper, buffer and both registration holds remain retained until actual drain and checked reference release succeed. The paired CPU profile passes 323 cases. A dedicated 64 MiB allocation holds the 2,048-byte rotary view, making its final mapping close independent of the paged allocation. These tests supply receiving identity explicitly; they do not qualify a raw control RPC or service retirement receipt. No model or DMA-BUF storage performance is measured.

The managed raw context now passes checked physical retirement. Nine separate-process CUDA cases cover successful repeated close, an outstanding alias, initialization and transfer drain refusal, refusal before checked close, ambiguous native close and partial construction. The parent retains a 64 MiB BF16 allocation with two nonoverlapping paged views filled with distinct values. Context-stream work must still be pending when close starts. Initialization uploads are drained on their original stream before publication; the transfer stream is drained separately before retiring and closing raw mappings.

All nine scoped cases and the paired 327-case CPU profile pass complete source and exit-log verification. Ten existing copy/ordered-registration CUDA cases also pass against this source. The primitive keeps failed construction alive until importer exit, rejects new aliases after retirement and returns the same released allocation identities on repeated success. It remains a resource primitive: typed managed registration, a service release receipt and model recovery are subsequent gates. Active GDS is refused because its current staging deregistration logs backend errors and cannot prove checked release. This result therefore qualifies no GPU-L1 or DMA-BUF storage shutdown.

A real shifted restore must then compare model outputs and repair the state whose deeper-layer contents depend on its original preceding context. Rotating key positions alone does not make that contextual dependence disappear. Numerical checks, deliberate-corruption rejection, fallback and physical drain must pass before a staged versus DMA-BUF serving comparison can qualify. The earlier exact-prefix retention result answers a different, already measured question.

Reproduce the completed prerequisite gates

Use the prepared environments and exact source pins described in the CPU ownership instructions and CUDA instructions. The public component branches are LMCache and vLLM. Select the profile's exact commit rather than a moving branch tip.

# CPU ownership and transfer controls: 292 required cases
make defconfig-kmesh-rotary-transfers-cpu
make kmesh-contracts-plan
KMESH_CONTRACTS_SOURCE=/path/to/pinned/LMCache \
  KMESH_CONTRACTS_VLLM_SOURCE=/path/to/pinned/vllm \
  KMESH_CONTRACTS_OUTPUT=/path/outside/checkouts/cpu-capture \
  KMESH_CONTRACTS_PY=/path/to/prepared/python make kmesh-contracts

# Native layouts: 32 required CUDA cases
make defconfig-kmesh-native-cuda
KMESH_NATIVE_SOURCE=/path/to/native-profile/LMCache \
  KMESH_NATIVE_OUTPUT=/path/outside/checkouts/native-capture \
  KMESH_NATIVE_PY=/path/to/prepared/python make kmesh-native

# Retained downloads and uploads: six required CUDA cases
make defconfig-kmesh-rotary-transfers-cuda
KMESH_NATIVE_SOURCE=/path/to/transfer-profile/LMCache \
  KMESH_NATIVE_OUTPUT=/path/outside/checkouts/transfer-capture \
  KMESH_NATIVE_PY=/path/to/prepared/python make kmesh-native

Every execution uses a fresh capture directory outside the checkouts. Saved-capture verification runs on CPU with the producing helper revision. Captured logs, raw receipts and tensors remain outside the public source tree. Receipt consistency does not independently authenticate hardware execution.

For the later ordered-registration gate, use LMCache 27e256e1aae7090c4ccfc5eea587a7fbf93fddae with the same pinned vLLM source. Regenerate its gRPC bindings as documented, then select make defconfig-kmesh-ordered-registration-cpu for 316 required CPU cases, or make defconfig-kmesh-ordered-registration-cuda for six required CUDA cases. Use the same corresponding make commands above and fresh external capture directories. These profiles also freeze the actual loaded wire schemas; the CUDA receipt hashes its complete exit log.

The checked raw-import gate uses LMCache cb31561f6877f16d50e74891d3dc9bf00f888532 and make defconfig-kmesh-raw-ipc-lifetime-cuda, followed by the same native runner commands with a fresh output directory. Its three required cases are distinct from the broader fourteen-case IPC regression suite, whose mixed PyTorch metadata fixtures still create an unused export. The scoped gate rejects outstanding exporter-reference warnings. It does not qualify actual driver faults, exporter death or a complete service teardown protocol.

For the later native-outcome rules, select make defconfig-kmesh-raw-ipc-outcomes-cuda and LMCache b08f4c339c73c23d2ba46b7e2c17e880c34a7b19. Run the same native commands into a fresh capture directory. This separate six-case profile preserves the earlier three-case checkpoint without relabeling its source or evidence.

Run the corresponding commands above into fresh external capture directories. The CPU profile requires 323 cases and the CUDA profile requires four, with the same complete-exit-log and source verification rules.

25. When can collective recovery be evaluated?

After one serial restore has passed the ownership and model gates. Collective recovery means several consumers coordinate reuse of compatible state, potentially across worker instances. It must retain each consumer's generation, destination and unfinished work, rather than treating a shared logical request as one physical completion.

First qualify the bounded single-worker path. Then extend its real storage, rotation and model-repair consumer to multiple instances and compare against independent serial restores. Rank barriers in the CPU registry do not establish GPU shard compatibility, collective execution or a throughput gain.
