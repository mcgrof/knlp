KMesh / Agent workloads

Questions 26–29

What does real agent traffic ask of shared state?

The earlier questions measured sharing, retention and early loading on request families we built. This page asks what released agent traces actually contain: how often one agent starts many children at once, what those children share, and how long large contexts sit idle. It also records why vLLM removed cascade attention, the shared-prefix attention method that wide request families would use.

26. Which agent traces can answer these questions?

Four released traces, and each answers a different part. None of them releases prompt text. Two release block identifiers: each request's prompt is cut into fixed-size blocks, and equal blocks get equal identifiers. Equal leading identifiers then stand in for a shared prefix. That is a workload intention, not a verified KV identity on any model.

The Copilot release accompanies Liu et al., Agentic Coding in the Wild, which studies a larger population of 13 million sessions. Its main observations for KMesh are that cache reuse is high inside a turn and much lower across turn boundaries, that model switches and context compaction invalidate reuse, and that users leave minutes-long idle gaps between turns. Our counts below come from the released days only.

One reading note for that release. An LLM call's timestamp marks the end of the call. In 81,519 consecutive call pairs, 99.94% fit that reading and 75% fit the start reading that the release's own analysis code uses. Read as start times, calls appear to overlap. Read as end times, two or more calls overlap in under 0.2% of turns, and four or more in 0.02–0.06%. Tool-batch timestamps do not agree with the call clock, so our turn times use model calls only.

27. Do agent launches fan out over a shared saved ancestor?

No. Wide launches exist, but their children share only the harness preamble. A launch is one parent step that starts one or more children; its width is the number of children. For each launch we compare the children's first requests. The group span is the prefix common to all of them. The preamble span is the part the first child also shares with a child of a different launch: the system prompt and tool definitions that every launch carries. The saved family ancestor is the part of the group span that existed before the launch and is not preamble. It is the state a storage read could serve to all children at once.

Wide launches are 2% of Weka launches, with 8% of its children, and 15% of FreeInference July launches. They are four to seven children wide. What the children share beyond the preamble is at most 2.4K tokens in Weka at 1 s grouping, 21.8K at 5 s and 5.3K in FreeInference, and all of it first appears at the launch. Storage holds no copy of state that was only just produced. Children also receive almost nothing from their parent: in Weka, 1,374 of 1,697 children share no leading block with the parent's last request, and the largest share is 9% of the child's prompt. No harness in either trace hands its children the parent's conversation.

The preamble can go cold, but the repeated reads are small

The preamble is specific to a session, not shared by every user of a harness. In FreeInference, where block identifiers are shared across the week, a child shares a median of only 144 tokens with children launched by other users. A session's preamble can therefore leave GPU memory between its launches. A wide launch would then read it back once per child, which is the case singleflight removes. 28. Where does long context sit idle?

Between turns. The resumed turn is the large storage target. In the Weka corpus we counted main-agent requests of at least 32K input tokens that arrive at least 60 s after the previous main-agent request ended. A resume counts as a subagent wait when a subagent was spawned inside the gap.

The user's own turn is about 23 times larger in total tokens, and it gives no notice.

About a fifth of all the prompt tokens this deployment recomputes belong to long-context turns that resume on the same model after five or more idle minutes. Storing a context at the end of a turn and restoring it when the next turn starts targets exactly those tokens. Unlike a subagent wait, the user's return gives no notice, and the gap runs from minutes to an hour, so the stored copy must stay in storage that long. A model switch (about 5% of turn boundaries) or a compaction (about 3%) invalidates a stored copy; the table excludes both.

These are client counts, not our engine. The cached fraction is the deployment's own label. The five-minute cliff matches a provider prompt-cache lifetime; it does not show what a local engine with storage would keep. Recomputed tokens are prompt tokens minus cached tokens, which is not the same as GPU time: longer prompts cost more per token.

29. What happened to cascade attention in vLLM?

vLLM removed it in October 2026, after it had been off by default since March. Cascade attention computes attention over a prefix shared by many requests once, computes each request's private part separately, and merges the results. Question 12 enabled it explicitly with an 8,192-token shared ancestor and 32 children: generation wall time fell 17.8%, and 24 of 96 continuations changed because the floating-point evaluation order changed.

Cascade attention in vLLM
DateChange
2025-11-21#25266 adds a rewritten GPU model runner. It never implements cascade.
2026-03-11#36318 turns cascade off by default "to avoid potential numerical issues by default". It changes only the configuration default.
2026-08-27#53183 makes the rewritten runner the default for all models.
2026-10-12#61126 removes cascade attention: kernels, heuristics, scheduler and KV-cache plumbing, runner logic, tests and documents. It first ships in v0.32.0. The disable_cascade_attn option remains as a no-op that is scheduled for removal.

The removal states its reason directly. Cascade attention "has been opt-in (disable_cascade_attn=True by default), already hard-disabled for FlashInfer (see #25679), force-disabled for async spec decode / DBO / batch invariance / CPU, and unsupported by most backends — yet it still costs a per-step scheduler scan, branches in the model runner and backends, and recurring bugs." Its tests check accuracy and identical outputs on a shared-prefix batch; it reports no performance comparison.

Why it reached so few batches

The engagement rule was strict. Before each step, the scheduler counted the leading KV blocks referenced by every request holding KV in the engine, not only the requests in the batch. One request without the prefix turned cascade off for the whole batch. The code's own comment notes that the count can be zero "even though all scheduled requests share a common prefix". There was one shared prefix per batch, with no support for several request groups that each share a different prefix. The reference count could also be wrong: issue #61673 reports a request decoded against another request's KV prefix while a CPU offload connector was in use.

Other serving stacks are in a similar place. SGLang's cascade kernel request, #1715, has been open since October 2024. TensorRT-LLM added a cascade kernel for beam-search decode in #14396, behind an environment variable that is off by default. The published gains come from batches built to share a prefix, beam or tree decoding, or a common system prompt: Hydragen, FlashInfer's cascade inference, Bifurcated Attention, DeFT and PAT. PAT groups requests by shared prefix as a vLLM plugin and reports 17–93% lower time per output token. We found no evaluation on Claude Code, Copilot or SWE-agent traffic.

Was it dropped because agent workloads have no use for it?

Partly, but that is not the stated cause. In order of evidence strength:

  1. Engineering scope. The rewritten runner never had cascade, and it became the default for all models. The removal cites maintenance cost against little reach. This is stated upstream.
  2. The engagement rule. The whole engine had to share one prefix, which mixed serving traffic rarely does. This is in the source.
  3. The workloads. The traces in questions 27 and 28 show agent launches four to seven wide that share a session preamble. Cascade pays when many concurrent decodes read one long prefix: reinforcement learning rollouts with many samples per prompt, best-of-n sampling, beam search and tree search. This is our inference from the traces and the published results.
  4. Numerics. Changed outputs explain the off-by-default change in March, not the removal.

The kernel still works where wide same-prefix groups exist, as question 12 measured. A return of cascade to vLLM would need a per-group design in the current runner and a workload with such groups. On this evidence, agent serving is not that workload.

What the evidence points to

In agent traffic, the KV cache worth saving is each session's own context between turns, not context shared between agents. KMesh's work moves to that resumed turn: which contexts to keep, in which memory tier and for how long, so that a resumed turn restores its context instead of computing it again. Singleflight stays in place for the rare wide launch; the traces give it little volume. Early preparation still matters for subagent waits, which come with seconds of notice, but they are a small share of the idle tokens. The overview lists what continues and what is parked.

These are workload counts, not KV measurements. Equal block identifiers are a workload intention. Weka's sampling removes the widest sessions, so a corpus of heavy parallel exploration, such as tree search or many-agent planners, could still contain wide launches over a large saved ancestor. FreeInference's family counts are small. Copilot's subagent behavior in its other editors is not in the public slice. The thresholds of 16K tokens, 60 s and 300 s are our choices, not measured break-even points.
