LMCache on NFS and pNFS: held descriptors and a faster NFS client

LMCache's native file connector opens, reads and closes a file for every KV-cache object it loads. On a network filesystem the open and the close are round trips to the server. We are evaluating a new option, held_fd_capacity, which keeps read-only descriptors of published objects open between loads, so a repeated read sends no metadata request at all. On a pNFS metadata server that does not grant delegations, this removes four server operations from every object read. On one small desktop host with one NVMe drive and no GPU in the data path, 16 test clients rose from 37,926 to 140,427 object reads per second, and close stalls of up to 3.3 seconds went away. On a local filesystem an open costs about a microsecond, so the gain there is small (4-5%).

What this is, and what it is not yet. These are measurements of the storage read path, taken by a test program that calls LMCache's native file connector directly. They are not yet a full vLLM integration test. One step closer to serving, we drove the same connector through the storage manager of LMCache's multiprocess (MP) server, the separate LMCache process that vLLM talks to, but without vLLM. There, on 256 KiB objects already in memory and an NFS server that keeps opens on the client, held descriptors gained only 2-5%: the storage manager spends about 27 µs per object, against about 2 µs for the open and close they remove. On a pNFS metadata server each open is a network round trip, so the saving there should be larger, but we have not measured it through the MP server yet. Three things remain to be done: a vLLM integration test through the MP server, scaling tests with higher-end NVMe drives and faster GPUs, and a production-grade pNFS network, with dedicated metadata and data servers, several data servers and many client hosts on real network links.

1. Test it on your mount

You need a Linux client with the NFS or pNFS mount you serve LMCache from, a C++ compiler, git, uv (or a Python that already has PyTorch, given in CONFIG_KNLP_RPL2_PNFS_PYTHON) and about 1.1 GiB free in a directory of that mount. The site profile runs as an ordinary user. It clones and builds LMCache's CPU extensions from the branch below, writes only into one subdirectory, rpl2-site, of the directory you give, and changes no mount, export or cache setting; delete that subdirectory to undo the run.

git clone https://github.com/mcgrof/knlp.git && cd knlp
make defconfig-rpl2-site
make RPL2P_ROOT=/disk/rpl2 RPL2_OUTPUT=$HOME/rpl2-records \
     RPL2_SITE=/mnt/pnfs/scratch

RPL2P_ROOT holds the LMCache build and must be on a local disk; RPL2_OUTPUT receives the records; RPL2_SITE is the directory on your mount. The run ends with site-summary.md, which sets your figures beside ours. Three defconfigs cover the cases:

3. What the option does

LMCache stores each KV-cache object as one file and publishes it with an atomic rename. The key names the object's content, so a published file never changes under its name. Without the option, every load opens the file, reads it and closes it. With held_fd_capacity set to a positive number, the connector keeps up to that many read-only file descriptors open. A load of a held object reads through its descriptor with pread, and the existence check for a held object needs no stat.

The descriptors live in a bounded cache, split into up to 16 shards by file name so readers of different objects do not share a lock. When the cache is full, the least recently used descriptor that no read is using is closed. A descriptor in use is never closed; when a delete through the adapter removes its entry, it is closed by its last reader. A read that fails or comes back short through a held descriptor drops it and tries once more with a fresh open, so a revoked or replaced file costs one retry, not a wrong answer. Readers that miss on the same file at the same time share one open: one of them opens it and the others wait for its descriptor, so the server sees one OPEN per file.

On NFS version 4, an open file is also an open state on the server. Each held descriptor therefore keeps one open state there, the same as any process that keeps a file open.

4. When it helps

The option removes the cost of an open and a close. How much that is depends on the filesystem and on what the server does with them.

pNFS, metadata server without delegations (Lattice)An OPEN and a CLOSE compound: four server operations (OPEN, CLOSE and two GETATTRs)No metadata-server operationServer load, round trips and the close stalls they cause

So the option matters most where every open goes to a metadata server, which is the usual case for pNFS and for many shared NFS deployments. It is safe but nearly pointless on a local disk.

5. What it assumes about your objects

A held descriptor keeps reading the file it opened, even after the name is removed or renamed over. That is correct because LMCache writes each object once, publishes it by rename and never rewrites it in place: the bytes a descriptor reads are always the bytes of its key. Eviction by another LMCache process or host is therefore safe. A descriptor keeps serving an object another process evicted until it leaves the cache, and the file's storage stays allocated until then.

The assumption breaks if something outside LMCache rewrites or replaces object files under the same names. In our fault tests a second client renamed a different file over a held name and unlinked another. The held arm kept serving the bytes it had admitted for the rest of the run in the first case, and for 3.1 seconds in the second, until the server returned ESTALE. Open per read would have followed the new name. Do not use held descriptors on a directory that other tools modify.

Within that rule we found no wrong byte: 155,494 verified 8 MiB reads over file replacement through LMCache, layout revocation, data-server and metadata-server restarts, a second client's rename and unlink, and a metadata-server partition past its lease. During a short metadata-server outage the held arm kept serving reads that the open-per-read arm could not start.

6. Configure it

Set the capacity in the fs_native L2 adapter. Size it for the hot set you want served without opens; each held descriptor costs one open file on the client and, on NFS version 4, one open state on the server.

--l2-adapter '{"type": "fs_native", "base_path": "/mnt/pnfs/lmcache/l2",
               "use_odirect": true, "held_fd_capacity": 4096}'

The default, 0, keeps the old behavior. Check the client's open-file limit (ulimit -n) and, for a large capacity, any per-client open-state limit of your NFS server.

7. Our measurements

All runs completed every request and every digest check. The pNFS lab is the one host described in the test system: the metadata server, the data server and every client share that host's CPU and memory bandwidth, so absolute rates describe this host. The per-read operation counts are protocol behavior and carry over to any deployment of this server and client.

Open per read reaches the server's ceiling at about four clients, after which throughput falls while latency keeps rising. Held descriptors send no operation after the first touch and scale until the shared host's CPU is the limit. With 8 MiB objects read directly from the data server, both arms become bandwidth-bound on this host, but open per read has close stalls of 0.86 to 3.3 s at p99 in every cell, and at one client reads 442 objects per second against 865 held.

One more finding concerns objects shared within one host. When a request names the same object twice and each read opens it, the client sends concurrent OPENs of one file. Lattice answers them with NFS4ERR_DELAY (148 times in 26 requests), the Linux client backs off at least 100 ms, and every request took about 108 ms. Held descriptors open each file once and avoid this.

Plain NFS and a local disk

Between two desktop hosts over 1 Gb/s, NFSv4.2 to a Linux server that grants read delegations, 256 KiB page-cache reads: no NFS operation reached the server in either arm. Held descriptors still raised throughput by 13%, 4% and 18% at 1, 4 and 16 reader processes, by removing the client's own open and close work. On local XFS the gain is 4.7%, 4.4% and 4.0% at 1, 4 and 16 readers, against a bound of 6.6% of cycles for open and close. Only 9% of that open and close cost is XFS's own code; the rest is the generic file open path. These local and plain-NFS figures use the sharded-cache revision of the option described above; the first revision's single cache lock made one local reader 6% slower.

9. Compare the three read modes

Once an object is in the page cache, reading it is a memory copy. LMCache's read pool hands each object to a worker thread, which costs a wakeup and a contended lock per object. A new adapter setting, read_mode, chooses who copies cached objects:

read_mode settings
SettingWho reads a cached objectWhat we measured
"pool" (default)A read worker, for every keyLowest latency for a lone request; most CPU per object
"inline"The worker that took the request, with preadv2(RWF_NOWAIT); only uncached keys go to the pool2-9 times less CPU per object; slower for a lone request, faster with several in flight
"adaptive"The pool while fewer than read_busy_target reads (default 16) are in flight, inline abovePool latency when idle; a request split between the two waits for the slower half
--l2-adapter '{"type": "fs_native", "base_path": "/mnt/pnfs/lmcache/l2",
               "held_fd_capacity": 4096, "read_mode": "inline"}'

The mode never changes which bytes are read, only who copies them. With use_odirect on, every read goes to the device, so every mode behaves as "pool". A filesystem that refuses RWF_NOWAIT also falls back to the pool after the first attempt: tmpfs refuses it, local XFS accepts it, and so far the Linux NFS client refuses it. On a Linux 7.3-rc2 client with an NFSv4.2 pNFS (flexible files) mount from the lab's Lattice server, a buffered preadv2(RWF_NOWAIT) fails with EOPNOTSUPP. The site profile's doctor step and the inline_unsupported counter in each read-mode record tell you which case you are in.

On NFS the three modes therefore behave the same. In that lab, two runs at 1, 4 and 16 requests in flight put every mode between 417,475 and 505,117 objects per second, with CPU per object within 9% of "pool" in each cell. A 15-second cell at 16 in flight sent 16 OPENs for the 16 objects in each mode.

An earlier build of the descriptor cache stalled here. It let readers that missed on the same file open it at the same time and kept one descriptor. At first touch the request workers' inline attempts and the read workers opened the same files at once. Lattice answers concurrent opens of one file from one client with NFS4ERR_DELAY, and the client's retry delay grows to seconds. At 16 requests in flight "inline" and "adaptive" fell to 7 and 14 objects per second, and one 15-second inline cell sent 95 OPENs and finished 17 requests. The cache now opens each file once at a time (section 1), and the same cell finishes 459,213 requests. On local XFS the crossover points depend on how many copies run at once and on your CPU's cache layout, so compare the modes at your own load; the results page has our numbers.

10. The NFS client change, and how to test it

Profiling plain NFSv4.2 opens showed a spin lock taking 10% of all cycles, under the client's state-owner code. A state owner is the NFSv4 identity a client opens files under, one per credential. Two locks are involved: the per-server clp->cl_lock, which every open to that server from the host takes to find its state owner, and the state owner's own so_lock, which every open and close under one credential takes.

Four Linux kernel commits address both locks and measure the result. They are on v7.3-rc7, on the kernel branch in section 2.

  1. selftests: filesystems: add an NFS open scaling test. nfs_open_scale opens and closes a set of small files under an NFS directory from a growing number of threads and reports opens per second at each thread count. By default the threads share one credential and so one state owner. -u gives each thread its own uid (it needs root), so the client-wide and the per-owner locks can be told apart; -r N cycles N uids per thread to stress owner lifetime. Usage: nfs_open_scale -d <dir on NFS> -t 1,2,4,8 -f 64 -s 4 [-u] [-r N] [-F], or the directory in NFS_OPEN_SCALE_DIR; -F allows a non-NFS directory for comparison.
  2. NFSv4: find an in-use state owner without taking cl_lock. The lookup walks the owner tree under RCU and takes a reference only on an owner already in use; idle owners still take the locked path. Owners are freed after an RCU grace period.
  3. NFSv4: do not scan the state owner LRU on every open. The idle-owner scan is skipped while the list is empty and otherwise runs at most once a second per server.
  4. NFSv4: protect the open counts with a per-state lock. Each open file's state gets its own lock for its open counts and mode, which the cached-open, open-stateid update and close paths took under the owner's so_lock. Opens of different files under one credential no longer share a lock. so_lock keeps protecting the owner's list of open files.

We measured them as an A/B on one 8-vCPU virtual machine, NFSv4.2 over loopback to a Linux server in the same machine with read delegations granted, so no OPEN reached the server after the first open of each file. Boots alternated between three kernels, two boots each, three runs per boot: the base (v7.3-rc7 with the selftest), commits 2 and 3, and all four commits.

With one shared credential, which is how an LMCache reader pool opens files, the per-state lock lifts opens per second 64% at 8 threads, and the slowest of its six runs (1.99 million) beats the fastest base run (1.48 million). Commits 2 and 3 alone give nothing in that case. Profiles show why: on the kernel with commits 2 and 3, 20.6% of cycles at 8 threads are in the spin lock slow path, nearly all of it on so_lock (nfs4_try_open_cached, nfs4_get_open_state, __nfs4_close, update_open_stateid). With all four commits the slow path drops out of the top three symbols; what remains is the list insert and delete of an open state, about 3% of cycles. With a credential per thread there is no shared owner, and commits 2 and 3 give most of the gain by taking cl_lock off the lookup.

A kernel with lock, RCU, memory and list debugging (lockdep, KASAN) ran owner churn, uid rotation, both credential modes and remounts with all four commits and reported nothing. Those runs open files only for read; opens for write and state recovery after a lease expiry are not yet tested.

Test it on a client with more cores. A shared lock costs more as cores grow, and our clients have 16. A site can run the same A/B on its own clients against its Lattice or NFS mount:

  1. Build two client kernels from the same base, one without and one with the four commits; build the selftest from the patched tree (make -C tools/testing/selftests TARGETS=filesystems/nfs) and use the same binary on both kernels.
  2. Boot the base kernel and run, on a directory of the mount used by nothing else, nfs_open_scale -d <dir> -t 1,2,4,8,16,32 -f 64 -s 4 three times, then the same as root with -u. The site profile's kernel step runs the first form when CONFIG_KNLP_RPL2_SITE_KERNEL_SELFTEST names the binary.
  3. Boot the patched kernel and repeat; alternate boots at least twice so each kernel has two boots.
  4. Record opens per second for each thread count and mode, the kernel release, the client's core count, whether the server grants read delegations, and one profile per kernel at the top thread count (perf record -g, then the callers of native_queued_spin_lock_slowpath).

Compare the shared-credential rows with ours. A gain that grows with cores in those rows says the change is worth more on large clients than on our 16-core hosts; the per-thread rows separate the client-wide lock from the per-owner one. The site profile's records and these runs are what we would like to see from other clients.

11. Limits

Our pNFS figures come from one metadata server and one data server on one host (the test system), with a small RonDB configuration, one NVMe drive and a remote client at 1 Gb/s. The many-client plateau describes that shared host; a dedicated metadata server saturates at a different rate, but it still sees four operations per read from every client that opens per read. The first read of an object still sends LOOKUP and OPEN. We did not measure layout recall storms, the server-side cost of many held open states, or a serving engine end to end, so none of these figures is a time-to-first-token result. The one measurement through LMCache's MP server used a Linux NFS server with read delegations and small cached objects, not pNFS. The kernel change is tested for opens for read only; opens for write and state recovery after a lease expiry are not yet tested.
