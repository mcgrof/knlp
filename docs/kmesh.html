Inference systems · Application-informed reuse

KMesh

Share one engine copy. Read it once. Prepare it early.

Related requests often need the same computed context. KMesh explores how an application can tell vLLM and LMCache which requests will reuse that state, when they will arrive and how long it should remain available.

Read the conclusions  ·  Explore the twenty-five questions

The idea: coordinate reuse around existing engine sharing

Imagine an agent reads a document and then launches four follow-up requests. Their common context is the ancestor; each follow-up adds private input and output. The model saves attention state for text it has processed; this is its key/value (KV) cache. vLLM runs the model, and its existing prefix cache can share that saved state when requests begin with the same tokens. LMCache stores state outside the engine, in host RAM or on storage. Singleflight makes one request restore a cold ancestor while matching followers wait and then adopt that copy.

Sharing inside the engine leaves another question: can the external cache serve later lookups without reading the SSD again? External retention keeps the restored objects in LMCache, in host RAM or an external GPU arena. Application notice can then move preparation before the follow-ups arrive. KMesh investigates this coordination and the lifetime of shared inference state.

Extending FlashInfer's cascade ideas to caching and offloading

KMesh applies the shared-prefix ideas behind FlashInfer's cascade attention to caching, offloading and restoration. Both organize work around a shared ancestor and its private branches. Cascade attention reuses shared-prefix KV reads across queries during decoding. It computes attention for their private suffixes separately, then merges the prefix and suffix results for each query.

The offload work carries that structure through the memory hierarchy: singleflight coordinates one restoration and shared engine copy; external retention keeps the external copy available for later lookups; advance preparation makes that shared state ready before the branches arrive. The common goal is to avoid repeating work for each branch at every layer. The attention and storage experiments measure these layers separately; their combined performance benefit remains unmeasured. See the cascade controls and retained early-loading comparison for the measured results.

What the results establish

External retention completed the read-once path while preserving the singleflight sharing that was already working. In the earlier preloading comparisons, singleflight was on and the children shared one ancestor inside vLLM. LMCache lookups could still trigger repeated SSD reads. Keeping the external copy removed that duplicated storage work.

Beyond a shared beginning: what if the same text moves?

The retention results above share an identical beginning of a prompt. A separate experiment asks whether four follow-ups can reuse saved state for the same text when each puts different instructions before it. Moving the text changes its position and preceding context, so copying the saved bytes alone is insufficient. Our TokenDance-style implementation extends LMCache's CacheBlend code: it supplies the shared segments and their positions, recalculates missing positions, and uses CacheBlend to select additional work before reusing the rest.

CacheBlend already supports non-prefix reuse. The TokenDance-style case adds an explicit group of related requests and identifies their shared text segments for KMesh. These tests compare our loading and coordination changes; they establish no advantage over stock CacheBlend's repair method.

We test loading 416 shared tokens through a separate cache process and running that same repair algorithm. The four follow-ups generate exactly the same tokens as when that extended TokenDance-style method runs inside the model process. Their saved attention state and next-token scores match bit for bit, both when finishing one follow-up at a time and when running one model layer, or computation stage, for all four follow-ups before advancing to the next layer. The group uses LMCache's cache in host RAM. Its failure test lets three follow-ups finish while the failed one cleans up and retries by recalculating its whole prompt.

A separate SSD comparison runs follow-ups one at a time. DMA-BUF, Linux's buffer-sharing interface, lets the SSD read directly into GPU memory instead of staging the read in host RAM. Read-call time falls by 3.7% across seven matched pairs, but complete restoration is faster in only four pairs. Checking the loaded data still copies it back to the CPU. This storage comparison has singleflight off and fixed retention on; it explicitly evicts the retained objects before every child to force fresh SSD reads. The earlier read-once experiment kept retention and singleflight on across the children. Combining this storage path with the group remains untested. The recovery page explains the setup and results from the beginning. These runs all use CacheBlend's selective recalculation; we have not shown here that it matches recalculating the entire prompt or improves serving speed.

Computing the corruption checksum on the GPU is a concrete next candidate: it could replace a 12 MiB payload copy back to the CPU with small digests. Overlapping independent SSD reads and GPU checks is another candidate. The recovery page explains what would need to change and how to evaluate it; neither optimization has been measured.

Papers

  • Cascade Inference: Memory Bandwidth Efficient Shared Prefix Batch Decoding
    Shared-prefix attention computation and merging with private suffixes. The post describes multi-level prefix hierarchies already implemented in MLC-Serving; KMesh explores coordination and future reuse around that computation.
  • DualPath: Breaking the Storage Bandwidth Bottleneck in Agentic LLM Inference
    Cross-turn temporal KV reuse in long-context, short-append agent trajectories, and a dual-path loading scheme that rebalances the resulting storage-bandwidth bottleneck.
  • TokenDance: Scaling Multi-Agent LLM Serving via Collective KV Cache Sharing
    Round-aware segment indexing, collective position-independent KV reuse, and Master–Mirror diff-aware storage for sibling agents in synchronized All-Gather rounds. The design KMesh reconstructs as its open baseline.
  • ForkKV: Scaling Multi-LoRA Agent Serving via Copy-on-Write Disaggregated KV Cache
    Fork-with-copy-on-write for multi-LoRA agents: a shared trunk plus lightweight per-agent divergence. The evidence that the shareable unit extends past the KV cache to adapter-affected state.
