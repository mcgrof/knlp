Inference systems · Agent context retention

KMesh

Keep what comes back. Restore it on demand.

Agents leave long contexts idle while they wait for a user or a tool, and then come back to them. KMesh studies how a serving system can keep the saved model state for those contexts, the key/value (KV) cache, and restore it when the agent resumes instead of computing it again. KMesh began as a study of state shared between related agents. Released agent traces show that such sharing carries little volume, and that each session's own context between turns carries much more. The research closed in November 2026.

KMesh is closed

We closed the KMesh research on November 23, 2026. It began with state shared between related agents. Released agent traces showed that such sharing carries little volume, and moved the question to each session's own context between turns. That question exposed a gap in how LMCache stores a resumed session, and the fix is now an upstream pull request. Two directions remain open. The outlook describes them: one is research, the other is integration.

Outlook: two directions

Both directions start from one observation: an agent's context waits on something outside the model, a tool or a user, and the serving system decides what to do with that context during the wait. The first direction is research, because no result answers it yet. The second is integration: the interfaces exist, and the work is to connect LMCache to them.

1. Use the tool-call wait (research)

When the model calls a tool, its session stops until the result comes back. The context up to the call is complete and already cached, but the resumed turn must still compute the result's tokens over that whole context before it can answer. The FreeInference agentic trace records how long these waits are. In both released weeks, 69–75% of tool-result tokens arrive after a wait of 1 s or more, and a quarter after 5 s or more. Calls to the file-read tool carry the largest share of result tokens.

Dynamo's speculative prefill already uses the end of a turn to warm the next turn's known prompt. The open question is what more a serving system can prepare during a tool wait, so that the resumed turn computes less after the result arrives, and whether that work still pays when other sessions share the GPU. KMesh has no result on it yet.

The wait runs from the end of the response that made the call to the start of the session's next request, so it includes the harness time around the tool. Calls made in one response share it. Token counts use the release's tokenizer, not a served model's. The trace scripts reproduce the table with tool_wait.py.

2. Execute kv.retain hints in LMCache (integration)

Serving engines now accept a typed, versioned kv_hints envelope on each request; vLLM merged it in September 2026 (vLLM #53423). Its proposed kv.retain action lets an orchestrator that knows the workflow name the token ranges a session will use again, each with a priority and a duration, so that the cache evicts other blocks first (vLLM #38514, open). This gives the retention question on this page to the party that can see the agent. The vLLM proposal applies the hint to vLLM's own GPU prefix cache. LMCache holds the same context in host memory and on storage, and it reads no KV hints today.

LMCache is a storage tier for vLLM and also plugs into SGLang's cache. A kv.retain reader in LMCache would let any of these producers keep a waiting session's context in host memory or on storage, not only in GPU memory. Dynamo is one user. llm-d, an agent runtime that sends its own hints, and a gateway that passes on a client's cache lifetime are others. The SGLang path also needs LMCache's SGLang integration to read the hints that SGLang now forwards. This page does not propose how LMCache should act on a hint.

A producer must also choose each hint's duration. The idle-context cost model compares the cost of keeping one context in host memory or on storage for 5 minutes to 72 hours with the cost of computing it again once, and uses the return times in the Copilot release to estimate how often the kept context is used. Its prices, speeds and return rates are editable assumptions, not measurements.

How KMesh moved from sharing to retention

The agent workloads page reads four released agent traces. Wide fan-out is rare in them. In a Claude Code corpus, launches of four or more children are 2% of all launches, and their children share only a preamble that belongs to one session. Long contexts sit idle between turns instead. In the same corpus, long main-agent requests that resume a minute or more after a user or tool wait carry 15.7% of the main agent's input tokens. In the GitHub Copilot release, long-context turns that resume on the same model after five or more idle minutes carry 17–19% of the prompt tokens the deployment recomputes. Their prompts are about 80K tokens at the median and about 165K at the 90th percentile, and the user's return gives no notice.

So the question changes from sharing to retention: which contexts to keep, in which memory tier and for how long, so that a resumed turn restores its context instead of computing it again. The parts we built for request families still apply to that question: singleflight, external retention, ownership of saved state across processes, and the SSD paths into GPU memory.

The first experiments: reuse inside a request family

Imagine an agent reads a document and then launches four follow-up requests. These related requests form a family. Their common context is the ancestor; each follow-up adds private input and output. The model saves attention state for text it has processed; this is its key/value (KV) cache. vLLM runs the model, and its existing prefix cache can share that saved state when requests begin with the same tokens. LMCache stores state outside the engine, in host RAM or on storage. Singleflight makes one request restore a cold ancestor while matching followers wait and then adopt that copy.

Sharing inside the engine leaves another question: can the external cache serve later lookups without reading the SSD again? External retention keeps the restored objects in LMCache, in host RAM or an external GPU arena. Application notice can then move preparation before the follow-ups arrive. The experiments below measure this coordination and the lifetime of shared inference state.

Cascade attention and family-aware offloading

FlashInfer's Cascade attention shares access to a common KV prefix while computing attention for several queries. It computes their private suffixes separately and merges the attention results. This reduces repeated GPU memory access inside the attention computation.

KMesh investigates the lifetime and movement of reusable state: which copy to retain, which requests can share a restoration, and when to prepare it. Cascade can consume shared KV after it becomes available; family-aware offloading can also coordinate artifacts with no attention computation at all. Family membership supplies reuse hints, while compatible object identity determines whether sharing is valid. The shared-ancestor structure connects these efforts, but their mechanisms have separate costs and correctness conditions. Their combined performance benefit remains unmeasured.

See the Cascade controls and retained early-loading comparison for the measured results.

vLLM removed cascade attention in v0.32.0, citing its maintenance cost against little reach. It engaged only when every request holding KV shared one prefix. Released agent traces also give it little to work with: launches of four or more children are uncommon, and their children share only a session preamble. The traces point instead to long contexts that sit idle between turns. The agent workloads page gives the trace sources, the counts and the upstream history.

Shared artifacts beyond KV cache

An agent family can share more than attention state. Several children may need the same retrieved documents, document embeddings, tool response, saved memory or execution record. The shared part can remain immutable while each child owns its changes. KMesh's broader goal is to coordinate the loading, retention and release of those artifacts through their existing storage and restoration interfaces.

Reuse depends on the artifact
ArtifactPossible shared workRequired boundary
KV cacheLoad compatible state once and reuse a shared prefix or repair a moved segment.Match model and layout; preserve ownership and completion. Changed preceding context can require model recomputation.
Document representations and saved model memoryReuse a document encoding, embedding or compatible saved context artifact.The producing model, version, format and consuming interface must agree. Each format needs its own restore validation.
Tool results, playbooks and execution recordsShare a valid result or immutable record instead of fetching or rebuilding it for every child.Respect input identity, version, freshness and access permissions. Reusing the record does not automatically reuse the model's work to read it.

The agentic cache-offloading model explores how richer artifacts, indexes and copies can grow the working set beyond RAM. It is a capacity projection, not a measurement of KMesh performance. Small plan templates can fit in memory; large shared artifacts create a different storage problem. KMesh should reuse the existing artifact loaders and coordinate with their development. CPU-consumed artifacts need an appropriate host-storage path; DMA-BUF is relevant where a qualified device-buffer path helps their actual consumer.

The first objective was to establish whether family information makes offloading more useful. A fair comparison keeps ordinary caching, the storage path, memory budget and output requirements fixed, then measures what changes when the cache knows which requests are related. Fewer reads are useful evidence, but completed agent work, waiting time, retained memory and displaced cache hits determine the tradeoff. The KV results below establish bounded benefits from retention and early preparation. They do not yet establish a general family-policy benefit or non-KV artifact support. The released traces answer the volume side of that question: family structure carries little of the idle context, so this work now comes after the resumed turn.

What the results establish

External retention completed the read-once path while preserving the singleflight sharing that was already working. In the earlier preloading comparisons, singleflight was on and the children shared one ancestor inside vLLM. LMCache lookups could still trigger repeated SSD reads. Keeping the external copy removed that duplicated storage work.

Reusing shared text at new prompt positions

The retention results above share an identical beginning of a prompt. A separate experiment asks whether four follow-ups can reuse saved state for the same text when each puts different instructions before it. Moving the text changes its position and preceding context, so copying the saved bytes alone is insufficient. Our TokenDance-style implementation extends LMCache's CacheBlend code: it supplies the shared segments and their positions, recalculates missing positions, and uses CacheBlend to select additional work before reusing the rest.

CacheBlend already supports non-prefix reuse. The TokenDance-style case adds an explicit group of related requests and identifies their shared text segments for KMesh. These tests compare our loading and coordination changes; they establish no advantage over stock CacheBlend's repair method.

We test loading 416 shared tokens through a separate cache process and running that same repair algorithm. The four follow-ups generate exactly the same tokens as when that extended TokenDance-style method runs inside the model process. Their saved attention state and next-token scores match bit for bit, both when finishing one follow-up at a time and when running one model layer, or computation stage, for all four follow-ups before advancing to the next layer. The group uses LMCache's cache in host RAM. Its failure test lets three follow-ups finish while the failed one cleans up and retries by recalculating its whole prompt.

A separate SSD comparison runs follow-ups one at a time. DMA-BUF, Linux's buffer-sharing interface, lets the SSD read directly into GPU memory instead of staging the read in host RAM. Read-call time falls by 3.7% across seven matched pairs, but complete restoration is faster in only four pairs. In that comparison, checking the loaded data still copies it back to the CPU. This storage comparison has singleflight off and fixed retention on; it explicitly evicts the retained objects before every child to force fresh SSD reads. The earlier read-once experiment kept retention and singleflight on across the children. Combining this storage path with the group remains untested. The recovery page explains the setup and results from the beginning. These runs all use CacheBlend's selective recalculation; we have not shown here that it matches recalculating the entire prompt or improves serving speed.

A follow-up keeps DMA-BUF reads fixed and computes the same SHA-256 checksum on the GPU. It returns 128 digest bytes per child instead of downloading the 12 MiB source payload for checking. Our tested CUDA kernel is much slower than CPU hashing, and complete restoration is slower in all seven matched pairs. Model outputs still match exactly. That experiment retains CPU hashing as its default; this result concerns one kernel and the existing whole-object format. The GPU checksum results and reproduction instructions give the measurements and the next optimization targets.

Papers

  • Cascade Inference: Memory Bandwidth Efficient Shared Prefix Batch Decoding
    Shared-prefix attention computation and merging with private suffixes. The post describes multi-level prefix hierarchies already implemented in MLC-Serving; KMesh explores coordination and future reuse around that computation.
  • Agentic Coding in the Wild: Characterizing GitHub Copilot Traces at Production Scale
    Production agent sessions: high cache reuse inside a turn, much lower reuse across turn boundaries, invalidation by model switches and compaction, and minutes-long user idle gaps. Its released traces supply the turn-resume counts on the workloads page.
  • PAT: Accelerating LLM Decoding via Prefix-Aware Attention with Resource Efficient Multi-Tile Kernel
    Groups decode requests by shared prefix inside one batch, as a vLLM plugin. It addresses the single-prefix limit of the removed cascade path.
  • DualPath: Breaking the Storage Bandwidth Bottleneck in Agentic LLM Inference
    Cross-turn temporal KV reuse in long-context, short-append agent trajectories, and a dual-path loading scheme that rebalances the resulting storage-bandwidth bottleneck.
  • TokenDance: Scaling Multi-Agent LLM Serving via Collective KV Cache Sharing
    Round-aware segment indexing, collective position-independent KV reuse, and Master–Mirror diff-aware storage for sibling agents in synchronized All-Gather rounds. The design KMesh reconstructs as its open baseline.
  • ForkKV: Scaling Multi-LoRA Agent Serving via Copy-on-Write Disaggregated KV Cache
    Fork-with-copy-on-write for multi-LoRA agents: a shared trunk plus lightweight per-agent divergence. The evidence that the shareable unit extends past the KV cache to adapter-affected state.
