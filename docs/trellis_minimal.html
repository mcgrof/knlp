Trellis Minimal: read the fast-memory update in code

scripts/trellis_minimal.py strips Trellis down to the mechanism that matters: a fixed-size memory is rewritten token by token with one tiny learning step. This page follows that file in execution order, explains every symbol and tensor shape, and spends extra time on the point that tends to eject readers from papers: why a Jacobian appears, what it means in the forward pass, and why backprop uses its transpose.

The map first

The entire mechanism in six arrows

$z_t=Mw_t$

The important conceptual split is between slow weights and fast state. The neural-network projections are ordinary learned parameters shared by every sequence. The matrix M is not a model parameter: it starts blank for each episode and changes while the sequence is being processed.

Connection to the surrounding family. The linear-attention and bounded-memory page develops DeltaNet and Gated DeltaNet. In this teaching script, setting phi = identity removes the nonlinear pullback and exposes the gated delta-rule form directly.

2. Follow _address()

An alias is one token-like event, but the tensor holds a sequence

def _address(self, aliases: torch.Tensor):
    h = self.encode(aliases)
    key = F.normalize(self.to_key(h), dim=-1).unsqueeze(1)
    alpha = self.to_alpha(h).unsqueeze(1)
    beta = 0.98 + 0.019 * torch.sigmoid(self.beta_raw)
    beta = beta.expand(aliases.shape[0], 1, aliases.shape[1], 1)
    return key, alpha, beta

If aliases has shape [B,T,32], then aliases[:, t, :] is one synthetic event. The call self.encode(aliases) processes all $T$ events in parallel because PyTorch linear layers operate on the final dimension. The code is not pretending that the whole sequence is one token.

F.normalize(..., dim=-1) L2-normalizes each produced address independently. It changes the vector's length to one while preserving its direction. This keeps address magnitude from secretly becoming another write-strength knob.

Why is it called key here but w later?

The names come from two abstraction levels. The router calls the alias-derived vector a key because that is its semantic role. The generic scan receives a whole sequence of vectors under the neutral name write. Inside the timestep loop, one member of that sequence is called w.

key[:, :, t, :] = write[:, :, t, :] = w_t    (key-memory pass)

The generic name matters because the same scan is reused for the value memory. There, write[:, :, t, :] is a normalized tool vector, not the alias key. Calling everything key inside the scan would make the second pass actively misleading. Naming is apparently allowed to have context, a rare mercy.

There are two sigmoids in the story

The sigmoid above produces the retention gate beta. Later, another torch.sigmoid(z) appears inside the derivative of SiLU. They have nothing to do with each other except that humanity reused the same function for two useful purposes.

3. The private per-event objective

Trellis writes by taking one gradient step

For one event, the teaching script uses the objective

$L_t(M)=\frac12\lVert\phi(Mw_t)-\alpha_t\rVert^2$

Read it literally: address memory with $w_t$, pass the resulting slot code through $\phi$, compare it with the desired target $\alpha_t$, and alter $M$ to reduce that error.

It helps to name the intermediate quantity

$z_t=Mw_t$

so the nested computation becomes

$M \rightarrow z=Mw \rightarrow y=\phi(z) \rightarrow L=\frac12\lVert y-\alpha\rVert^2$

Backpropagation simply walks this chain in reverse.

4. Jacobian without the intimidation tax

A Jacobian records how multiple inputs affect multiple outputs

For a scalar function, a derivative answers how one output changes when one input changes. For a vector function $\mathbf y=f(\mathbf x)$, every output may depend on every input. The Jacobian is just the table of those partial derivatives:

$J_{ij}=\frac{\partial y_i}{\partial x_j}$

That same matrix appears in two directions. This is worth learning because papers routinely write $J$ and then behave as though everyone spent childhood weekends differentiating vector functions.

Forward sensitivity
$\Delta\mathbf y\approx J\,\Delta\mathbf x$

A small change in the input is pushed forward through the local linear approximation.

Backward gradient
$\nabla_{\mathbf x}L=J^\top\nabla_{\mathbf y}L$

The loss gradient arriving from downstream is pulled backward to tell each input how it affects the loss.

The forward equation says what the function does to a perturbation. The backward equation asks the reverse bookkeeping question: given how the loss cares about each output, how much should it care about each input?

Backprop normally does not build the Jacobian. It needs the product $J^\top g$, where $g$ is the gradient arriving from the next operation. Automatic differentiation computes that vector-Jacobian product directly whenever it can. Materializing a giant Jacobian merely to multiply it would be mathematically valid and computationally ridiculous.
5. Why SiLU makes the Jacobian diagonal

The diagonal comes from elementwise use, not from the loss

In the minimal script, $\phi$ is SiLU applied independently to every coordinate:

$\phi(\mathbf z)=[\operatorname{SiLU}(z_1),\operatorname{SiLU}(z_2),\operatorname{SiLU}(z_3),\ldots]^\top$

Therefore output coordinate 1 does not depend on input coordinate 2. So $\partial y_1/\partial z_2=0$. Every cross-coordinate derivative is zero, which forces the Jacobian to be diagonal:

$J_\phi(\mathbf z)=\begin{bmatrix} \phi'(z_1)&0&0\\ 0&\phi'(z_2)&0\\ 0&0&\phi'(z_3) \end{bmatrix}$

This is an exact structural fact, not an approximation. A diagonal matrix also satisfies $J^\top=J$, but the bigger win is that multiplying by it is just elementwise multiplication:

$J_\phi(\mathbf z)^\top\mathbf g=\phi'(\mathbf z)\odot\mathbf g$

The loss still matters because it determines the incoming gradient $\mathbf g$. For Trellis's squared-error objective,

$\mathbf g=\nabla_yL=\phi(z)-\alpha$

so the full pullback becomes

$u=\nabla_zL=\phi'(z)\odot(\phi(z)-\alpha)$

A different loss could couple output coordinates and produce a very different $\nabla_yL$. SiLU's local Jacobian would still be diagonal because each SiLU output still depends on only one input coordinate.

6. Read error_code() one line at a time

The scary Jacobian expression becomes four cheap tensor operations

def error_code(z: torch.Tensor, alpha: torch.Tensor, phi: str):
    if phi == "identity":
        return z - alpha

    sig = torch.sigmoid(z)
    s = z * sig
    dsilu = sig + s * (1.0 - sig)
    return dsilu * (s - alpha)

SiLU is defined by

$\operatorname{SiLU}(z)=z\,\sigma(z)$

so sig = torch.sigmoid(z) is not a surprise extra mechanism. It is simply computing the $\sigma(z)$ already inside SiLU. Then s = z * sig is SiLU itself.

Using the product rule and $\sigma'(z)=\sigma(z)(1-\sigma(z))$ gives

$\operatorname{SiLU}'(z)=\sigma(z)+z\sigma(z)(1-\sigma(z))$

Because s = z * sig, the code can write that derivative as

dsilu = sig + s * (1.0 - sig)

The final line

return dsilu * (s - alpha)

is therefore the complete vector backpropagation operation

$J_{\operatorname{SiLU}}(z)^\top(\operatorname{SiLU}(z)-\alpha)$

without ever allocating $J$. The multiplication is a Hadamard or elementwise product, not a Kronecker product. The outer product arrives one step later.

7. Connect the Jacobian all the way back to memory

Backprop peels the nested loss from right to left

$L(M)=\frac12\lVert\operatorname{SiLU}(Mw)-\alpha\rVert^2$

There are three derivative steps:

1. Squared error: $\nabla_yL=y-\alpha$.
2. SiLU: $u=\nabla_zL=J_\phi(z)^\top(y-\alpha)$.
3. Matrix-vector product: $\nabla_ML=u w^\top$.

The last expression is an outer product. If $u$ has length $M$ and $w$ has length $D$, then $uw^\top$ has shape $M\times D$, exactly the shape of the memory matrix that must be updated.

$M\leftarrow\beta_tM-\gamma u_tw_t^\top$

So $u$ answers which slot-space outputs were wrong and in what direction? The vector $w$ answers at which address should that correction be written? Their outer product turns those two vectors into a structured matrix edit.

8. The recurrence in executable form

Five lines are the memory operator

for t in range(write.shape[2]):
    w = write[:, :, t, :]
    z = torch.einsum("bhmd,bhd->bhm", state, w)
    u = error_code(z, alpha[:, :, t, :], phi)
    update = torch.einsum("bhm,bhd->bhmd", u, w)
    state = beta[:, :, t, :].unsqueeze(-1) * state - g * update

z = state @ w asks what the current memory says at the event's address. error_code() computes $\partial L/\partial z$. The second einsum forms $uw^\top$. The last line applies retention and subtracts the gradient step.

The use of einsum is shape bookkeeping, not additional mathematics. Written for one batch item and one head, the same code is simply:

$z=Mw,\qquad u=\nabla_zL,\qquad \Delta M=uw^\top,\qquad M\leftarrow\beta M-\gamma\Delta M$
9. Remove one thing and Gated DeltaNet appears

Set $\phi$ to identity

If $\phi(z)=z$, then its derivative is one in every coordinate and its Jacobian is the identity matrix:

$J_\phi=I$

Therefore

$u=I^\top(z-\alpha)=z-\alpha=Mw-\alpha$

and the Trellis write becomes

$M\leftarrow\beta M-\gamma(Mw-\alpha)w^\top$

or, after moving the sign inside the residual,

$M\leftarrow\beta M+\gamma(\alpha-Mw)w^\top$

That is the gated delta-rule shape: decay the old state, predict the value at the key, measure the residual, and write that residual back along the key direction. The bounded-memory overview develops this lineage in more detail, while the least-squares lineage connects the same residual-driven update to the classical delta rule.

The useful mental jump: going from the identity control to the minimal Trellis write does not replace the recurrent-memory idea. It changes the error signal from a linear residual $z-\alpha$ to a nonlinear residual pulled backward through $\phi$.
10. Why the router owns two memories

Key memory finds the internal code; value memory reconstructs the tool

key_state, _ = trellis_scan(
    key, alpha, beta, gamma, self.phi, key_state
)
value_state, _ = trellis_scan(
    value, alpha, beta, gamma, self.phi, value_state
)

Both memories learn against the same target code $\alpha$. The key memory is written by alias-derived address vectors. The value memory is written by tool vectors. Sharing the target code creates an internal bridge between them.

alias $\rightarrow$ key memory $\rightarrow$ slot code $\rightarrow f \rightarrow$ value memory $\rightarrow$ tool vector

The query path makes that explicit:

code = torch.einsum("bhmd,bhqd->bhqm", key_state, query)
code = F.silu(code)
code = code - code.mean(-1, keepdim=True)
code = code / (code.std(-1, keepdim=True, unbiased=False) + 1e-6)

got = torch.einsum("bhmd,bhqm->bhqd", value_state, code)
got = F.normalize(got, dim=-1).squeeze(1)
logits = got @ self._tool_bank().T

This second use of F.silu is part of the read map $f$. Do not confuse it with error_code(), where the SiLU derivative is written manually because that function constructs the inner learning signal.

11. Why random aliases make the example educational

The slow weights can learn the protocol, not the episode

make_episode() draws fresh normalized 32-dimensional aliases every time. Since a particular alias is not a persistent vocabulary item, the ordinary model parameters cannot memorize that alias A means calculator. The binding must live in the fast state created for this episode.

state = model.blank_state(batch, aliases.device, aliases.dtype)
state = model.bind(state, aliases, tools)
logits_before = model.query(state, aliases)

state = model.bind(
    state,
    aliases[rows, index].unsqueeze(1),
    new.unsqueeze(1),
)
logits_after = model.query(state, aliases)

The overwrite is the sharp test. A memory that only accumulates associations can keep returning the stale tool. The residual-driven update must suppress the old association enough for the replacement to win. This is why the example is more informative than a one-shot store-and-read demo.

12. Why the nonlinear write changes parallelization

Exact sequential semantics are cheap to understand, harder to batch

With identity $\phi$, the state update is affine in the current memory. A sequence of such updates has enough algebraic structure to be blocked into chunkwise matrix operations. The WY/UT page explains why products of rank-one transformations can be reorganized into GPU-friendly blocks.

With nonlinear $\phi$, the current error code depends nonlinearly on the current state:

$u_t=J_\phi(M_tw_t)^\top(\phi(M_tw_t)-\alpha_t)$

The exact next update therefore depends on the result of the previous update in a way that no longer closes into the same simple affine chunk rule. The minimal file intentionally implements the exact token-by-token recurrence. The production path can trade exact within-chunk state freshness for parallel work; that is a systems approximation, not a mysterious new memory mechanism.

The one equation worth remembering. Trellis's inner write is ordinary backprop applied to a tiny request-local loss: $M\rightarrow Mw\rightarrow\phi(Mw)\rightarrow\frac12\lVert\phi(Mw)-\alpha\rVert^2$. The Jacobian is not decoration added by the paper. It is what naturally appears when a vector-valued nonlinear function sits inside a loss and we differentiate through it.
