Trellis from the teaching script

Trellis Minimal: read the fast-memory update in code

scripts/trellis_minimal.py turns the Trellis memory operator into a small episodic alias-to-tool problem. This page follows the actual call path: generate one episode, create the two fast memories, turn aliases into learned codes, bind aliases to tools, and only then enter the Trellis recurrence and its gradient.

1. Generate one episode

Random vectors are aliases; random integers are tool identities

The teaching task needs two different kinds of random data. An alias is deliberately an arbitrary continuous vector that should have no meaning outside the current episode. A tool is one member of a fixed discrete set such as calculator, shell, or SQL runner. That is why the function uses torch.randn() for aliases and torch.randint() for tools.

def make_episode(batch: int, n_bindings: int, n_tools: int, gen, device):
    aliases = F.normalize(
        torch.randn(batch, n_bindings, 32, generator=gen),
        dim=-1,
    )
    tools = torch.randint(
        0, n_tools, (batch, n_bindings), generator=gen
    )

    index = torch.randint(0, n_bindings, (batch,), generator=gen)
    old = tools[torch.arange(batch), index]
    new = torch.randint(0, n_tools - 1, (batch,), generator=gen)
    new = new + (new >= old).long()

    return (
        aliases.to(device),
        tools.to(device),
        index.to(device),
        new.to(device),
    )
ArgumentMeaning
batchHow many independent episodes are generated together.
n_bindingsHow many alias-to-tool pairs each episode initially contains. This becomes the sequence length T for the initial bind.
n_toolsHow many discrete tool identities exist. Tool IDs are integers from 0 through n_tools - 1.
genA PyTorch random generator. Supplying the same seeded generator makes the random episode stream reproducible.
deviceWhere the returned tensors should live, for example CPU or GPU. The function generates them, then moves them with .to(device).

Why torch.randn(batch, n_bindings, 32)?

torch.randn() draws continuous values from a standard normal distribution. Its three dimensions are [B,T,32]: B episodes, T bindings per episode, and 32 coordinates per alias. F.normalize(..., dim=-1) then rescales every 32-dimensional alias to unit length. The direction is random; the magnitude is fixed.

Be precise about the indexing. aliases[b, t, :] is one 32-dimensional alias in one episode. aliases[:, t, :] is not one alias: it is the whole batch of B aliases at binding position t, with shape [B,32]. The batched Trellis code processes those B independent episodes together.

Why torch.randint() for tools?

A tool is a category, not a random point in continuous space. torch.randint(0, n_tools, (batch, n_bindings)) therefore produces integer IDs with shape [B,T]. Later, nn.Embedding turns each integer tool ID into a learned 32-dimensional tool vector.

The remaining random integers create the overwrite test. index chooses which binding in each episode will be replaced. old retrieves its current tool ID. new is sampled from only n_tools - 1 possibilities and shifted upward whenever it would collide with old. That little arithmetic guarantees the replacement tool differs from the old one.

Call path. make_episode() returns aliases and tools. run_episode() passes both whole tensors to model.bind(state, aliases, tools). There is no hidden conversion from one alias into a sequence; the T dimension already is the list of bindings in the episode.
2. Create the two fast memories

blank_state() returns key_state and value_state

MiniRouter has ordinary learned parameters that persist across episodes: the alias encoder, projections, tool embedding table, the inner step size, and the retention parameter. The episode-specific information is different. It lives in two fast-memory matrices that are created as zeros for every new episode.

def blank_state(self, batch: int, device, dtype):
    shape = (batch, 1, self.n_slots, self.d_head)
    zeros = torch.zeros(shape, device=device, dtype=dtype)
    return zeros, zeros.clone()

# Later, bind() gives the two returned matrices their names:
key_state, value_state = state

The two tensors have the same shape, [B,1,n_slots,d_head], but they do different jobs.

Fast stateWhat it learns during this episode
key_stateTakes an alias-derived address and is trained to produce an internal slot-space code for that alias.
value_stateTakes the vector for the tool bound to that alias and is trained toward the same internal slot-space code. During query, this relationship is used in the reverse direction to reconstruct the tool vector.
alias-derived vector → key_state → shared internal code
tool vector → value_state → same shared internal code

The shared internal code is named alpha in the script. The next section shows where it comes from. At this point the important fact is simply that the router keeps two separate mutable matrices, not one vague thing called “state.”

3. Decode _address() line by line

It produces an address, a target code, and a retention factor

def _address(self, aliases: torch.Tensor):
    h = self.encode(aliases)
    key = F.normalize(self.to_key(h), dim=-1).unsqueeze(1)
    alpha = self.to_alpha(h).unsqueeze(1)
    beta = 0.98 + 0.019 * torch.sigmoid(self.beta_raw)
    beta = beta.expand(aliases.shape[0], 1, aliases.shape[1], 1)
    return key, alpha, beta

No Trellis memory is read or updated in this function. _address() only runs the persistent learned network on each alias and prepares three tensors that a later memory update will use.

h = self.encode(aliases)

The input has shape [B,T,32]. The encoder is a small ordinary neural network whose linear layers operate on the final dimension, so it applies the same learned transformation independently to every aliases[b,t,:]. With d_model = 64, h has shape [B,T,64]. It is simply the hidden representation of each alias. It is not fast memory.

key = F.normalize(self.to_key(h), dim=-1).unsqueeze(1)

to_key projects each 64-dimensional hidden alias to a d_head = 32 vector. Normalization gives it unit L2 norm. This vector will later become the address or write direction used with key_state. unsqueeze(1) inserts the one-head dimension, changing [B,T,32] into [B,1,T,32].

alpha = self.to_alpha(h).unsqueeze(1)

alpha is not the current result stored at the key. It is a target produced directly from the alias hidden representation by the persistent learned projection to_alpha. With n_slots = 32, its shape is [B,1,T,32].

The current memory result does not exist until the later Trellis recurrence computes z = M w. That distinction is central:

αt = desired slot-space code
zt = what the current fast memory actually returns
error = compare φ(zt) with αt

Both fast memories are trained toward the same alpha for a binding. The alias-derived key is associated with that code in key_state; the bound tool vector is associated with that same code in value_state. That shared target is what links the two memories.

beta = 0.98 + 0.019 * torch.sigmoid(self.beta_raw)

beta_raw is one trainable scalar. A sigmoid maps any real number into the interval (0,1). Multiplying by 0.019 gives (0,0.019); adding 0.98 pins beta to the high-retention interval (0.98,0.999).

sigmoid(beta_raw) in (0, 1)
0.019 × sigmoid(beta_raw) in (0, 0.019)
beta in (0.98, 0.999)

The parameter starts at zero, so sigmoid(0) = 0.5 and the initial beta is 0.9895. Later the state update multiplies old memory by beta before applying the new write. A beta near one therefore retains most of the old memory; a smaller beta forgets more.

The constants 0.98 and 0.019 are not derived in this teaching file from some theorem. The source comment states the intent: this minimal router pins one learned scalar into a high-retention band, while the full model predicts beta per token.

beta.expand(B, 1, T, 1)

The teaching router has only one learned beta scalar. expand() broadcasts that same value across every episode and every binding position so its tensor shape matches what the recurrence expects. It does not create a different learned beta for every t.

Stop here before reading the recurrence. After _address(), we have only prepared key, alpha, and beta. Nothing has yet been written to key_state or value_state.
4. Bind aliases to tools

bind() is where the two memories and trellis_scan() finally meet

def bind(self, state, aliases, tool_ids):
    key_state, value_state = state
    key, alpha, beta = self._address(aliases)
    value = self._tool_bank()[tool_ids].unsqueeze(1)
    gamma = F.softplus(self.gamma_raw)

    key_state, _ = trellis_scan(
        key, alpha, beta, gamma, self.phi, key_state
    )
    value_state, _ = trellis_scan(
        value, alpha, beta, gamma, self.phi, value_state
    )
    return key_state, value_state

The first line finally names the two zero matrices created by blank_state(). The second line prepares alias-derived key, alpha, and beta. The third line looks up each integer tool_id in the learned embedding table and normalizes it, producing the continuous tool vector called value.

gamma is the positive inner learning rate. The script stores an unconstrained gamma_raw and applies softplus so gamma cannot become negative. Its initializer is chosen so the initial gamma is 0.05.

Now the word write has a reason to exist

trellis_scan() is generic. Its first argument is named write because the same recurrence is used with two different kinds of vectors. In the first call, write is key. In the second call, write is value.

Callwrite meansState being updated
first scanalias-derived keykey_state
second scantool embedding valuevalue_state

Inside trellis_scan(), the loop eventually selects one timestep with w = write[:, :, t, :]. So w_t is not a third mysterious object. It means “the current vector from whichever write sequence this scan received.” For the key-state scan, w_t = key_t. For the value-state scan, w_t = value_t.

keyt → key_state, target αt
valuet → value_state, same target αt
5. Read one Trellis write as a tiny learning problem

The current memory response is z; alpha is the target

Now enter one call to trellis_scan(). For event t, the scan takes the current write vector wt and asks the current memory matrix what it returns at that direction:

zt = M wt

The private objective for that event asks the transformed current response to match the precomputed target code:

Lt(M) = ½ ‖φ(M wt) − αt‖2
M → z = Mw → φ(z) → compare with α → squared error

This is ordinary gradient descent used inside sequence processing. The model does not launch a separate optimizer object for every token; the recurrence writes this derivative directly and takes one step on the fast state.

6. Jacobian review and application in Trellis

The Jacobian is the local dependency table used by backpropagation

A scalar derivative describes how one output changes with one input. Here φ maps a vector z to another vector y = φ(z). A change in one coordinate of z can, in general, affect several coordinates of y. The Jacobian records those local dependencies:

Jij = ∂yi / ∂zj

Row i asks about output coordinate yi. Column j asks about input coordinate zj. If yi does not depend on zj, that entry is zero.

Backpropagation arrives at φ with a gradient telling us how the loss changes with each output coordinate:

∇yL

To continue backward, the multivariable chain rule maps that gradient to the inputs of φ:

∇zL = Jφ(z)T ∇yL

That is the vector version of ordinary chain-rule bookkeeping: given how the loss reacts to each output of φ, determine how much it reacts to each input coordinate.

Backprop needs the product, not the full matrix. Frameworks normally compute JTg directly. They do not materialize the entire Jacobian unless a program explicitly asks for it.
7. Apply the Jacobian to SiLU

Elementwise SiLU makes the local Jacobian diagonal

In the minimal script, φ applies SiLU independently to each coordinate:

φ(z) = [SiLU(z1), SiLU(z2), SiLU(z3), ...]T

Output coordinate 1 depends on z1, but not on z2 or z3. The cross-coordinate derivatives are therefore zero:

∂φ(zi) / ∂zj = 0    for i ≠ j

The Jacobian is diagonal:

Jφ(z) = diag(φ′(z1), φ′(z2), ...)

A diagonal matrix equals its transpose, but the more useful fact is that multiplying by it becomes elementwise multiplication:

Jφ(z)T g = φ′(z) ⊙ g

For the squared-error objective, the gradient arriving from the loss is:

∇yL = y − α = φ(z) − α

Therefore Trellis needs:

u = ∇zL = φ′(z) ⊙ (φ(z) − α)

The diagonal structure comes from applying SiLU independently by coordinate. The squared-error loss supplies the incoming residual. Those are separate facts that combine in the final gradient.

8. Match the equation to error_code()

The code writes the SiLU derivative and the VJP explicitly

def error_code(z, alpha, phi):
    if phi == "identity":
        return z - alpha

    sig = torch.sigmoid(z)
    s = z * sig
    dsilu = sig + s * (1.0 - sig)
    return dsilu * (s - alpha)

The sigmoid on this path appears because SiLU itself is SiLU(z) = z σ(z). It is unrelated to the sigmoid used earlier to constrain beta.

SiLU′(z) = σ(z) + z σ(z)(1 − σ(z))

In the code, s = z * sig, so sig + s * (1 - sig) is exactly that derivative. The return statement is:

dsilu * (s - alpha)  =  φ′(z) ⊙ (φ(z) − α)  =  Jφ(z)T(φ(z) − α)

The script avoids constructing a square Jacobian because the elementwise activation tells us in advance that only its diagonal can be nonzero.

9. Continue back through z = M w

The gradient with respect to memory is an outer product

We now have u = ∂L / ∂z. The previous operation was z = Mw. Differentiating that operation with respect to the memory matrix gives:

∇ML = u wT

If u has S coordinates and w has D coordinates, then u wT has shape S × D, exactly the shape of one memory matrix.

NotationOperation here
a ⊙ bHadamard or elementwise multiplication.
u wTOuter product; produces the memory gradient matrix.
A ⊗ BKronecker product; not used in this step.
10. Read the full recurrence in trellis_scan()

Predict, compute the error code, form the outer product, update memory

for t in range(write.shape[2]):
    w = write[:, :, t, :]
    z = torch.einsum("bhmd,bhd->bhm", state, w)
    u = error_code(z, alpha[:, :, t, :], phi)
    update = torch.einsum("bhm,bhd->bhmd", u, w)
    state = beta[:, :, t, :].unsqueeze(-1) * state - g * update

For one batch item and one head, the same code is:

zt = Mt−1wt
ut = ∇ztLt
∇MLt = utwtT
Mt = βtMt−1 − γutwtT

The first line asks what the current memory says at this write direction. The second computes how that answer should change. The third lifts that error into a matrix-shaped gradient. The fourth retains a beta fraction of the previous state and takes one gradient step.

11. Query the two memories

Alias to key memory to shared code to value memory to tool

def query(self, state, aliases):
    key_state, value_state = state
    query, _, _ = self._address(aliases)

    code = torch.einsum("bhmd,bhqd->bhqm", key_state, query)
    code = F.silu(code)
    code = code - code.mean(-1, keepdim=True)
    code = code / (
        code.std(-1, keepdim=True, unbiased=False) + 1e-6
    )

    got = torch.einsum("bhmd,bhqm->bhqd", value_state, code)
    got = F.normalize(got, dim=-1).squeeze(1)
    logits = got @ self._tool_bank().T
    return logits * self.logit_scale.exp().clamp(1.0, 100.0)

The query alias goes through _address() again, but only the alias-derived key is used. Reading key_state with that key produces the slot-space code. The fixed read map applies SiLU and standardization. The resulting code then reads value_state in the transpose direction, producing a 32-dimensional vector that should point toward the bound tool embedding.

alias → query key → key_state → code → value_state → reconstructed tool vector → tool logits

The final matrix multiply compares the reconstructed vector with every normalized tool embedding. The largest logit is the predicted tool ID.

12. Follow bind, query, overwrite, query

The overwrite tests whether fast memory can correct an old association

state = model.blank_state(batch, aliases.device, aliases.dtype)
state = model.bind(state, aliases, tools)
logits_before = model.query(state, aliases)

state = model.bind(
    state,
    aliases[rows, index].unsqueeze(1),
    new.unsqueeze(1),
)
logits_after = model.query(state, aliases)

A memory that merely accumulates associations can keep returning a stale value after an overwrite. Trellis first computes z = Mw, so the update depends on what is already stored. The error against the new target can therefore correct an old association rather than blindly add another one.

13. Recover Gated DeltaNet by removing the nonlinearity

Set phi = identity and the Jacobian becomes the identity

If φ(z) = z, then Jφ = I. The error code becomes:

u = z − α = Mw − α

The Trellis write becomes:

M ← βM − γ(Mw − α)wT

Move the sign into the residual:

M ← βM + γ(α − Mw)wT

That is the gated delta-rule form: retain the old state, predict what is stored at the current address, compute the residual, then write that residual back along the address direction. The linear-attention page develops DeltaNet and Gated DeltaNet in the broader architecture context.

14. Connect the nonlinear write to implementation cost

State-dependent nonlinear writes break the exact affine chunking shortcut

With identity φ, the update is affine in the current state. A sequence of such rank-one updates can be reorganized into chunkwise matrix operations. The WY/UT page explains the algebraic machinery behind that kind of blocking.

With nonlinear φ, the next error code depends nonlinearly on the state produced by earlier writes:

ut = Jφ(Mt−1wt)T (φ(Mt−1wt) − αt)

The exact recurrence is therefore naturally sequential. The minimal script implements that exact token-by-token rule. A production chunked path can freeze or approximate within-chunk state to recover larger matrix operations, but that is an implementation tradeoff layered on top of the same memory objective.
