Trellis Minimal: read the fast-memory update in code

scripts/trellis_minimal.py turns the Trellis memory operator into a small episodic key-value problem. This page follows that program from the task it solves, through the tensors it constructs, to the gradient step that rewrites memory. The notation is introduced only when the code needs it.

1. Start with the task

The program learns how to bind an alias to a tool inside one episode

The toy problem is an in-context key-value store. Each episode creates fresh random 32-dimensional aliases and assigns them to a small set of tools. The model must remember those bindings, answer queries, then replace one binding when the episode says that it changed.

bind: alias A → calculator
bind: alias B → sql-runner
query: alias A → calculator
overwrite: alias A → shell
query: alias A → shell

The aliases are freshly sampled every episode. Slow model weights cannot memorize that a particular alias means a particular tool because that alias does not persist across training examples. The slow weights can only learn the protocol for storing and retrieving a binding. The episode-specific binding must live in fast memory.

def make_episode(batch, n_bindings, n_tools, gen, device):
    aliases = F.normalize(
        torch.randn(batch, n_bindings, 32, generator=gen),
        dim=-1,
    )
    tools = torch.randint(
        0, n_tools, (batch, n_bindings), generator=gen
    )
    ...
Keep this picture in mind. One aliases[:, t, :] vector is one synthetic event identifier. The plural tensor aliases holds the batch of episode bindings.
2. Separate slow weights from fast state

The neural network learns how to use memory; M stores this episode

MiniRouter contains ordinary learned parameters: an encoder, projections, tool embeddings, a step size, and a retention gate. Those parameters survive from one sequence to the next. The two Trellis state matrices do not. They start at zero for a new episode and are rewritten by the bindings in that episode.

def blank_state(self, batch: int, device, dtype):
    shape = (batch, 1, self.n_slots, self.d_head)
    zeros = torch.zeros(shape, device=device, dtype=dtype)
    return zeros, zeros.clone()

For one memory head, call the fast state M. In the script its shape is [B,H,S,D]: batch, head, memory-slot coordinate, and write-vector coordinate.

3. Turn each alias into a write address and target

Follow _address() after the task is clear

def _address(self, aliases: torch.Tensor):
    h = self.encode(aliases)
    key = F.normalize(self.to_key(h), dim=-1).unsqueeze(1)
    alpha = self.to_alpha(h).unsqueeze(1)
    beta = 0.98 + 0.019 * torch.sigmoid(self.beta_raw)
    beta = beta.expand(
        aliases.shape[0], 1, aliases.shape[1], 1
    )
    return key, alpha, beta

If aliases has shape [B,T,32], the encoder runs over all T aliases in parallel. Each aliases[:, t, :] is still one event. PyTorch linear layers apply the same learned map to the final dimension at every batch and sequence position.

to_key(h) produces the vector that tells memory where to write. F.normalize(..., dim=-1) gives each address unit L2 norm, so direction carries the address information without magnitude becoming another uncontrolled write-strength parameter.

to_alpha(h) produces the target code memory should return at that address. The learned beta_raw is passed through sigmoid only to keep the retention factor in a controlled range.

key, write, and w are three names along one call path

In the key-memory pass, _address() calls the alias-derived vector key because that is its semantic role. trellis_scan() is generic, so its argument is called write. Inside the timestep loop, one vector from that sequence is called w.

key[:, :, t, :] = write[:, :, t, :] = wt    in the key-memory pass

The neutral name write is necessary because the same scan is used for the value-memory pass, where the write vector is a normalized tool embedding rather than an alias-derived key.

4. Read the Trellis write as a tiny learning problem

Each event asks memory to reduce one squared-error objective

For event t, Trellis addresses the current state with wt:

zt = M wt

Memory is trained, for this event, to make the transformed response φ(zt) match the target code αt:

Lt(M) = ½ ‖φ(M wt) − αt‖2

This is ordinary gradient descent used inside sequence processing. The model does not run a separate optimizer object. It writes out the derivative of this small objective directly and takes one step on M.

M → z = Mw → φ(z) → ½ ‖φ(z) − α‖2
5. Jacobian review and application in Trellis

The Jacobian is the local dependency table used by backpropagation

A scalar derivative describes how one output changes with one input. Here φ maps a vector z to another vector y = φ(z). A change in one coordinate of z can, in general, affect several coordinates of y. The Jacobian records those local dependencies:

Jij = ∂yi / ∂zj

Row i asks about output coordinate yi. Column j asks about input coordinate zj. If yi does not depend on zj, that entry is zero.

Backpropagation arrives at φ with a gradient telling us how the loss changes with each output coordinate:

∇yL

To continue backward, we need the gradient with respect to the inputs of φ. The multivariable chain rule gives:

∇zL = Jφ(z)T ∇yL

This is the vector form of the same chain rule used in a scalar computation. Given how the loss reacts to each output of φ, the Jacobian transpose maps that signal back to each input coordinate.

Backprop needs the product, not the matrix. Frameworks normally compute JTg directly. They do not materialize the full Jacobian unless a program explicitly asks for it.
6. Apply the Jacobian to SiLU

Elementwise SiLU makes the local Jacobian diagonal

In the minimal script, φ applies SiLU independently to each coordinate:

φ(z) = [SiLU(z1), SiLU(z2), SiLU(z3), ...]T

Output coordinate 1 depends on z1, but not on z2 or z3. The cross-coordinate derivatives are therefore zero:

∂φ(zi) / ∂zj = 0    for i ≠ j

The Jacobian is diagonal:

Jφ(z) = diag(φ′(z1), φ′(z2), ...)

A diagonal matrix is equal to its transpose, but the more useful fact is that multiplying by a diagonal matrix is just elementwise multiplication:

Jφ(z)T g = φ′(z) ⊙ g

For the squared-error objective above, the gradient arriving from the loss is:

∇yL = y − α = φ(z) − α

Therefore Trellis needs:

u = ∇zL = φ′(z) ⊙ (φ(z) − α)

The diagonal structure comes from applying SiLU independently by coordinate. The squared-error loss determines the incoming residual. Those are separate facts that combine in the final gradient.

7. Match the equation to error_code()

The code writes the SiLU derivative and the VJP explicitly

def error_code(z, alpha, phi):
    if phi == "identity":
        return z - alpha

    sig = torch.sigmoid(z)
    s = z * sig
    dsilu = sig + s * (1.0 - sig)
    return dsilu * (s - alpha)

The sigmoid on this path appears because SiLU itself is SiLU(z) = z σ(z). It is unrelated to the sigmoid used earlier to constrain beta.

The derivative is:

SiLU′(z) = σ(z) + z σ(z)(1 − σ(z))

In the code, s = z * sig, so sig + s * (1 - sig) is exactly that derivative. The return statement is:

dsilu * (s - alpha)  =  φ′(z) ⊙ (φ(z) − α)  =  Jφ(z)T(φ(z) − α)

The script avoids constructing a square Jacobian because the elementwise activation tells us in advance that only its diagonal can be nonzero.

8. Continue back through z = M w

The gradient with respect to memory is an outer product

We now have u = ∂L / ∂z. The previous operation was z = Mw. Differentiating that operation with respect to the memory matrix gives:

∇ML = u wT

If u has S coordinates and w has D coordinates, then u wT has shape S × D, exactly the shape of one memory matrix.

NotationOperation here
a ⊙ bHadamard or elementwise multiplication.
u wTOuter product; produces the memory gradient matrix.
A ⊗ BKronecker product; not used in this step.
9. Read the full recurrence in trellis_scan()

Predict, compute the error code, form the outer product, update memory

for t in range(write.shape[2]):
    w = write[:, :, t, :]
    z = torch.einsum("bhmd,bhd->bhm", state, w)
    u = error_code(z, alpha[:, :, t, :], phi)
    update = torch.einsum("bhm,bhd->bhmd", u, w)
    state = (
        beta[:, :, t, :].unsqueeze(-1) * state
        - g * update
    )

For one batch item and one head, the same code is:

zt = Mt−1wt
ut = ∇ztLt
∇MLt = utwtT
Mt = βtMt−1 − γutwtT

The first line asks what memory currently says at this address. The second computes how that answer should change. The third lifts that error back into a matrix-shaped gradient. The fourth retains most of the old state and takes one gradient step.

10. Understand why the router has two memories

One memory maps aliases to a shared code; the other maps that code to tools

key_state, _ = trellis_scan(
    key, alpha, beta, gamma, self.phi, key_state
)
value_state, _ = trellis_scan(
    value, alpha, beta, gamma, self.phi, value_state
)

The key memory writes alias-derived vectors against target α. The value memory writes tool vectors against the same target α. The shared target code is the bridge between the two memories.

alias → key memory → code → read map → value memory → tool vector

The query path first reads the key memory with the alias-derived query. It transforms and normalizes that slot code, then uses the resulting code to read the value memory and compare the reconstructed vector against the tool bank.

code = torch.einsum(
    "bhmd,bhqd->bhqm", key_state, query
)
code = F.silu(code)
code = code - code.mean(-1, keepdim=True)
code = code / (
    code.std(-1, keepdim=True, unbiased=False) + 1e-6
)

got = torch.einsum(
    "bhmd,bhqm->bhqd", value_state, code
)
got = F.normalize(got, dim=-1).squeeze(1)
logits = got @ self._tool_bank().T

This F.silu(code) is part of the read map. It is separate from the manual SiLU derivative in error_code(), which constructs the inner learning signal used to update memory.

11. Follow one episode through bind, query, overwrite

The overwrite is the important test of the learned write rule

state = model.blank_state(
    batch, aliases.device, aliases.dtype
)
state = model.bind(state, aliases, tools)
logits_before = model.query(state, aliases)

state = model.bind(
    state,
    aliases[rows, index].unsqueeze(1),
    new.unsqueeze(1),
)
logits_after = model.query(state, aliases)

A memory that merely accumulates associations can keep returning a stale value after an overwrite. The Trellis residual is state-dependent: z = Mw first asks what is already stored, and the update is based on the error between that existing response and the new target. That gives the mechanism a direct way to correct an old association rather than only add another one.

12. Recover Gated DeltaNet by removing the nonlinearity

Set phi = identity and the Jacobian disappears

If φ(z) = z, then Jφ = I. The error code becomes:

u = z − α = Mw − α

The Trellis write becomes:

M ← βM − γ(Mw − α)wT

Move the sign into the residual:

M ← βM + γ(α − Mw)wT

That is the gated delta-rule form: retain the old state, predict what is stored at the current address, compute the residual, then write that residual back along the address direction. The linear-attention page develops DeltaNet and Gated DeltaNet in the broader architecture context.

13. Connect the nonlinear write to the implementation cost

State-dependent nonlinear writes break the exact affine chunking shortcut

With identity φ, the update is affine in the current state. A sequence of such rank-one updates can be reorganized into chunkwise matrix operations. The WY/UT page explains the algebraic machinery behind that kind of blocking.

With nonlinear φ, the next error code depends nonlinearly on the state produced by earlier writes:

ut = Jφ(Mt−1wt)T (φ(Mt−1wt) − αt)

The exact recurrence is therefore naturally sequential. The minimal script implements that exact token-by-token rule. A production chunked path can freeze or approximate within-chunk state to recover larger matrix operations, but that is an implementation tradeoff layered on top of the same memory objective.
