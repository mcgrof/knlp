The four questions, answered where we could

What would a metadata adapter have to show?

Caching where a KV object lives only helps if real work remains after the storage client's own caching, if that work is on the request's critical path, and if reuse never returns the wrong bytes. We stated these four questions before measuring. Three now have answers for the systems we tested: what remains is an open and a close per object, whole-request paired blocks separate it from payload time, and reuse of sealed objects stays correct under the faults we ran. The fourth, the effect on a serving request, is still open. Each section keeps the question and adds what we found; the numbers are on the results page.

1. What metadata work remains after normal client caching?

A network filesystem client already caches a great deal. The Linux NFS client keeps file handles, attributes and directory entries, and it can hold delegations that let it skip some server checks. A pNFS client also keeps the layouts the metadata server hands out and reuses them until the server recalls them or they are returned. Whatever an application-level cache could save is what survives all of that.

The answer depends on the client, the server, the mount options and the access pattern. The first read of an object, a repeated read of the same object and a read after a long idle period can each send different operations. An answer therefore has to name the software versions and default settings it used, count the operations actually sent for each case and leave the normal caches enabled. Disabling a cache to create work for an adapter to remove would answer a different question.

What we found. With normal caching on, a repeated read sends no layout or device request: the Linux pNFS client keeps both across close. What remains is the open and the close. On the Lattice metadata server, which grants no delegations, that is one OPEN and one CLOSE compound, four server operations per object read. On a Linux NFS server that grants read delegations, no operation reaches the server at all, and the open and close cost only client CPU (11.4 µs and 1.36 µs per call, against 1.07 µs and 0.35 µs on local XFS). A plan cache has nothing to remove that a held file descriptor does not remove more simply.

2. How can metadata, scheduling and payload time be told apart?

A read request spends time waiting to be scheduled, resolving the object, moving bytes and completing. Network round trips for metadata may overlap with data transfer or with each other, so the sum of individual operation times is not the time a request could save. Per-operation statistics are useful for finding where time goes, not for subtracting.

The safer unit is the whole request, timed from submission to completion and checked for correct bytes. Percentiles should come from complete requests. When two configurations are compared, they should differ in one thing and run alternately on the same system, because a comparison between different filesystems or adapters changes more than metadata. Tracing and verification also cost time, so it helps to know how much the measurement itself adds.

What we found. We timed whole requests in paired, alternating blocks that differ in one setting, counted RPCs per phase from the client's own counters or a trace, and kept hashing out of the timed window where it would compete with the reads. That separated a 0.2 ms saving per 8 MiB object in the pNFS lab, and showed that on a 1 Gb/s link the same saving is under 1% of a request because the payload dominates. It also caught our own harness twice: a hash inside the timed loop that took half of the cycles, and clients that fell into step and shared each other's cached data.

3. How can reuse stay valid when a location changes?

Two different events can make a remembered answer wrong. The storage system can move or re-replicate data while the object stays the same; in pNFS the server recalls a layout and the client must stop using it. The application can also replace an object under the same name with a new version. The first changes where to read, the second changes what to read, and reuse has to handle both.

Handling them means following the storage system's own recall and lease rules. It also means knowing which object version a request expects, and refusing or refreshing rather than returning old bytes under a new name. A timeout or a checksum alone cannot show that an object is current. Tests need the replacement, deletion, recall, server restart and partial-failure cases, each with a defined correct outcome.

What we found. For sealed objects published by rename and named by their content, reusing an open descriptor returned no wrong byte in 155,494 verified 8 MiB reads over replacement, layout revocation, data-server and metadata-server restarts, a second client's rename and unlink, and a metadata-server partition past its lease. A layout recall to a held reader was never sent by the server, so that case is not tested. The case that breaks reuse is a writer outside LMCache that replaces a name: the held descriptor keeps serving the bytes it admitted. That is why the option is limited to directories only LMCache writes.

4. Does a storage-level change affect a serving request?

A faster storage read matters only if the serving engine was waiting for it. An engine can overlap loading with computation, load some state ahead of time or recompute instead. The relevant measures are serving measures: time to first token, throughput and memory, on a real model, with the output checked against a run that does not use the offloaded state. A storage improvement that does not change those measures may still matter elsewhere, but it is not a serving result.

Still open. None of our measurements runs a serving engine end to end, so we make no time-to-first-token claim. The storage results do bound what a serving test could see: removing four metadata-server operations per object read, and close stalls of up to 3.3 seconds under load on the lab server.

5. What evidence would support a claim?

A claim that metadata caching helps a workload would need several pieces of evidence together. It would need the actual data path, for example which servers carried the bytes, rather than the configured one. It would need byte-exact correctness for every counted request and a named object version. It would need a matched comparison that changes one mechanism, repeated in alternating blocks with an interval rather than a single number. It would need the strongest existing alternative as the baseline, such as the client's own caching or an existing adapter, and a scope statement naming the software, hardware, cache state and workload. A negative result is useful in the same form: it applies to what was tested and redirects effort to the data path.

6. Limits of the basic tools

The basic reproduction is a baseline, not an answer to these questions. It reads one object per request with one request outstanding, from one client. It times whole requests and verifies bytes, but it does not count the NFS operations a request sent, does not check whether pNFS layouts were used and does not control the page cache. It is useful for checking a mount, its correctness and its ordinary whole-object read time before any deeper analysis.

The site and closure profiles run the same RPC counts, paired screen, many-reader sweep and read-mode comparison on any filesystem you already have, as an ordinary user.

The pNFS lab profiles address the first three questions for one server and client pair. They count the RPCs each arm sends to each server, hold every case to byte-exact digests, and compare stock LMCache with held descriptors in alternating blocks. The sweep also records metadata-server operations and CPU per object read as the number of clients grows. They still run on one host or a small number of hosts, with sealed objects and no serving engine, so the fourth question remains open.
