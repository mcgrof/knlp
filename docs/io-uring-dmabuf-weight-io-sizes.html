Which read sizes weight loading produces

No loader we traced asks the kernel for tensor-sized reads. vLLM's default reader maps each file and lets kernel readahead read it in 128 KiB commands. fastsafetensors' nogds reader asks for 516 KiB at a time, which reaches the drive as four 128 KiB commands and one 4 KiB command. Our DMA-BUF copier asks for 64 MiB at a time, straight into GPU memory, and the drive gets 2 MiB commands. Tensor sizes matter when a loader reads only part of a model, such as one expert of a mixture-of-experts layer: current MoE checkpoints store experts as 2 to 16 MiB tensors, and some store an expert's scales far from its weights, which adds a read of a few KiB.

Three sizes in one load

A weight load has three different read sizes, and each layer of the stack can change the size it receives. The tensor size is set by the checkpoint file: how big each tensor is and where it sits. The intent size is what the loader asks the kernel for: its read calls, its memory mappings and its io_uring requests. The command size is what reaches the drive: the NVMe read commands, after the page cache, readahead and the block layer have split or merged the loader's requests. We recorded all three for each load with the tracers of the ebpf-syscall project and one bpftrace script.

Where the command limits come from

The drive itself accepts read commands of up to 2 MiB. Its maximum data transfer size (MDTS) is 9. MDTS counts the controller's minimum memory page, which is 4 KiB on this drive (CAP.MPSMIN 0), so one command can carry 29 × 4 KiB = 2 MiB.

Linux sets a smaller limit, 128 KiB, for normal reads. With the IOMMU translating device addresses (the default DMA-FQ mode here), the NVMe PCI driver caps a command at the DMA-optimal mapping size: dma_opt_mapping_size() in drivers/nvme/host/pci.c. That size is the largest address range the IOMMU keeps in its allocation cache, 32 pages or 128 KiB (iova_rcache_range() in drivers/iommu/iova.c). The queue therefore reports max_hw_sectors_kb and max_sectors_kb of 128, with 33 segments. With the IOMMU in passthrough mode, this cap does not apply. The kernel branch used here also has an nvme module parameter, lift_dma_opt_clamp, that removes it. The parameter was off for every run on this page.

A DMA-BUF read uses the IOMMU mapping made once, when the buffer is registered. It needs no new mapping per command, so the kernel branch limits it only by MDTS: max_hw_dmabuf_sectors_kb is 2048. The block layer splits any larger request at the limit that applies.

Reads through the page cache, including mmap, have one more limit. Readahead reads at most the larger of read_ahead_kb and max_sectors_kb at a time, and both are 128 KiB here. A 4 MiB pread through the page cache therefore reaches the drive as 128 KiB commands. The drive could take 2 MiB commands, but Linux does not send them.

Dense checkpoints keep their bytes in a few large tensors. In Qwen2.5-7B, 89% of the bytes are in tensors of 128 MiB or more. In Llama-3.1-405B, 81% are in tensors of 1 to 2 GiB. Most current MoE checkpoints are the opposite: 87 to 99% of their bytes are in the routed experts, which are stored as separate tensors of 2 to 16 MiB. One expert is 6 MiB (Qwen3-Next) to 42 MiB (DeepSeek-V3 and Kimi-K2 in FP8). Lower precision makes the expert tensors smaller and adds a scale tensor for each weight tensor, so in the FP8 and FP4 checkpoints half of all tensors are scales. The scales hold at most 6% of the bytes. Qwen3.8-2.4T is the exception: it stores all experts of a layer as two fused tensors of 16 and 32 GiB, but one expert is still a contiguous 96 MiB slab inside them.

Where an expert sits matters when a loader reads only some experts. In Kimi-K2 and DeepSeek-V4-Pro every expert is in two places. The safetensors writer groups tensors by data type, so each file holds all its scale tensors together, away from the weights. Fetching one Kimi-K2 expert is one 42 MiB read plus one 10.5 KiB read up to 15 GB away in the same file. In DeepSeek-V4-Pro it is one 31.5 MiB read plus one 2 MiB read. In Qwen3-Next, 9,505 of 24,576 experts are split across two files. In every checkpoint, the tensor data starts off a 4 KiB boundary for more than 99.99% of the bytes, because the data section begins right after a header of arbitrary length.

What loaders ask for

No loader we traced asks the kernel for tensor-sized reads. The loader, not the tensor layout, sets the intent size of a full load. We traced three loaders on four checkpoints that we have in full: two dense BF16 models, an INT4 AWQ model and a 27 GB MoE model (EMO 1b14b, 128 experts per layer). Each load started with an empty page cache, and every tensor was checked against a SHA-256 of the file bytes. All 40 loads matched.

vLLM's default reader

vLLM's default loader opens each shard with the safetensors library and calls get_tensor() for every tensor. We ran the same calls outside vLLM. The library maps the shard into memory and makes no read call on it. Copying a tensor out of the mapping touches its pages. The kernel's readahead then reads the whole file ahead of the copy, so the tracer counted only 0 to 604 page faults per load. The drive gets 128 KiB commands, the Linux limit for a normal command, and reads the file once. This path is about 4 to 5 times slower than the other two here. We did not profile why.

fastsafetensors nogds

The nogds reader reads each shard with pread64 calls of 516 KiB into a host buffer, then copies the buffer to the GPU. Each call is 512 KiB of data plus 4 KiB for alignment. The drive gets four 128 KiB commands and one 4 KiB command for each call. These 4 KiB commands are 20% of all its commands, and they make the drive read 0.8 to 0.9% more bytes than the files hold. This is the only place in a full load where we saw many small commands, and they come from the reader's alignment, not from the tensors.

The DMA-BUF copier

The copier issues io_uring READ_FIXED requests of 64 MiB straight into GPU memory, with a shorter request at the end of each shard. The kernel splits each request into 2 MiB NVMe commands, the largest DMA-BUF command on this drive. For the 15.2 GB model that is 228 requests and 7,260 commands of 2 MiB, against 145,291 commands for nogds. The drive reads the file bytes to within 0.1%. Its only read calls are the 8-byte header length and the JSON header of each shard (9 to 72 KiB). The larger commands are why the copier is the fastest loader here; the weight-loading page explains this with drive rates.

Fetching experts

An MoE server that keeps experts on NVMe reads only the experts a request needs. That is where tensor size becomes intent size. In EMO 1b14b one expert is three 4 MiB tensors, stored next to each other. We fetched one expert and eight experts of one layer, once through safetensors and once with one pread per tensor.

With one pread per tensor, the loader asks for 4 MiB at a time, and the drive gets 128 KiB commands through the page cache. The drive's MDTS allows 2 MiB; the 128 KiB comes from the Linux limits described above. Readahead reads past the end of what was asked: 10% extra for one expert, 2% for eight. Through safetensors the extra is 25% for one expert and 7% for eight. At these sizes the drive gets no command smaller than 128 KiB apart from a few at the edges.

Two cases in the larger checkpoints would produce smaller reads. A fetch of one Kimi-K2 expert includes a 10.5 KiB scale read. Qwen3-Next stores 2 MiB expert tensors, so a reader that reads one tensor at a time asks for 2 MiB. We did not trace those checkpoints, because we have only their headers. We have also not traced an expert fetch through the DMA-BUF copier. With it, one expert would be one io_uring read into GPU memory, split into 2 MiB commands.

Reproduce

The scripts are in knlp's scripts/weight_io. You need the kernel branch above for the DMA-BUF loader, a built ebpf-syscall tree, bpftrace, and sudo for the tracers. The loaders run as your user. Put the fastsafetensors branch on PYTHONPATH:

git clone -b 2026-10-28-iouring-dma-buf https://github.com/mcgrof/fastsafetensors
export PYTHONPATH=$PWD/fastsafetensors
python3 scripts/weight_io/trace_intent.py --tools ~/ebpf-syscall --disk nvme0n1 \
    --model qwen2.5-7b=/models/Qwen2.5-7B-Instruct \
    --model moe=/models/my-moe --moe moe --out /data/intent
python3 scripts/weight_io/analyze_intent.py /data/intent > intent_summary.json

--moe adds the expert fetches for that model; --layer, --experts-1 and --experts-8 choose the layer and the experts. --disk names the block device that holds the models, so the NVMe tracer watches the right drive. For the checkpoint layout, the inventory stage of the weight-loading I/O workflow (make defconfig-weight-io-inventory && make) reads the shard headers over HTTP without downloading weights, and inventory_sizes.py turns its inventory.jsonl into the size classes and expert units shown above.

Limits

  • One GPU, one drive and one file system (XFS). A drive with a larger or smaller command limit changes the command sizes.
  • The loaders ran outside vLLM with the same calls vLLM makes. A served load can add its own reads.
  • Each case ran twice. That is enough to show the sizes, which do not change between runs, not to rank small timing differences.
  • The eight large checkpoints were measured from their headers only. Their read sizes under each loader are projected from the layout, not traced.
  • No tensor-parallel load was traced. A rank that reads part of a tensor can produce strided reads.
  • Expert fetches through the DMA-BUF copier were not traced.
